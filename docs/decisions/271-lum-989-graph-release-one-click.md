## Context
Since 0.13.0 the default install is two Release files, and the knowledge graph cannot run on it: the `lumogis-graph` image is not published and no graph services ship with the Release. Checkout installs turn it on by editing `.env` (two overlay files in `COMPOSE_FILE`, four settings and a hand-made secret) and restarting. The graph adds about 4 GB (the service's memory cap) on top of a base documented at about 8 GB, while entities, search, chat and "What Lumogis knows" already work without it. Published graph-vs-vector RAG results are mixed (graph helps multi-hop questions; plain RAG matches it on lookups), and Lumogis has no eval of its own. FalkorDB is SSPLv1, used today by pulling upstream's image.

## Decision
**Packaging.**
- Publish `lumogis-graph` as a sixth GHCR image (multi-arch, attested, LUM-980 pattern).
- The Release `docker-compose.yml` carries FalkorDB and `lumogis-graph` as services in an allowlisted `graph` profile, generated by the release builder from the existing overlays. Checkouts keep the overlays.
- The Release FalkorDB image is `falkordb/falkordb-server` (291 MB), provided an RDB round trip and a backup/restore from the full image are proven; otherwise the full image.
- The knowledge graph stays **off by default** everywhere.

**One click, Release installs only.** Admin → Knowledge graph gains Turn on and Turn off.
- **Core** (admin, same-origin, audited) writes `COMPOSE_PROFILES=graph`, `GRAPH_MODE=service`, `KG_SERVICE_URL`, `CAPABILITY_SERVICE_URLS`, `FALKORDB_URL` and a generated `GRAPH_WEBHOOK_SECRET` into `.env`, through one mode- and owner-preserving writer (`services/host_env.py`).
- **stack-control** starts the two services with fixed arguments and recreates `backup` and Core (`POST /graph/start`, `POST /graph/stop`).
- Checkouts keep the written steps, because their graph image is built locally.

**The memory verdict is advisory.** Below the threshold, Turn on asks the admin to confirm instead of refusing. The threshold is set from a measured footprint (8 GiB + measured peak + 1 GiB), never above 12 GiB.

**The page reports the sequence.** It gets the states `starting`, `stopping`, `start_failed` and `stop_failed`, and a server-computed table of which button is available (`turn_on`, `turn_off`).

**Offer.** Admins see an offer on the page while the graph is off and one dismissible line in System status; members see nothing.

**stack-control's environment.** Its `docker compose` calls no longer inherit `.env` values from the sidecar's own start-up (`_compose_env()`). Compose reads them from the file, so a sidecar created before a change cannot recreate services with stale values.

**Packaging boundary.** The graph is not built into the Core image.

## As built (deviations from the draft, intent preserved)
- **The threshold is measured: 10 GiB (LUM-991).** On the LUM-929 seeded RC stack (Apple M4, Docker Desktop 15.6 GiB), FalkorDB plus `lumogis-graph` used 0.13 GiB idle and peaked at 0.165 GiB together during a library Rescan; the Rescan was stopped after 50 of 294 files by Thomas's decision (2026-11-18), so the figure covers that part of the library. The rule gives 8 + 0.5 + 1 = 9.5 GiB; `GRAPH_MIN_TOTAL_MEMORY_BYTES` is set to **10 GiB**, rounded up to a whole number so the copy and the quickstart keep saying "about N GB" (`test_quickstart_graph_memory.py` pins a whole number of GiB). The copy and the quickstart now say "about 2 GB more … about 10 GB in total" instead of "about 4 GB more … about 12 GB"; the service's 4 GB memory cap (`KG_MEM_LIMIT`) is unchanged.
- **`falkordb-server` is proven (LUM-991).** An RDB dump written by `falkordb/falkordb:v4.18.1` loads in `falkordb/falkordb-server:v4.18.1` with identical counts (toy stack), and the reverse holds. On a release-shaped install `make backup` includes FalkorDB from the server image, and a restore with FalkorDB stopped before `restore.sh` brings the graph back exactly. `RELEASE_FALKORDB_IMAGE` stays `falkordb/falkordb-server:v4.18.1`. The documented restore order (restore, then restart `falkordb`) loses the graph on **both** images, because the running engine saves its in-memory data over the restored `dump.rdb` on shutdown; that is a restore-procedure defect, not an image one, and is tracked separately.
- **State order.** `stop_failed` and `stopping` come before `on`, because the graph is still healthy while it is being stopped and a failed stop leaves it running. `stopping` ends when Core has been recreated after the stop began (`graph_toggle.CORE_STARTED_AT`), the sequence's last step.
- **Windows.** `starting` lasts up to 35 minutes and `stopping` up to 10 (the plan said 10 and 5), so both outlast stack-control's own step budgets (the pull step alone may take 25 minutes).
- **`TurnOffBlock` gains `compose_too_old`.** A Release file without the profile cannot stop what it does not define.
- **`confirm_low_memory` is a strict boolean.** A non-boolean is a 422, never coerced.
- **A failed state clears only on the next action.** `start_failed` / `stop_failed` stay until Retry or the other button; a healthy graph still reads `on` over an older start failure.

## Alternatives Considered
- **A third Release file (`docker-compose.graph.yml`):** every graph install manages an extra file and `COMPOSE_FILE`, single-file tools can't use it, and one click would have to fetch it.
- **Graph services always present in the Release file:** every household pays for an optional feature.
- **On by default:** raises the memory floor from about 8 to about 12 GB for an unmeasured benefit; out-of-memory on common 8 GB machines and Docker Desktop defaults.
- **On automatically when memory allows:** starts containers and downloads about 1 GB nobody asked for; the offer reaches the same households with consent.
- **Written steps only:** Release users would edit `.env` and generate secrets, the friction the two-file install removed.
- **A general service manager over the Docker socket:** far more surface than one switch.
- **One click for checkouts too:** their `lumogis-graph` image is built locally and stack-control runs `--no-build`; building from the sidecar takes minutes and build tooling. Deferred (Later in LUM-989).
- **Refuse Turn on below the memory threshold:** the threshold is an estimate, and on Docker Desktop the admin can raise the VM's memory; Thomas chose warn + confirm (2026-11-17).
- **The graph inside the Core image (`GRAPH_MODE=inprocess`):** FalkorDB stays separate anyway; Core gets bigger for everyone, loses the graph's memory cap and process isolation, the in-process path is unproven at household speed, and bundling the FalkorDB server would put SSPL software inside an AGPL image.

## Consequences
- **Easier:** Release households turn the graph on and off from the admin page; the Release stays one compose file; nothing changes for households who never turn it on; the graph's download falls from about 2 GB to about 1 GB with `falkordb-server`.
- **Harder:**
  - The release builder's profile rule has one exception (`RELEASE_PROFILES`), and `check()` verifies the graph services, their profile and the file's `depends_on` and volume names without Docker.
  - The admin page gets a write path through stack-control. This supersedes ADR 267's read-only point and replaces ADR 267's "Release installs cannot turn it on yet" copy, as ADR 267's own revisit condition foresaw.
  - Four CI workflows and the release skill cover a sixth image. A new GHCR package starts private: the first Release with the graph profile must wait until `lumogis-graph` is public, or a household's first Turn on fails with `compose_failed`.
  - The state enum ADR 267 made LUM-196's contract gains four states; readers treat them as "not on".
  - The restart token now also permits starting and stopping the graph services (same trust level as `/restart`).
- **Future chunks must know:**
  - `docker compose down` skips profiled services when the profile is inactive, so turning the graph off stops and removes the services by name.
  - Neither `backup` nor `orchestrator` may `depends_on` a profiled service; Core's registry discovery is the only readiness signal.
  - Every stack-control compose call goes through `_compose_env()`; a new endpoint passes it as `env=`.
  - Core's `.env` writes go through `services/host_env.py` (one lock, atomic, mode and owner kept).
  - The Turn on/off `.env` keys and the toggle record in app settings (`graph_toggle_op`, `_started_at`, `_failed_at`, `_failed_code`) are owned by `services/graph_toggle.py`.
  - stack-control's `/graph/*` recreates `backup` and `orchestrator`; a future service that reads graph settings from `.env` must be added to `GRAPH_RECREATE`.

## Revisit conditions
- **Default on:** revisit when (a) a Lumogis eval on a household library shows graph context improves answers on multi-hop questions without hurting lookups, **and** (b) the measured footprint of FalkorDB plus `lumogis-graph` at household scale is small enough that the base memory floor (about 8 GB) still holds.
- **Threshold:** when the footprint is measured, set `GRAPH_MIN_TOTAL_MEMORY_BYTES = 8 GiB + ceil(peak, 0.5 GiB) + 1 GiB` and change the copy and quickstart with it (`test_quickstart_graph_memory.py` pins the quickstart). If that comes out above 12 GiB, the "about 4 GB" premise is wrong: stop and decide again.
- **Packaging:** if `GRAPH_MODE=inprocess` is retired, or an image where it runs ships, update ADR 267's state machine and this ADR together.
- **Release files:** if Compose profiles stop being honoured from `.env` by a supported Compose version, switch to a third Release file.
- **Licence:** if FalkorDB changes its licence or image layout (e.g. drops `falkordb-server`), re-check the Release image choice.
