## 1. What Lumogis is

**In plain language:** Lumogis is a **self-hosted household AI platform**. The guiding idea is: **the AI comes to your data, not the other way around.** Your documents, notes, memory, and indexes stay on hardware you control (a home server, NAS, or workstation). When you ask a question, Lumogis **finds relevant context locally**, **assembles a composed prompt**, and sends that bundle to an LLM—**fully local** if you use Ollama, or **to a cloud provider** if you configure one. In the cloud case, **composed prompts and retrieved excerpts** (not your full local corpus) may leave the machine; see **§2** and **§8** for precision. **Connectors** (calendars, ntfy, LLM APIs, …) **call their configured external services by design** when you use those features. Lumogis is **not** a hosted SaaS, public marketplace, or multi-tenant cloud product; it is aimed first at a **family or household on a LAN**, with **Core** as the trust anchor for identity, policy, credentials, and audit.

**Examples:**

- Ask Lumogis to **find something** across your indexed notes and files (semantic search + retrieval).
- Let Lumogis **remember household context** across sessions (memory scopes: personal, shared, system—see [ADR 015](decisions/015-personal-shared-system-memory-scopes.md)).
- Use **tools and actions** with **Ask/Do** permissions and an **audit log** so destructive or external effects are visible and approvable.
- An **admin** can manage **users**, **connector credentials**, **tokens**, and **read-only diagnostics** from Lumogis Web; members use chat, search, and their own settings.

**Technical nutshell:** The **orchestrator** (FastAPI “Core”) owns HTTP APIs, business logic in `services/`, infrastructure via `adapters/`, optional in-process `plugins/`, **signals** and **actions**, Postgres metadata, Qdrant vectors, and optional **out-of-process capability** services (e.g. `lumogis-graph`). **Lumogis Web** is the **primary** first-party client for **multi-user household** chat, settings, and admin surfaces (same-origin with `/api/v1/*`). **LibreChat** is an **optional**, **legacy-compatible** OpenAI-style chat UI (compose profile)—useful for continuity with older setups; it is **not** the supported multi-user identity surface ([ADR 012](decisions/012-family-lan-multi-user.md)). Nothing here implies a scheduled removal unless a future release note says so.

## 2. Core principles

| Principle | Lay explanation | Technical note |
| --- | --- | --- |
| **Local-first / privacy-first** | Your archive stays on your machine. | Raw corpus, embeddings store, and audit DB are local; cloud use is opt-in per provider keys. |
| **Self-hosted by default** | You run the stack; there is no Lumogis cloud that holds your files. | Docker Compose; operator sets `.env`, Caddy, and secrets. |
| **Core owns policy and execution** | “What is allowed” is not reimplemented in random clients. | Auth, connector permissions, tool execution gates, audit—see [ADR 028](decisions/028-self-hosted-extension-architecture-and-household-control-surfaces.md). |
| **Users and household roles** | Operators vs members: admin can manage the instance; users use data scoped to them. | `admin` vs `user` roles, `users` table, `UserContext`—[ADR 012](decisions/012-family-lan-multi-user.md). |
| **Safe credential handling** | Passwords and API keys are not splashed in the UI after save. | Encrypted credential payloads, copy-once tokens where applicable—[ADR 018](decisions/018-per-user-connector-credentials.md), [027](decisions/027-credential_scopes_shared_system.md), [029](decisions/029-self-hosted-account-password-management.md). |
| **Auditability** | Important actions leave a trail. | Append-only `audit_log`; structured logging—[ADR 019](decisions/019-structured-audit-logging.md). |
| **Modularity** | Swap vector store, LLM, etc., via adapters and ports. | `ports/` + `config.py` factories—`ARCHITECTURE.md`. |
| **Optional capabilities** | Heavy or isolated features can run **beside** Core, not inside its DB. | HTTP manifest at `GET /capabilities`, bearer trust—[ADR 010](decisions/010-ecosystem-plumbing.md), **[ADR 002](decisions/002-graph-store-falkordb.md)** (graph Protocol + optional premium overlays). |
| **Bounded agents under Core policy** | Assistants stay permission-gated and audited—not unconstrained operators beside household controls. | Tool loops honour Ask/Do, audit, and catalog behaviour documented in shipped ADRs and extension guidance below. |
| **No full-corpus cloud upload by default** | Your entire indexed library is not bulk-uploaded to an LLM vendor. | If a **cloud LLM** is configured, **composed prompts + retrieved excerpts** may leave the machine; **Qdrant/Postgres and raw files stay local** unless another feature sends them out. **Connectors** intentionally reach **their** configured services. |

## 4. Mental model: Core, clients, connectors, tools, capabilities

Aligned with [`docs/architecture/tool-vocabulary.md`](architecture/tool-vocabulary.md). For each term: **easy explanation**, then **technical definition**.

| Term | Plain English | Technical |
| --- | --- | --- |
| **Core** | The brain on your box: policies, storage, and execution. | The orchestrator process and its adapters—Postgres/Qdrant/Ollama/etc. |
| **Client** | A program that talks to Core over HTTP and shows UX. | **Lumogis Web** (household + admin); optional **LibreChat** (chat-only legacy path); scripts; must stay thin—no direct DB. |
| **Connector** | A named channel for secrets/settings (ntfy, CalDAV, paperless-ngx, LLM provider, …). | Registered id in `connectors/registry.py`, encrypted rows in `user_connector_credentials`, tiers per [ADR 027](decisions/027-credential_scopes_shared_system.md); `ToolSpec.connector` links tools to permission checks. |
| **Credential** | The saved secret or config Lumogis uses on your behalf. | Encrypted payload + MultiFernet key rotation support in `_credential_internals`; never returned raw in Web façades. |
| **Tool** | Something the model may **call** with structured arguments. | `ToolSpec` + OpenAI-style definition; executed via `run_tool` / `ToolExecutor` with permission gates. |
| **Action** | A registered, audited operation (often with side effects). | `actions/` registry + executor + Ask/Do—[ADR 006](decisions/006-ask-do-safety-model.md). |
| **Signal** | Something the world pushed or that Core polled (feed, page, calendar…). | `SignalSource.poll()` → scoring → storage → `Event.SIGNAL_RECEIVED`. |
| **Routine** | Automation that can **elevate** Ask→Do after trusted approvals. | `services/routines.py`, threshold from env—paired with action audit. |
| **Plugin** | In-process Python extension in Core. | `plugins/<name>/`; hooks + optional `config` carve-out for first-party graph plugin—[`plugin-imports.md`](architecture/plugin-imports.md), [ADR 005](decisions/005-plugin-boundary.md). |
| **Capability** | Optional **separate** service Core discovers and may call. | HTTP `GET {base}/capabilities`, `GET {base}/health`, `POST {base}/tools/{name}`; bearer trust; **no** shared Core DB—[ADR 010](decisions/010-ecosystem-plumbing.md). |
| **MCP** | A **transport** exposing a small, curated tool set for agents. | FastMCP at `/mcp/`—not the full tool registry; [ADR 010](decisions/010-ecosystem-plumbing.md), [017](decisions/017-mcp-token-user-map.md). |

## 5. The five contributor pillars

Lumogis maps code to **five** pillars ([`ARCHITECTURE.md`](../ARCHITECTURE.md)):

1. **Services** — business logic (`orchestrator/services/`): search, memory, ingest, unified tool catalog builder, capability registry helpers, users, connector credentials, etc.
2. **Adapters** — one file per external system (`orchestrator/adapters/`): Qdrant, Postgres, Ollama, extractors, notifiers.
3. **Plugins** — optional in-process packages (`orchestrator/plugins/`).
4. **Signals** — monitors and scoring (`orchestrator/signals/`).
5. **Actions** — executable operations with audit (`orchestrator/actions/`).

**Tool catalog / execution** is a **cross-cutting overlay**, not a sixth pillar: `build_tool_catalog` / `build_tool_catalog_for_user` observe registries; `ToolExecutor` and `run_tool` enforce execution. **Capabilities** are **out-of-process** services, not plugins. **Routes** (`orchestrator/routes/`) should stay **thin** and call services—routes must not import adapters (CI-enforced).

**Examples in-repo:** `services/unified_tools.py` (catalog + `prepare_llm_tools_for_request` / `finish_llm_tools_request`), `services/execution.py` (`ToolExecutor`), `services/capability_http.py` (HTTP invoke + `graph_query_tool_proxy_call`), `services/me_tools_catalog.py` + `routes/me.py` (`GET /api/v1/me/tools` façade).

## 6. Users, roles, and household model

**Lay view:** A home instance has an **admin** (operator) and one or more **users** (family members). Everyone signs in through Lumogis Web when `AUTH_ENABLED=true`. With `AUTH_ENABLED` off (the default), Lumogis Web opens without sign-in as the single admin and shows a banner saying so; the mode is re-read from Core on every load (LUM-853). The admin can reset passwords and manage household-level settings; members see only their data unless shared scopes apply.

**Technical view:**

- **`users` table** — accounts with argon2id password hashes, `role` (`admin` | `user`), optional `disabled`, monotonic **`token_version`** for access-JWT invalidation—[ADR 012](decisions/012-family-lan-multi-user.md), [029](decisions/029-self-hosted-account-password-management.md), [041](decisions/041-jwt-access-token-revocation-multi-device-sessions.md). Refresh rotation uses **`auth_sessions`** rows (migration **`023`**); the legacy **`refresh_token_jti`** column was dropped in migration **`037`** (LUM-244) once its downgrade window closed. Nullable **`onboarding_completed_at`** (migration **`025`**, LUM-165) records when the authenticated user dismissed the first-run onboarding gate in Lumogis Web. Nullable **`wow_dismissed_at`** (migration **`028`**, LUM-216) records when the user dismissed the first wow-moment card path (guided query + entity discovery on chat).
- **`auth_sessions` table** — one row per browser/device refresh session (distinct from chat **`sessions`** in migration **003**): hashed refresh token, **`family_id`** for OAuth-style reuse detection, optional **`device_label`** / fingerprint hashes—[ADR 041](decisions/041-jwt-access-token-revocation-multi-device-sessions.md).
- **Chat `sessions` table** (migration **003**, memory scopes in **013** — distinct from **`auth_sessions`** above): per-user conversation ledger with **`updated_at`** maintained by the shared **`set_updated_at`** trigger; migration **024** adds **`idx_sessions_user_updated_at (user_id, updated_at DESC)`** so **`memory.recent_sessions`** / MCP recency reads stay index-friendly as the table grows—[ADR 055](decisions/055-lum-209-sessions-recency-index.md).
- **Conversation history (LUM-162)** — Lumogis Web **`GET/DELETE /api/v1/conversations`** lists ended chats from **`sessions`** (after **`POST /session/end`** enqueues summarization). Continue seeds a **new** tab thread with summary context (slice 1) or verbatim transcript from **`web_conversations` / `web_messages`** (migration **027**, slice 2). **`POST /api/v1/conversations/{id}/messages`** and conversation detail responses accept optional **`source_refs`** (citation JSONB array) and **`action_proposal_id`** (nullable FK to **`action_proposals`**, migration **047**, LUM-395) so LUM-205 can render citations and proposal links from persisted rows; stable citation keys include **`document_id`**, **`chunk_index`**, **`quote`**, **`file_path`**. Cross-user proposal references return **404** `conversation_not_found`; unknown proposal ids return **422** `invalid_action_proposal`. Hard delete purges Postgres, Qdrant session points, and the personal FalkorDB **`Session`** node when graph mode is enabled; partial vector/graph failures return **`partial: true`** with an honest retry toast. **`purged_conversations`** tombstones (migration **034**) plus APScheduler **`purge_partial_sweep`** (LUM-416) reconcile stranded Qdrant/graph arms; published Session projection nodes are removed on delete (LUM-419). **`GET /api/v1/memory/recent`** (MCP/desktop consumers) returns recent **`sessions`** rows with **`ended_at`** mapped from **`updated_at`** (**LUM-418**); the Web sidebar uses **`/conversations`**, not **`/memory/recent`**. Lumogis Web **`threadStore.ts`** still holds per-tab ephemeral UI state until LUM-205 wires full server-side thread load.
- **Document library (LUM-160)** — Lumogis Web **`/documents`** lists ingested **`file_index`** rows via **`GET /api/v1/documents`** with derived status (`indexing` / `indexed` / `failed`). Personal documents can be **hard-deleted** (`DELETE /api/v1/documents/{id}`) across Postgres (including shared projections), Qdrant chunk points (`document_chunk_point_id`), and optional FalkorDB **`Document`** nodes; partial failures tombstone in **`purged_documents`** (migrations **032–033**) with UI retry (LUM-500/501). **Re-ingest** (`POST /api/v1/documents/{id}/reingest`, optional **`force`**) enqueues **`ingest_upload`** or **`ingest_watch_file`** batch work when the source file still exists on disk; missing sources return **409 `source_unavailable`**. **Push upload** (`POST /api/v1/ingest/upload`, 202) returns **`job_id`**; optional header **`X-Lumogis-Batch-Id`** groups multi-file batches. **Progress poll:** **`GET /api/v1/ingest/jobs/{job_id}`** and **`GET /api/v1/ingest/batches/{batch_id}`** (server returns `completed` / `failed` / `in_progress` only — the web client owns upload **`total`**). **SSE:** **`ingest_progress`** on **`GET /api/v1/events`** mirrors poll JSON; coarse list refresh still uses **`document_status_changed`** plus TanStack Query polling while any row is **`indexing`**. Stage bar on document detail is for **re-ingest** / **`in_flight_job_id`**; fresh multi-file upload progress lives in the library upload panel (LUM-511, [ADR 110](decisions/110-lum-511-ingest-job-progress-ux.md)). — [ADR 101](decisions/101-lum-160-document-library-ui.md), follow-ups [103](decisions/103-lum-160-document-purge-followups.md).
- **Household document sharing (LUM-157)** — a document **owner** can share a personal document with the household from the detail view (**`POST /api/v1/documents/{id}/publish`**, body `{"scope":"shared"}`) and revoke it (**`DELETE /api/v1/documents/{id}/publish`**). Both **validate ownership synchronously** (`404` foreign / non-personal, `400` invalid scope) then **enqueue a background job** and return **`202 {document_id, job_id, share_status}`**. Sharing does more than flip metadata: the **`share_document`** batch handler **projects the document's Qdrant chunks into `scope='shared'` by reusing the stored vectors** (no re-embed) so other members can genuinely **search and document-chat** the content; unshare removes only those shared copies. New job stages **`projecting`** / **`partial`** flow through **`ingest_progress`** and the **`GET /api/v1/ingest/jobs/{job_id}`** poll (a chunk-level upsert failure yields an honest **`partial`**, never a false `shared`). Concurrency is serialised per-document via a Postgres advisory lock (**`services/share_lock.py`**) so a share and a re-ingest re-projection can't race; re-ingesting a still-shared source **re-projects** shared chunks (**`reproject_shared_on_reingest`**) so members never see stale content; purging the source removes the shared chunks (no orphans). `DocumentSummary`/`DocumentDetail` gain **`share_status`** (`personal` / `sharing` / `shared` / `unsharing` / `partial`), **`in_flight_share_job_id`**, and **`is_owner`**; the owner's own projection row is collapsed in `list_documents` (one row per shared doc). Web: an owner-gated **`ShareToggle`** (plain-language confirm before sharing; non-owners see a read-only indicator), a **"Shared"** badge (precedence system > shared > personal), and a **"Shared with household"** filter on **`/documents`**. Owner-only enforcement is server-side (a forged non-owner call still `404`s); `is_owner` gates only the UI affordance. Requires migration **046** (partial `file_index_user_path_uniq` `WHERE published_from IS NULL`, so the shared projection row doesn't collide with the source). The lower-level raw route **`POST /api/v1/files/{id}/publish`** projects small documents inline but routes any document with more than **`LUMOGIS_SHARE_INLINE_MAX_CHUNKS`** chunks (default **50**) to the same background `share_document` job, so a large share never blocks the request thread. Re-sharing after a re-ingest **unprojects then re-projects** so the shared set exactly mirrors the current source chunks (no stale/orphaned shared points), chunk projection is gated to `scope='shared'` only, and each projected chunk requires an integer `chunk_index` (chunks missing one are skipped with a warning rather than colliding on a shared point id). — [ADR 155](decisions/155-lum-157-document-content-projection.md), scope model [ADR 015](decisions/015-personal-shared-system-memory-scopes.md).
- **Graph-aware document entity sharing (LUM-586)** — when a household document is shared (LUM-157), the **`share_document`** background job also cascades the document's **extracted entities** into `scope='shared'` (Postgres `entities` + Qdrant `entities` points, reusing LUM-581's `project_entity` with `share_origin='document'`), then fires a **`DOCUMENT_SHARED`** webhook so the KG service (`GRAPH_MODE=service`) MERGEs shared `:Entity` nodes and sweeps incident `RELATES_TO` edges between shared endpoints. The cascade is a **no-op when graph mode is `disabled`**. In **`GRAPH_MODE=inprocess`**, Core still creates the shared Postgres+Qdrant rows and fires the hook event, but **does not** project shared entities into FalkorDB — the in-process graph plugin deliberately excludes `on_document_shared`; operators who want graph-aware household recall after document share **must use `GRAPH_MODE=service`** (out-of-process `lumogis-graph` webhook + shared reconcile arm). Under **`GRAPH_MODE=service`**, the orchestrator has no in-process FalkorDB connection but dispatches the webhook to the KG service. **Refcounted retraction** on owner unshare (`unproject_file`), admin unshare (via `unproject_file` in the sharing registry), and hard purge (`document_purge`) removes doc-only shared entities when no other still-shared document justifies them; entities independently shared via LUM-581 (`share_origin='user'`) survive document unshare, and dual-provenance rows (`'multiple'`) downgrade to `'user'` rather than delete. A daily **shared-scope reconcile** arm (`reconcile_shared_entities`) backstops dropped webhooks. Requires migration **050** (`entities.share_origin`). Grouped-under-source-document UI in "My shared items" remains a deferred LUM-583 follow-up. — [ADR 158](decisions/158-graph-aware-entity-sharing-lum586.md), builds on [ADR 155](decisions/155-lum-157-document-content-projection.md).
- **Household entity sharing (LUM-581)** — an entity **owner** can share one of their own personal entities with the household, and unshare it, from the memory/entity surface in Lumogis Web. It reuses the **existing** publish routes (**`POST /api/v1/entities/{id}/publish`** body `{"scope":"shared"}`, **`DELETE …/publish`**) and the `project_entity`/`unproject_entity` Qdrant mirror — **no new route, no background job**. Unlike documents, an entity is a single vector point, so publish/unpublish is **synchronous** (`200/204`; no `sharing`/`partial` job stages). The entity read models (`EntityCard` from **`GET /api/v1/kg/entities/{id}`** and **`GET /api/v1/kg/search`**) gain **`share_status`** (`personal` / `shared` only) and **`is_owner`**, mirroring the LUM-157 cross-resource contract (`is_shared` is a derived convenience). Derivation is server-side and parameterised: an owner's personal source reads `shared` when a `published_from` projection exists for it, another member's projection row reads `shared` with `is_owner=false`, and the owner's own projection row is **collapsed** out of search results so they see one entity, not a duplicate. Web: an owner-gated **`EntityShareToggle`** (plain-language confirm before sharing; non-owners see a read-only "Shared with your household" indicator), a **"Shared"** badge, and a **"Shared with household"** filter on the search surface. Owner-only enforcement is server-side (a forged non-owner call still `404`s via the `WHERE user_id=%s AND scope='personal'` fetch guard); **staged** entities are refused (`409 entity_is_staged`) so an unreviewed extraction is never leaked. No schema or collection change. — reuses [ADR 155](decisions/155-lum-157-document-content-projection.md), scope model [ADR 015](decisions/015-personal-shared-system-memory-scopes.md).
- **Bootstrap admin** — first user creation when the table is empty and bootstrap env is set (see `.env.example` / ops docs).
- **Authentication** — `/api/v1/auth/*`: login, refresh (httpOnly cookie), logout. Access JWT carries **`sid`** (session id) and **`tv`** (token-version snapshot); middleware rejects stale **`tv`** vs Postgres. **`LUMOGIS_REQUIRE_TV_CLAIM`** (default **true** since LUM-918; missing **`tv`** → 401; `false` restores the old lenient behaviour). Access tokens live **`ACCESS_TOKEN_TTL_SECONDS`** (default **900**), clamped to **60–3600**: a larger value is lowered to an hour with a boot WARNING (LUM-918). Optional per-session revocation — **`LUMOGIS_REQUIRE_SID_REVOCATION_CHECK`** (default **false**) checks **`sid`** vs **`auth_sessions.revoked_at`** on each authenticated request when **`AUTH_ENABLED=true`** (no effect in single-user dev mode). It stays off by default because every refresh moves the token to a new session row: with the check on, a refresh in one browser tab signs out the access tokens of the other tabs on the same cookie, and they refresh in turn. Without it, revoking one device's session stops its refresh at once and its access token at most one access lifetime later. **`LUMOGIS_SID_REVOCATION_CACHE_TTL_SECONDS`** (default **30**) bounds an in-process LRU for verdicts; **`0`** disables that cache so every verification hits Postgres (**operator diagnostics only**). Checks run **after** **`tv`** succeeds. **`GET/DELETE /api/v1/me/sessions`**, **`POST /api/v1/me/logout-all`**; admin session inventory under **`/api/v1/admin/users/{user_id}/sessions`**. Refresh cookie path **`/api/v1/auth`**. **`LUMOGIS_TOKEN_VERSION_CACHE_TTL_SECONDS`** bounds in-process **`tv`** cache (Lumogis runs **one orchestrator process** — `--workers 1`, which is the shipped and only supported mode, so this cache is always coherent. Running multiple worker processes would give each its own copy of this cache **and** its own rate-limit counters, session-revocation cache and job-queue state; that is not supported and the orchestrator **refuses to boot** if `WEB_CONCURRENCY` — or an explicit `--workers` — is above 1, because the failure mode is silent incorrectness rather than a crash (LUM-832). Decided 2026-08-10; LUM-30 closed as won't-do). **Token typing (LUM-885):** access and refresh JWTs carry a **`typ`** claim (`access` / `refresh`), every verifier requires the right one, and a refresh JWT is never accepted as a Bearer (a missing `typ` on a *refresh* JWT is tolerated for one refresh lifetime after the upgrade; an access token without `typ` gets 401 and the Web client refreshes once). **Account-state changes revoke everything the user holds:** delete, demote, password change (self, admin reset, email reset, CLI) and **`logout-all`** revoke MCP tokens, auth sessions and bump **`token_version`** in one transaction; promotion bumps `token_version` only; delete, disable and demote also cancel the invites that user sent, and an invite redeems only while its creator is an active admin. An MCP token is also checked against its owner on every request (a deleted or disabled owner is rejected). **The refresh secret must differ from `AUTH_SECRET`**: with `AUTH_ENABLED=true` boot is refused when `LUMOGIS_JWT_REFRESH_SECRET` / `JWT_REFRESH_SECRET` is missing, a placeholder or equal to `AUTH_SECRET` (the compose entrypoint fills `JWT_REFRESH_SECRET` automatically; `make doctor` reports it before an upgrade). The knowledge-graph service verifies the same access tokens and applies the access-only rule wherever it runs; its own `AUTH_ENABLED=true` needs PyJWT in the graph image, which the standard image does not install. — [ADR 243](decisions/243-lum-885-account-state-token-cascade.md).
- **Why not cloud multi-tenant:** Product target is **household LAN**; hosted multi-tenant is explicitly deferred ([ADR 012](decisions/012-family-lan-multi-user.md), remediation plan §1, portfolio).

**Household invites (LUM-186):** Migration **`044-user-invites.sql`** adds **`user_invites`** (hashed token, role, `allows_shared` metadata, expiry, single-use consume). Admin **Admin → Users → Invite member** generates a copy-link (`LUMOGIS_PUBLIC_ORIGIN` + `/invite?token=…` when origin is set; relative path in dev). Redemption is rate-limited and auth-bypass public (like login). v1 does **not** enforce per-user shared-scope visibility from `allows_shared` — onboarding copy only; shared/system rows remain visible per migration **013** until a follow-up capability lands.

**Forgot password (LUM-65):** Migration **`073-password-reset-tokens.sql`** adds **`password_reset_tokens`** (invite-shaped: `prst_` tag, SHA-256 at rest, 16-char lookup prefix, single-use atomic consume) and **`system_mail_outbox`**.

*Two passes, and the first ships alone.* **Pass 1** is honesty: the login screen now says how to recover — ask a household admin (**Admin → Users**), or, for an operator with shell access, `python -m scripts.reset_password`. That guidance is what `/forgot-password` shows whenever email reset is not available, which on a default deployment is always.

**Pass 2** is the email path, and an operator turns it on deliberately at **Admin → System mail**. Enablement is a conjunction of four things, and the admin page names whichever one is missing:

1. system SMTP configured (stored Fernet-encrypted as the `system_smtp` system-tier credential — **not** a household member's mailbox, which would be circular: the account most likely to need a reset email is the one whose credentials would be needed to send it);
2. a **Send test that actually delivered** — configuration alone is never taken as proof, and changing the host, port, username, password, or From address clears the stamp until it is re-proven;
3. **`LUMOGIS_PUBLIC_ORIGIN`** set — reset links are built from it and never from the request's `Host` header; and
4. **`LUMOGIS_ALTCHA_HMAC_KEY`** set — the self-hosted ALTCHA proof of work on the public request path.

*Why the mail is queued rather than sent.* The token row and its `system_mail_outbox` row commit in **one transaction**, and a background job (default every 15s, `LUMOGIS_SYSTEM_MAIL_DRAIN_SECONDS`) does the SMTP. So a reset email arrives seconds after the request, not instantly — that delay is the design, not a fault. It buys two things a synchronous send cannot: the request answers identically for a known and an unknown address (a timing pad cannot hide a branch that waits on a 30-second SMTP timeout, and the gap would be widest exactly when the relay is unhealthy), and a slow relay can never occupy the worker slots that `POST /auth/login` needs.

*Operator notes.* Only the System mail routes may write `system_smtp` — every generic connector-credential surface refuses it with `422 use_system_mail_admin`. Redeeming a link runs the same `_apply_new_password` as every other path, so all sessions die and `token_version` bumps; conversely, resetting a password by **any** route (admin, CLI, self-service) consumes any outstanding emailed link, so a link cannot outlive the password it was minted to replace.

*Those four conjuncts gate **sending**, not **redeeming**.* A link already in someone's inbox still works if you rotate the relay password afterwards — three of the four (Send test, public origin, ALTCHA key) are preconditions for minting and delivering a link, and none is needed to verify a hash and write a password. Turning email reset off does **not** revoke links already sent; to kill one, reset that account's password, which consumes outstanding links on every channel. Links expire on their own after `LUMOGIS_PASSWORD_RESET_TTL_MINUTES` (default 30, clamped to 5–120), and the outbox stops retrying a queued message once it outlives that window rather than delivering a link that is already dead.

*TLS on outbound mail is verified.* Both the system mailer and the household mailbox sender check the relay's certificate **and** hostname. A relay presenting a self-signed or otherwise untrusted certificate will fail to connect where earlier versions connected silently — add the CA to the trust store rather than looking for a switch to turn verification off; this channel carries relay and mailbox credentials.

*The proof-of-work is tunable.* `LUMOGIS_ALTCHA_COST` defaults to **200**, roughly 1.4s median on an idle desktop and a few seconds on a mid-range phone. It is a per-candidate KDF iteration count, so total work scales as `cost × ~256` — raising it by 10× raises the solve time by 10×, and the tail matters because the solve is a random search: about 2% of attempts take four times the average. The browser widget gives up at 90 seconds.

**Still deferred:** SMS reset, cloud CAPTCHA, a secondary backup recovery email, and SMTP invite delivery (invites remain copy-link only).

## 7. Credentials and permissions

**Lay view:** Connectors hold the keys Lumogis needs (ntfy, calendars, LLM APIs). You paste them once; the UI does not show them again. Admins can help manage household-level configuration; some secrets are **per user**, some **shared** or **system** tier.

**Technical view:**

- **Per-user / household / system** credential scopes—[ADR 027](decisions/027-credential_scopes_shared_system.md).
- **Storage:** `user_connector_credentials` with **encrypted** payloads; **MultiFernet** allows key rotation—`orchestrator/services/_credential_internals.py`.
- **Connector permissions** (Ask/Do/blocked) — per-user rows; `get_connector_mode` drives catalog **labels** and execution checks—[ADR 024](decisions/024-per-user-connector-permissions.md).
- **The autonomy page — what Lumogis may do on your behalf (LUM-849, [ADR 220](decisions/220-lum-849-autonomy-surface.md)):** `/me/permissions` is where a person decides whether Lumogis acts without asking, and it is labelled **"What Lumogis may do"** in Settings (the **route path is unchanged**, so existing links and bookmarks keep working). It asks **two questions in plain words** rather than listing connector ids: **"Send email as you"** (replies, forwards, new messages, unsubscribes — *other people receive these and they cannot be taken back*) and **"Tidy your mailbox"** (save drafts, flag, label, mark read, move — *only you see these, and they can be undone*). The irreversible question renders first. The split is by **connector** — every `smtp` action is irreversible and received by someone else, every `imap` action is reversible and private — and each row states **"Applies to all your mailboxes."**, because the setting is stored `UNIQUE (user_id, connector)` with **no instance column** and every other email control in the product is per-mailbox. A row still at the lazy default reads **"Ask me first (default)"**; there is no separate revert control, and `DELETE /api/v1/me/permissions/{connector}` remains available to API callers. **Email signals cross-links here once**, above the mailbox list rather than beside the per-mailbox send control, so the page does not imply a per-mailbox scope it does not have.
- **The list can say when it is incomplete (LUM-849):** **`GET /api/v1/me/permissions`** normally returns one row per known connector, lazily defaulting to Ask. When the action registry is unreachable it falls back to the caller's **explicit rows only** — so a connector you never configured has no row and would simply vanish. It now attaches **`Warning: 199`** on that branch and the page renders *"Some settings couldn't be loaded just now, so this list may be incomplete."* while keeping the settings that did load fully usable. A **known question whose row is missing renders its question and says the setting could not be loaded** — it is never shown as "Ask me first", because that is a statement the server makes and an absent row is the absence of one. A connector the page has **no words for is rendered with its id and an honest note**, never dropped: a setting that can act on your behalf must never be invisible on the page that lists what may act on your behalf. The response body is unchanged (still a JSON array).
- **Switching to DO from Approvals (LUM-962, [ADR 258](decisions/258-lum-962-approvals-do-mode-flip.md)):** **`POST /api/v1/approvals/connector/{connector}/mode`** accepts exactly the connectors the Ask/Do gate enforces — registered action connectors (`smtp`, `imap`) and known **`capability.{id}`** connectors — the same set `PUT /api/v1/me/permissions/{connector}` accepts ([ADR 220](decisions/220-lum-849-autonomy-surface.md)). One module, `services/permission_connectors.py`, defines that set; nothing else compares a connector against `list_actions()` to decide it. Read-only tool connectors (`filesystem-mcp`, `lumogis-memory`, `lumogis-graph`) answer **404** `unknown_connector`, because `check_permission` gates only writes and DO would change nothing for them. Approvals answers **403** `hard_limited_connector` when **any** of a connector's gated action types is hard-limited (an action connector's registered action types; a capability's write-tool names), because `check_permission` skips hard limits under DO; `PUT /me/permissions` applies no such refusal (LUM-914). When Core cannot read the relevant registry, Approvals **fails closed**: the switch and `POST /api/v1/approvals/elevate` answer 404, while `PUT /me/permissions` keeps its degrade-allow with `Warning: 199` for plain connectors. **`GET /api/v1/approvals/pending`** reaches the same verdict from the same registry snapshot: a row that cannot be switched, or would be refused, carries `suggested_action: explain_only`, and `elevation_eligible` is true only when the row's `(connector, action_type)` is a registered action (a capability tool can never be elevated). Lumogis Web renders **"Switch {connector} to DO mode"** only when `suggested_action` is not `explain_only`, and otherwise says *"This can't be switched from here."* Switching a capability to DO does not grant its required scopes (LUM-612).
- **`GET /api/v1/me/tools`** exposes **permission_mode** (`ask` / `do` / `blocked` / `unknown`) as **read model** only; granting/changing permissions is elsewhere.
- **Capability permission scopes (LUM-612, LUM-507 pillar a):** a capability's declared **`permissions_required`** (LUM-41 manifest) is **enforced least-privilege** — at the invocation chokepoint (`services/execution.py::execute_capability_http`) Core denies (fail-closed) any capability call whose required scopes are not in the user's **granted** set, naming the missing scopes so the caller can request a grant. A capability's permission identity is the connector **`capability.{manifest.id}`**; grants live in the ADR-024-reserved **`scopes TEXT[]`** column on `connector_permissions` (migration **052**), cached as one `(mode, scopes)` value so every existing invalidation path (revoke, `DELETE`, account-disable) drops scopes too. Grant/revoke via **`PUT /api/v1/me/permissions/{connector}`** (body `{"mode"?, "scopes"?}`; `scopes` present replaces the granted set, absent leaves it unchanged; scope strings are `area:verb`, 422 on malformed); the consent surface **`GET /api/v1/me/permissions/capabilities`** lists each registered capability's **required** vs **granted** vs **missing** scopes. Manifests whose `id` is not grant-shaped, or that declare a malformed required scope, are **refused at registration** (never silently locked out). The KG `query_graph` bridge is a trusted first-party tool and is **not** scope-gated.
- **Capability sandbox + egress (LUM-613, LUM-507 pillar b):** an out-of-process capability runs in its **own container** and makes its **own** outbound calls, so Core's in-process hooks **cannot** stop it from exfiltrating — the hard container-network guarantee is **LUM-618** (which gates the public community marketplace launch). This chunk ships the enforceable half: a **fail-closed community-dispatch gate** — a discovered capability is **community (untrusted)** unless its manifest `id` **and** discovery origin match the operator-maintained, origin-pinned allowlist `orchestrator/first_party_capabilities.txt`; a community capability is **refused dispatch** (structured `tool-unavailable`, host not contacted, and hidden from the LLM tool catalog) until an operator sets **`LUMOGIS_ALLOW_UNCONTAINED_COMMUNITY_CAPABILITIES=true`**. The trust boundary is **id-based** (deployment-independent; not the author-declared `license_mode`, not the compose service name) and **decoupled** from the LUM-43 credentials allowlist. Capabilities declare their egress hosts in the additive manifest field **`external_endpoints`** (bare hosts / IPv4, validated + bounded; read into the OOP tool audit and `/me/tools` visibility — **visibility, not consent**); the registry **refuses** a refresh whose origin conflicts with a registered `id` (shadow-takeover guard, loud `capability_identity_conflict` audit) and **evicts** an already-registered service that later returns an invalid manifest (never on a transient network blip). Untrusted plugins are **out-of-process only** — the in-process loader refuses any non-first-party module (ADR-170 §0). The two `tethered.scope()` defense-in-depth wraps are deferred to **LUM-619** pending a concurrency/nesting verification; LUM-613 adds no `tethered` import. This layer never claims to *prevent* OOP egress — it declares, gates dispatch, and audits.
- **Container-network egress containment (LUM-618 / LUM-621, LUM-507 pillar b-hard):** the **hard** guarantee LUM-613 deferred, and the gate for the public community marketplace. On Docker, a community capability runs on an **`internal: true`** network (`enable_ipv6: false`) — Docker gives it **no route to the internet** — and its only egress path is a dedicated, profile-gated **Squid** proxy that allowlists **only** the capability's declared `external_endpoints`: HTTPS by TLS **SNI** via `peek`+`splice` (**no decryption / no MITM / no CA injection** — end-to-end TLS is preserved), HTTP by `dstdomain`, deny-all default. Default compose image is **digest-pinned** (`EGRESS_PROXY_IMAGE=jacobalberty/squid@sha256:…`, linux/amd64). The dispatch gate dispatches a community capability iff its id is in a **containment marker** (`contained_capabilities.txt`), which **supersedes** the deprecated `LUMOGIS_ALLOW_UNCONTAINED_COMMUNITY_CAPABILITIES` flag (retained, back-compat, one-time deprecation warning). The marker is **mtime-reloaded** on the next OOP dispatch (no Core restart; keep-last-good if the file disappears). The image-default marker is **empty** (fail-closed); the egress overlay supplies it via `LUMOGIS_CONTAINED_CAPABILITIES_FILE`, so "contained" cannot be asserted without the network wiring that backs it. Install-time `scripts/gen_capability_egress_acl.py` turns a manifest's `external_endpoints` into the proxy allow file; **`make check-egress-acl-divergence`** (`--check`) fails closed when the committed allow file drifts from declared endpoints (CI beside compose-policy egress). When the egress overlay is active, Squid deny lines in the shared access log produce a structured Core **`egress.denied`** WARNING (hostname-only, deduped) — spike outcome **A** confirmed HTTPS `TCP_DENIED` is logged under the pinned `lumogis_egress` logformat. **Compose-policy Pass C** (`scripts/check_compose_policy.py --community-service`) verifies in CI that a community service is on the isolated network and on **no** internet-facing network. Hard enforcement is **Docker-only**; native deployments keep community capabilities refused (fail-closed on the LUM-613 gate). Known residuals (documented): SNI/Host divergence on shared-infrastructure hostnames, IPv4-literal `dst` ACL, ECH, and signing (**LUM-614**).

- **Test connection (LUM-834, [ADR 218](decisions/218-lum-834-connector-test-connection.md)):** each connector card at **`/me/connectors`** carries a **Test connection** button. **`POST /api/v1/me/connector-credentials/{connector}/test`** (`require_user` + same-origin, **10 tests / 60 s per user**) probes the **stored** credential server-side and answers **`{ok, code, detail}`**. **`ok` is tri-state**: `true` verified, `false` tried and failed, **`null` not attempted** — so a connector with no probe shows *"No connection test for this connector"* rather than a red ✗ on something that works. **A failed test is a `200`, never a `5xx`.** Codes: `verified`, `auth_failed`, `unreachable`, `not_configured`, `credential_unavailable`, `invalid_config`, `unsupported`, `tested_elsewhere`. **`detail` is a fixed string chosen by `code` and is never derived from an exception message** — several `ValueError`s off this surface embed the configured host, so logs carry the exception **type** only. **Which connectors:** **`paperless`** is probed (one bounded, read-only, authenticated `GET`, redirects refused); **`imap`** and **`smtp`** answer `tested_elsewhere` and their cards link to **Email signals**, where they are tested pre-save with folder detection; **`system_smtp`** refuses with `422 use_system_mail_admin` like every other generic credential verb; everything else is `unsupported`. **No decrypt path is added** — the probe decrypts inside `load_connection`, server-side, and no payload value or key name crosses the wire. Bounded by **`LUMOGIS_CONNECTOR_PROBE_TIMEOUT_S`** (default **5 s**, floor **0.5 s**) as a **budget across two phases** — the credential load's DNS resolve and the probe's own request — because bounding the resolve alone leaves a host that resolves and then never answers hanging. **`ACTION_CRED_TESTED`** audits *that* a test ran and its verdict, never its inputs; not-attempted outcomes are not audited at all. **No admin mirror:** the probe takes no tier, so an admin-tier button would have tested the caller's own credential while presenting as a tier test.
- **Turning a connector off, and seeing which fields are set (LUM-834 chunk B, [ADR 219](decisions/219-lum-834-connector-enabled-and-field-presence.md)):** each card at **`/me/connectors`** carries an **on/off toggle** and per-field **set / not set** rows. **Switching a connector off does not delete its credential** — **`PATCH /api/v1/me/connector-credentials/{connector}`** (`require_user` + same-origin, body `{"enabled": bool}`) sets a flag, so turning it back on resumes without re-entering the secret. Disabling **stops ingest and actions**: `get_payload` and the runtime resolver both refuse a disabled row, each loader refuses to fall back to its `*_ENV` variables, and the tier walk **stops** rather than quietly using a household credential the user did not ask for. `PATCH` returns **404** when nothing is saved yet, and **422** for `system_smtp` (like every sibling verb) and for `imap`/`smtp`, which are configured per mailbox and have no card here. **`enabled` is separate from `delivery_paused`** — that flag is system-set on delivery failure and cleared on recovery; effective state is `enabled AND NOT delivery_paused`. **Which fields are set is answered without decrypting anything:** `put_payload` stores the payload's **key names** (never values) alongside the ciphertext, and `GET /registry` publishes each connector's declared fields (`name`, `label`, `is_secret`). A row written before this feature reports its fields as **unknown** — *"Configured. Field details appear after the next save."* — rather than as "nothing set", because a working credential must never render as unconfigured. **Secret fields show a consequence, not a tick:** saving still requires the secret (the backend replaces the whole payload; see LUM-846), so the card says *"saved. Changing anything on this card means entering it again."* rather than `✓ set`. **The Test button is disabled while a connector is off**, and the probe answers `disabled` rather than claiming either "no credential saved" or "connected successfully". **`imap` and `smtp` render no card** — they are set up on **Email signals**, and a one-line signpost says so. **Ask/Do is not on the card:** per-connector permission modes gate *actions*, and only `imap`/`smtp` register any, so the setting lives on the autonomy page — **`/me/permissions`**, labelled *"What Lumogis may do"* (LUM-849, [ADR 220](decisions/220-lum-849-autonomy-surface.md)) — where it applies.
- **Editing a credential replaces it whole (LUM-846).** Every typed credential form now requires its secret on **every** save, including edits, and says so. This is not a preference: `put_payload` is a whole-payload replacement with no merge, so a form that omitted a blank field did not *keep* the stored value — it **deleted** it. Three forms shipped a "Leave blank to keep existing" hint against that backend (`caldav`, `imap`, and `ntfy`'s optional token), which meant opening a connector to fix a typo in its URL and pressing Save silently destroyed the stored secret; the next poll then failed with a credential error that read as *"the server rejected us"*. `ntfy`'s token is genuinely optional and is the one exception — its key is always sent, and blank now explicitly means *remove the token* rather than doing so silently. Honest "leave blank to keep" needs either a backend merge or field-presence metadata, both of which are chunk B.
- **The JSON fallback form no longer saves on blur (LUM-846).** Connectors without a typed form fall back to a raw-JSON textarea. It had no submit button — leaving the field saved — and it seeds from an *empty* object, because the server never sends a stored payload back. Together that meant opening a connector's card, clicking into the box to see the configuration, and clicking away **replaced the whole credential with `{}`**. Saving is now explicit, an empty object is refused when editing, and the box states that it cannot show what is currently saved.
- **Typed paperless form (LUM-834):** `paperless` no longer falls through to the raw-JSON textarea. Payload keys are **`base_url`** and **`token`**, and **both are required on every save** — `put_payload` is whole-payload replacement, so a form that omitted the secret on edit would destroy the stored credential.

**Examples:** **ntfy** — notification channel connector ([ADR 022](decisions/022-ntfy-runtime-per-user-shipped.md)). **LLM provider keys** — per-user ([ADR 026](decisions/026-llm-provider-keys-per-user.md)). **CalDAV** — [ADR 021](decisions/021-caldav-connector-credentials.md). **MCP tokens** — [ADR 017](decisions/017-mcp-token-user-map.md).

**Cloud LLM privacy mode ([ADR 147](decisions/147-lum-194-cloud-llm-privacy-mode.md), LUM-194):** Household **routing policy** (not network isolation) that blocks **remote** models when local-only is effective. Instance keys in `app_settings`: `privacy_mode` (`local_only` | `allow_cloud`, default `local_only` when absent on fresh install) and optional `privacy_mode_locked`. Per-user further restriction (`local_only` only — cannot expand beyond instance) lives in `privacy_user_settings` when `AUTH_ENABLED=true`. Enforcement is at `config.get_llm_provider` / `is_model_enabled` using a fail-closed allow-list (`is_local_model()`). Admin configures instance policy at **Admin → Privacy mode** (`/admin/privacy-mode`); members may further restrict at **Me → Privacy mode** (`/me/privacy-mode`) when the instance allows cloud and is not locked. Chat requests for a blocked remote model fall back to a local model with `lumogis.privacy` metadata (non-streaming JSON and first SSE chunk); hard blocks emit `privacy_mode_block` audit rows (JSON includes `decline_type: external_call_denied` for LUM-137). Migration **043** seeds `allow_cloud` on upgrade when the household already demonstrated cloud usage. Lumogis Web explains the block where cloud models first appear (LUM-881, [ADR 227](decisions/227-lum-881-privacy-question-where-blocked.md)): the chat and document-chat model pickers and the LLM key-save card show a one-line hint when `GET /api/v1/models` reports a model with `disabled_reason: "privacy_mode"`, with a link to **Admin → Privacy mode** for admins; a model with no key reads `no_credentials` whatever the privacy mode, so an install with no cloud key is never told about it.

**Egress guard ([ADR 153](decisions/153-lum-553-tethered-egress-allowlist.md), LUM-553):** Optional **defense-in-depth** behind ADR 147 — **not** a substitute for routing policy. When **`LUMOGIS_FF_EGRESS_GUARD=true`** (default **off**), Core wraps LLM adapter calls with an in-process socket allowlist (`tethered` PEP 578 `scope()`). Allowed hosts are derived from local backends (Postgres, Qdrant, FalkorDB, ntfy, Ollama), `LUMOGIS_OUTBOUND_PRIVATE_HOST_ALLOWLIST`, and cloud API hosts only when effective privacy policy permits cloud. Blocks surface as HTTP **503** `egress_blocked` on non-stream chat, or in-band SSE errors on streaming (HTTP 200). Operator copy must state this is **bypassable** and does **not** guarantee network isolation.

**Process-wide egress ceiling ([ADR 153](decisions/153-lum-553-tethered-egress-allowlist.md) revisit, LUM-571):** Where the LUM-553 guard wraps only the LLM adapter call and LUM-625 only the IMAP connect, the **ceiling** is a whole-process cap. When **`LUMOGIS_FF_EGRESS_GUARD_CEILING=true`** (default **off**, independent of `EGRESS_GUARD`), Core installs a `tethered.activate(locked=True)` policy **once at lifespan startup, after the store health checks**, so every outbound socket opened through Python's socket layer — from *any* subsystem, not just the LLM/IMAP doors — is checked against a union allowlist. `tethered.activate()` and every `scope()` compose by **intersection**, so the ceiling allowlist is a **superset** of every scope: `build_allowlist(for_ceiling=True)` folds the LLM/backend hosts plus the household IMAP mail **and** proxy hosts (the LUM-625 connect target under Layer 2) and the infra hosts (`CAPABILITY_SERVICE_URLS`, `STACK_CONTROL_URL`, `STT_SIDECAR_URL`, single-user `CALENDAR_CALDAV_URL`). The value: on a **local-only** instance, cloud hosts are excluded, blocking cloud egress process-wide (Python socket layer), not only inside the LLM wrapper. **Locked + baked at boot:** the policy cannot be lifted at runtime and the allowlist is frozen at startup, so any allowlist-affecting change (privacy toggle, new mailbox/model, connector host) needs a **Core restart** — and if the flag is on but `tethered` is unavailable, Core **refuses to boot** (fail-closed). The ceiling also **fails closed** if `tethered`'s own policy check raises (`fail_closed=True`, LUM-637): the connection is blocked rather than allowed; to recover, turn the flag off and restart. **Opt-in strict mode / honest posture:** bypassable in-process PEP-578 hook (C extensions / `ctypes` / raw syscalls / non-Python subprocesses under `external_subprocess_policy="warn"`), **not** an OS firewall, never "impossible egress"; deployments using web-search / arbitrary-feed connectors, web-push, multi-user CalDAV, or a cold-cache model download must add those hosts to `LUMOGIS_OUTBOUND_PRIVATE_HOST_ALLOWLIST` or leave the ceiling off. Note `tethered` writes the full allowlist into the process environment (`_TETHERED_CHILD_POLICY`, inherited by children), so the allowlist is not secret at the process boundary.

**Security note:** Do not log secrets; diagnostics and façades avoid env dumps and raw ciphertext. Copy-once tokens where the product uses that pattern. Passwords are never shown again after set.

## 8. Memory, search, entities, and context

**Lay view:** Lumogis keeps **structured records** in a database and a **semantic index** for “fuzzy” finding. When you chat, it pulls snippets that matter, trims them to a budget, and **only that bundle** may go to an external model if you use one.

**Technical view:**

- **Postgres** — authoritative metadata, sessions, entities tables, audit, signals, etc.
- **Qdrant** — vector (and optional sparse/hybrid) search; **user_id** / scope visibility filters on queries for multi-user isolation (`visible_qdrant_filter`). Live two-user semantic-search isolation (real `Filter(should=…)` ANN) is regression-tested under compose in `orchestrator/tests/integration/test_two_user_qdrant_isolation_live.py` (**LUM-307**, [ADR 156](decisions/156-lum-307-two-user-qdrant-isolation-test.md)); unit translation remains in `test_qdrant_store_filter_build.py` (**ADR 057**).
- **Memory scopes** — personal, shared, system—[ADR 015](decisions/015-personal-shared-system-memory-scopes.md). Session recall (`services/memory.py` `retrieve_context`, behind chat context injection and MCP `memory.search` / `context.build`) searches the Qdrant **`conversations`** collection, which holds personal session summaries, personal Web-capture notes, and the shared/system projections of sessions, notes and audio memos. Every writer builds its point payload through **`services.memory.conversation_payload`**: `session_id` (the item id) and `summary` (its recallable text), plus `user_id` and `scope` for the visibility filter and kind-specific extras (`note_id`, `audio_id`, `published_from`, `source`, `topics`, `entities`). A note or audio memo published to the household (`POST /api/v1/notes/{id}/publish`, `POST /api/v1/audio_memos/{id}/publish`) is therefore recalled with its text by every member who allows shared scope. Points shared before LUM-954 carry `note_id`/`text` or `audio_id`/`transcript`; `retrieve_context` still reads them, after the visibility filter has admitted the hit. A unit tripwire fails when a module writes to `conversations` without the helper — [ADR 255](decisions/255-lum-954-shared-note-recall-payload.md) (**LUM-954**); live proof in `orchestrator/tests/integration/test_memory_scope_isolation_live.py` (**LUM-36**).
- **Graph node scope (LUM-961)** — every Knowledge Graph node carries `scope`, and the graph writers set it. The store adapter never defaults it. Document, entity, evidence, code-structure and temporal nodes are always `personal`. Session, Note and AudioMemo nodes take their row's scope: `personal` for the owner's item, or `shared` / `system` plus `published_from` for a published projection. `graph/schema.py:node_scope` refuses an unknown scope, or a scope that disagrees with `published_from`, before anything is written, and reconcile counts that row as `projected_failed`. Graph reads (`/graph/stats`, ego, path, mentions, the temporal personal tier) filter on `scope` through `visible_cypher_fragment`. Each member therefore sees their own nodes, and the household's shared and system nodes as their shared-scope setting allows. Graph reconcile projects personal `file_index` rows only, so the personal Document node is never relabelled by its shared copy. The LUM-586 shared-edge sweep matches personal nodes by `scope = 'personal'` and logs `swept_edges=N` on each share. A CI test ratchet fails any new `create_node` call site until it stamps `scope` — [ADR 260](decisions/260-lum-961-kg-node-scope.md).
- **Household biography conflict policy (LUM-514, [ADR 147](decisions/147-lum-514-household-biography-conflict-resolution.md))** — when multiple household members publish **shared-scope** biography pins that disagree on the same fact group, Core **detects** a conflict (never silent last-writer-wins among divergent values). Default synthesis behaviour is **represent-both with attribution** (`user_id` labels). Household **admins** resolve via **`POST /api/v1/biography/conflicts/{id}/resolve`** (`confirm_one`, `keep_both`, `dismiss`); any member may **list** open conflicts (`GET /api/v1/biography/conflicts`). Audit rows live in Postgres table **`biography_conflict_resolutions`** (migration **043**). **`category=identity`** and single-author households are exempt (strict no-op). Production detection is invoked by the LUM-516 synthesis job (`detect_and_persist_open_conflicts`); **`biography_pins`** lands in LUM-515.
- **Entity extraction** — stored and linked per ingestion/session flows—see `services/entities.py`, entity ADRs ([014](decisions/014-entity-relations-evidence-dedup.md), etc.).
- **Entity summary write isolation (LUM-358, [ADR 154](decisions/154-lum-358-household-concurrent-write-isolation.md))** — Postgres `entities` rows carry monotonic **`version`**, live **`summary`**, and consolidation **`staged_summary`** (migration **044**). Future summary writers (LUM-108 write-back, LUM-109 consolidation) must use **`services.entity_write_guard`** for read-version / guarded-commit (`UPDATE … WHERE version=$read_version`); **`scope='system'`** summaries are read-only for household members in v1. Consolidation runs acquire a **non-blocking** per-`(scope_owner, entity_type)` **`pg_try_advisory_lock`** on a **dedicated checkout connection** via **`services.consolidation_lock`** (salt **8421358**; hold only for fast claim/stage — never across LLM inference). Multi-user field-tier merge rules live in **`services.entity_conflict_policy`** (LUM-514 vocabulary for shared-scope divergence). Extraction paths do not yet mutate `summary`.
- **Context building** — retrieval + `context_budget` truncation **on plaintext fragments** before LLM calls (`ARCHITECTURE.md`, `orchestrator/services/context_budget.py`). Graph **`Event.CONTEXT_BUILDING`** subscribers receive **`query`**, **`context_fragments`** (mutated in place), and **`user_id`**; entity pick uses **`select_context_entities`** (hybrid explicit + optional Qdrant semantic pass, ranked and capped) — **[ADR 051](decisions/051-context-building-hybrid-entity-selection.md)** (**LUM-210**). Operator env (Core + KG mirror): **`LUMOGIS_CONTEXT_ENTITY_BUDGET`**, **`LUMOGIS_CONTEXT_BUILDER_SEMANTIC`**, **`LUMOGIS_CONTEXT_BUILDER_SEMANTIC_TOPK`**, **`LUMOGIS_CONTEXT_BUILDER_SEMANTIC_THRESHOLD`**, **`LUMOGIS_CONTEXT_ENTITY_RANK_*`**, **`LUMOGIS_CONTEXT_ENTITY_EXPLICIT_BONUS`**. Allocator exposes a dedicated **`entities`** slice for `[Graph]` plaintext in addition to **`session_context`** / **`plugin_context`**. **Memory-as-hint ([ADR 066](decisions/066-lum-124-memory-as-hint.md), LUM-124):** when retrieval produced at least one plaintext fragment, Core appends a short operator English hedge on the assistant **ack** path (session, document, and graph excerpts are **hints**, not ground truth), gated by **`LUMOGIS_MEMORY_HINT_ENABLED`** (default **on**); the injection-sanitiser path **prepends** the hedge **before** the nonce-attested scaffolding. **`[Graph]`** entity lines (built in **`services/lumogis-graph/graph/query.py`**) may include a frozen metadata suffix **`(hint: type=…; confidence=…; last_seen=…)`** derived from Postgres **`entities.memory_type`**, **`mention_count`**, **`updated_at`** / **`last_verified_at`**, and per-**`entity_type`** half-life envs (**`LUMOGIS_ENTITY_HALFLIFE_*_DAYS`**, including **`FILE`**). Optional dev flag **`LUMOGIS_MEMORY_CORRECTION_PLACEHOLDER`** (default **off**) allows a Falkor **`memory_type='correction'`** projection from **`FEEDBACK_RECEIVED`** until **LUM-114** ships durable feedback ingest.
- **Document auto-RAG ([ADR 059](decisions/059-lum-308-document-auto-rag-chat.md), LUM-308)** — optional **`LUMOGIS_AUTO_RAG_ENABLED`** (**default `false`**) lets each **`POST /v1/chat/completions`** retrieve gated chunks from the Qdrant **`documents`** collection (same **`user_id` / scope visibility** as **`GET /search`**), score with the configured BGE reranker when present, and inject plaintext **after session summaries and before graph lines** into the same ADR 039 bundle as today. Injected Qdrant **`point_id`** values are tracked for the request so **`search_files`** can omit duplicates without a second round-trip. Tune **`LUMOGIS_AUTO_RAG_*`** via **`.env.example`**; **`docs/capabilities.md`** notes latency and path/token privacy when enabled.
- **Document chat mode (LUM-175)** — **`POST /api/v1/chat/completions`** with optional **`document_id`** (`file_index.id`) pins a turn to one library document: scoped retrieval bypasses global auto-RAG off, skips session/graph context, forces **`use_tools=false`**, and returns **`lumogis.context_citations`** (chunk indices). Web route **`/documents/:documentId/chat`** shows a **Context used** strip. Errors: **`document_not_found`** (404), **`document_context_unavailable`** (422), **`invalid_document_id`** (422), **`auto_rag_failed`** (503). Env: **`LUMOGIS_DOCUMENT_CHAT_TOP_K_PRE`** / **`LUMOGIS_DOCUMENT_CHAT_TOP_K_POST`** — [ADR 101-lum-175](decisions/101-lum-175-document-chat-mode.md).
- **Document injection hardening ([ADR 039](decisions/039-document-injection-sanitisation.md), LUM-127)** — by default (**`INJECTION_SANITISER_ENABLED=true`**, **`INJECTION_ACTION=wrap`**) Core runs a YAML regex/heuristic table at **ingest** and wraps retrieved corpus in **`<retrieved_chunk …>`** scaffolding before it is merged into chat context or **`search_files`** tool JSON; session + graph snippets are folded into a **`<lumogis_injected_context request_nonce='…'>`** envelope with nonce-bearing assistant scaffolding. **`Event.CONTEXT_BUILDING`** subscribers still observe **plaintext** fragments; tagging runs **after** the synchronous hook (+ service-mode KG extend). **`TOOL_CHAIN_CAP`** (default **`10`**) pessimistically caps parallel tool dispatches per chat completion (**`lumogis_blocked`** JSON stub when tripped). Pattern file **`INJECTION_PATTERN_FILE`** must resolve **under** the packaged **`orchestrator/data/`** subtree (same rule as bundled default **`injection_patterns.yaml`**). Operators who need to pause the feature temporarily can set **`INJECTION_SANITISER_ENABLED=false`** (patterns are not loaded; compaction trust prefix skipped in **`memory.py`**).
- **If a cloud LLM is used:** **Composed prompts and retrieved excerpts** (after context budgeting) are sent to the provider—they **may contain private text** from your index. Lumogis does **not** ship the **entire** local corpus or disk image as a bulk upload; what leaves is **what Core assembled for that request**. **Connectors** are separate: they contact **their** external APIs when invoked, by design.

## 9. Actions, tools, and audit

**Lay view:** Some operations are safe to run immediately (**Do**); others must wait for your **approval** (**Ask**). Everything important is logged.

**Technical view:**

- **Ask vs Do** — [ADR 006](decisions/006-ask-do-safety-model.md); executor enforces mode; destructive actions stay Ask.
- **Action registry** + **handlers**; **audit_log** append-only—[ADR 019](decisions/019-structured-audit-logging.md). **`GET /api/v1/audit`** lists rows for the authenticated user with optional `connector`, `action_type`, `event_type` (namespaced taxonomy or category prefix), `after`/`before` (422 when inverted), `limit`/`offset`, and admin-only `as_user`. Responses include `total` and enriched per-row `event_type`, `scope`, `source`, and `description` (derived server-side from existing summaries — [ADR 156](decisions/156-lum-197-audit-log-ui.md), LUM-197).
- **ToolCatalog** — `build_tool_catalog` / `build_tool_catalog_for_user` — read-only inventory with transports (`llm_loop`, `mcp_surface`, `catalog_only`).
- **ToolExecutor** — `execute_inprocess` / `execute_capability_http` with `PermissionCheck` and audit envelope; **OOP** capability calls fan in to `audit_log` (`tool.execute.capability` style rows)—see `tool-vocabulary.md`.
- **`LUMOGIS_TOOL_CATALOG_ENABLED`** — default **`true`** when unset (`config.get_tool_catalog_enabled()`); set **`false`** (or **`0`** / **`no`**) to opt out. When **false**, the LLM loop does **not** merge OOP capability tools into the live tool list. When **true**, `prepare_llm_tools_for_request` may append healthy, bearer-authenticated capability tools; **`finish_llm_tools_request`** must run after each request (`loop.py` try/finally)—see `services/unified_tools.py`.
- **Continue Site session state ([ADR 099](decisions/099-lum-128-continue-site-pattern.md), LUM-128):** `ask()` / `ask_stream()` share `_run_session_loop()` with frozen **`SessionState`** (`orchestrator/models/session_state.py`) rebuilt via `dataclasses.replace()` at model-call, tool-dispatch, turn-advance, and terminate sites. **`ToolChainBudget`** lives on `SessionState`; sync and stream paths preserve distinct tool-dispatch predicates (`stop_reason` vs non-empty stream tool calls). **`on_loop_event(event, state)`** is in-process only (LUM-139 may subscribe later). LUM-122 compaction will hook at PRE_REQUEST (`_inject_context` + comment seam in `routes/chat.py`).
- **Fail-closed:** Missing bearer, unhealthy capability, or denied permission should not silently execute OOP tools.
- **Action proposal claim ([ADR 040](decisions/040-action-proposals-atomic-claim.md), LUM-123; amended by LUM-762)** — Approved proposals live in Postgres table **`action_proposals`** (migration **`022`**). **This is an atomic claim over a synchronous execution, not a queue** — nothing drains it in the background, and nothing is meant to. **`claim_by_id`** promotes **`approved` → `executing`** atomically. **`POST /api/v1/approvals/proposals/{proposal_id}/execute`** claims then runs **`actions.executor.execute`**; concurrent losers get **409** (`proposal_claim_conflict`), and a row deferred to a future **`run_after`** gets **409** (`proposal_deferred`, with `retry_after`). **Failure is terminal on the first attempt** — every failure kind dead-letters; there is no retry ladder and no **`executing` → `approved`** edge, because a redrive of an unkeyed third-party SMTP submission would be a duplicate email rather than a retry. Stale **`executing`** rows are swept to **`dead`** (not re-approved). **`attempt`** is write-once (**0** = never attempted, **1** = attempted and failed; note the sweeper does **not** bump it); **`run_after`** is reserved for LUM-147's **`NOT_NOW`** deferral and is filtered by the claim so it can never be advisory. Env: **`ACTION_PROPOSALS_CLAIM_STUCK_AFTER_SECONDS`** (default **300**), **`ACTION_PROPOSALS_CLAIM_SWEEPER_SECONDS`** (default **60**), **`ACTION_PROPOSALS_SWEEPER_ENABLED`** (default **true**; the legacy spelling **`ACTION_PROPOSALS_QUEUE_ENABLED`** is honoured with a startup warning for one release — it gated a sweeper and never gated a queue). **`ACTION_PROPOSALS_MAX_ATTEMPTS`** is **removed** and ignored if set. With **`AUTH_ENABLED=false`**, admin **`as_user`** is broadly available (same footgun as **`GET /pending`**); proposal execute is side-effecting. Standard per-user **export** omits **`action_proposals`** (operational — see **`user_export._OMITTED_USER_TABLES`**).

**Flow (simplified):** User asks → Core builds context (retrieval + budget) → LLM may emit tool call → permission / Ask-Do check → `run_tool` / executor → handler or HTTP proxy → **audit_log** (+ structured logs).

## 10. Signals and routines

**Signals** — External or scheduled inputs (RSS, page change, calendar, **paperless-ngx document archive (LUM-281)**, system). Monitors poll; processor scores and persists; plugins can react via hooks.

#### Filesystem inbox auto-ingest (LUM-330, operator)

- **Purpose:** Drop supported files into **`ai-workspace/inbox/`** (bind-mounted as **`/workspace/inbox`** in the orchestrator container) and Core ingests them without **`POST /ingest`**. Failures that are not transient move to **`ai-workspace/quarantine/`** with a sibling **`.error.json`** sidecar (not counted in inbox depth alerts).
- **Owner:** Set **`INBOX_OWNER_USER_ID`** to the Lumogis **`user_id`** that owns dropped files (required for watcher or poll; no silent **`default`** fallback). When unset, neither the **`watchdog`** observer nor the poll job starts.
- **Mode (`LUMOGIS_INBOX_MODE`):** **`event`** (default) — in-process **`watchdog`** observer with write-stability before ingest; **`poll`** — APScheduler job **`inbox_poll`** scans the inbox on an interval (use on SMB/NFS or macOS Docker Desktop bind mounts where inotify is unreliable); **`off`** — no observer and no poll job. Invalid mode values log **ERROR** at startup and coerce to **`off`** (fail-closed).
- **Paths:** **`LUMOGIS_INBOX_PATH`** defaults to **`/workspace/inbox`**; relative values resolve under **`WORKSPACE_PATH`** (default **`/workspace`**). Quarantine is always **`{WORKSPACE}/quarantine/`** (sibling of inbox, outside the watched tree).
- **Tuning:** **`LUMOGIS_INBOX_STABILITY_DELAY_MS`** (default **1500**) — max wait for stable **(size, mtime)** before ingest; **`LUMOGIS_INBOX_POLL_INTERVAL_S`** (default **10**, floor **5** in config) — poll interval; **`LUMOGIS_INBOX_MAX_FILE_MB`** (default **200**) — skip oversized files before calling extractors. Poll mode calls **`inbox_poll_should_ingest`** (mtime vs **`file_index.updated_at`**) before **`ingest_file`** so unchanged files are not re-hashed every tick; event mode always ingests after stability.
- **Partial writes:** Basenames starting with **`.`** and suffixes **`.tmp`**, **`.part`**, **`.crdownload`** are ignored. **`on_moved`** handles intra-inbox atomic renames (e.g. editor **`file.tmp` → `file.pdf`**). After **three** consecutive stability timeouts in poll mode, the file is quarantined with reason **`stability_timeout`**.
- **Observability:** **`GET /healthz`** merges **`inbox_mode`**, **`inbox_watcher`** (`ok` | `degraded` | `disabled`), and (poll only) **`inbox_poll_last_scan`** — **no absolute paths** on the unauthenticated probe. **`GET /api/v1/admin/diagnostics`** (auth-gated) adds **`inbox_path`** and the same fields. **`system_monitor`** inbox depth uses the configured inbox path (top-level file count only; recursive watcher vs depth alert is a known limitation).
- **ADR:** [070-lum-330-folder-watch-inbox](decisions/070-lum-330-folder-watch-inbox.md).

#### paperless-ngx → Lumogis ingest (v0.1, operator / admin API)

- **Purpose:** OCR’d text from a self-hosted **paperless-ngx** instance is polled over its REST API (`/api/documents/`) with **token** auth, deduped in Postgres (`external_documents`), and embedded into the normal **`documents`** Qdrant collection. No new default Compose service — wire paperless yourself on the Docker network.
- **Credentials:** `PUT /api/v1/me/connector-credentials/paperless` with JSON payload `{"base_url":"http://paperless:8000","token":"<API token>"}` (registered connector id **`paperless`**). When **`AUTH_ENABLED=false`**, optional env fallbacks **`PAPERLESS_BASE_URL`** + **`PAPERLESS_TOKEN`** apply only to **`user_id="default"`** (single-user dev), mirroring CalDAV’s env trio pattern.
- **Source row:** Admin `POST /api/v1/sources` with **`"source_type": "paperless"`** and **`url`** set to the same API base (trailing slash trimmed). **`confirm:false`** returns `{"source_type":"paperless","url":<normalized>,"preview_items":[]}` without RSS detection. **`confirm:true`** inserts into **`sources`** with **`extraction_method":"paperless_http"`** and schedules polling (floor **60s**).
- **Incremental cursor:** First poll omits `added__gt` (full history, ordered by `added`) — large libraries need many ticks under per-tick caps. Later polls use **`added__gt`** watermark stored in **`sources.poll_cursor`** (ISO timestamps from paperless).
- **End of a poll walk (LUM-747):** paperless is Django REST Framework, and DRF answers **any page beyond the last with `404`**, not an empty page. The poller walks pages until one comes back empty, so it always requests one page past the end and sees that 404 on every productive tick. It is treated as a **terminal empty page** — returned immediately, logged `paperless_page_past_end` at **INFO**, never retried. (Before this it fell through the adapter's retry ladder: five attempts, ~31s of backoff, and a `paperless_http_final_failure` **ERROR** for a perfectly healthy poll.)
- **Diagnosing a wrong base URL:** a `404` on **page 1** is *not* a terminal page — DRF's `allow_empty_first_page` answers an empty archive with a `200` and `count: 0`. So a page-1 404 means the endpoint is wrong (bad `base_url`, paperless moved, a reverse proxy rewriting the path) and is logged as **`paperless_documents_endpoint_not_found`** at **WARNING** with the base URL. If a connector silently ingests nothing, look for that line first, then for `paperless_url_mismatch` (credential base vs `sources.url`).
- **Outbound URL / SSRF:** `base_url` is validated via **`validate_outbound_connector_base_url`** on credential read, credential save path (via payload validation), and the **`POST /sources`** paperless branch. **`169.254.0.0/16`** is always blocked. Private / loopback / RFC1918 / ULA ranges are allowed when **`LUMOGIS_ALLOW_PRIVATE_OUTBOUND_URLS`** is **`true`** (default for LAN Docker). Set it to **`false`** and use **`LUMOGIS_OUTBOUND_PRIVATE_HOST_ALLOWLIST`** (comma- or space-separated hostnames, e.g. `paperless`) to allow specific hostnames that resolve to private IPs. If DNS does not resolve at validation time, only scheme/host shape checks run — residual **DNS rebinding** risk is mitigated by pinning paperless on a trusted network.
- **Paperless version:** **≥ 2.16.2** recommended. (An earlier note here claimed ≥ 2.16.1 for an `added__gt` timezone fix; the changelog does not support that — v2.16.1 fixes **`created`** date filtering broken in 2.16.0, and v2.16.2 fixes `created` datetime coercion. No 2.16.x release names an `added__gt` timezone fix. The ≥ 2.16.2 floor stands for a different reason: upstream tells MariaDB users to skip 2.16.0–2.16.1 over a migration problem. Verified against the changelog during LUM-309.)
- **Webhook consumers:** handle optional **`ingestion_source_kind`** on **`DOCUMENT_INGESTED`**; branch on **`"external"`** when **`file_path`** uses the **`paperless://`** URI scheme.

#### Email (IMAP) connector with local mail classification (LUM-170, ADR-174; taxonomy LUM-629, ADR-175)

- **Purpose:** A **read-only** email signal source that polls IMAP mailboxes and **classifies incoming mail on-box** — every message gets an **importance score** plus a **category**. The six defaults (`school`, `insurance_renewal`, `bills_finance`, `family_personal`, `promotional_bulk`, `other`) are now a **user-editable taxonomy** (LUM-629): each user can rename or disable the defaults and add their own "custom labels". Plugs into the existing signals pipeline (`feed_monitor` `source_type="imap"`).
- **User-editable taxonomy + rules (LUM-629):** categories and classification rules are per-user, edited from the **Email labels** page (`/me/email-labels`). API: **`GET/PUT /api/v1/me/email-taxonomy`** (rename/disable defaults, add/delete custom categories; `other` is a protected, undeletable floor) and **`GET/PUT /api/v1/me/email-classification-rules`** (sender/domain/subject-keyword/**body-keyword**/bulk-header conditions → a category; user rules are evaluated **before** the built-in heuristics). Stored as a sparse overlay over the defaults (absence of a row = default; migration `055`); the classifier reads the effective taxonomy at runtime and falls back to the defaults if the store is unreachable (never a cloud call). `signals.category` stores the category **slug**, resolved to a label via the taxonomy. **`POST /api/v1/me/email-taxonomy/{slug}/reclassify`** re-applies rules to existing mail in a label — **subject-only and LLM-free** (headers/sender/body are transient), moving a signal only on a positive match (never draining unmatched mail into `other`).
- **Body-keyword rules (LUM-630):** a rule's `match.body_contains` matches the **extracted plain-text body**. Body is available only for **fully-ingested** mail, so body rules are **best-effort**: they don't fire on metadata-only mail, on HTML-only bodies, at reclassify (body not persisted), or on the overflow of a large sync burst (`_MAX_EMAIL_BODIES_PER_TICK`). Subject/sender rules are unaffected.
- **Taxonomy-aware LLM prompt (LUM-631):** the on-box email classification prompt enumerates the user's enabled category slugs, so the **local** model can **propose a custom/renamed label** when no rule matches (previously the residual was always `other`). Rules still take precedence and `coerce_category` still floors anything outside the taxonomy to `other`. Cloud LLM is never used on email content — the prompt runs only through the `require_local_model` guard. The proposed category is advisory and must not be treated as a trust/authenticity signal.
- **Hard privacy boundary:** email headers/bodies are **never** sent to a cloud LLM. Classification runs through the local `process_signal` LLM path guarded by an **on-box-local model** check (stricter than `config.is_local_model` — a remote Ollama endpoint is rejected). The model comes from the three email tasks (`email_classify`, `email_reply_draft`, `email_compose_refine`) in the **`tasks:`** block of `config/models.yaml`, on-box only (see *Background model tasks* below); a non-local model causes the LLM pass to be skipped (rules-only) with `code=email_body_cloud_blocked`. **`EMAIL_LLM_ALLOWLIST`** optionally trusts specific local LLM hosts.
- **Prompt-injection posture (LUM-699):** every LLM call site that reads email content delimits that content from its instructions and states explicitly that the delimited block is untrusted message data, not commands — `signal_processor.py`'s classification prompt (`<email>` tags), the same file's RSS/paperless signal prompt (`<content>` tags), and `email_reply_draft.py`'s reply-suggestion prompt (`<email>` tags, subject + body together), matching and slightly exceeding the pattern the composer's refine feature (`text_refine.py`) already shipped. This is a **prompt-level mitigation, not a proof** — a sufficiently capable/adversarially-tuned model could still be misled by content inside the delimiter. The classification path's real backstop is `email_classifier.finalize()`'s clamps (bulk-mail importance cap, known-contact floor, taxonomy-allowlist category coercion), which apply regardless of what the LLM returns. None of the three prompts neutralize a body/content containing the literal delimiter tag text itself (a tag-escape attempt) — same limitation `text_refine.py` already has; a real (non-null) `InjectionScanner` adapter for [LUM-362](https://linear.app/lumogis/issue/LUM-362) would be the natural place to close that, not a prompt-level fix.
- **Multi-mailbox:** each user may configure **several** mailboxes (personal / work / shared). Register one with **`POST /api/v1/me/email-sources`** `{"host","mailbox_label","port"?,"full_ingest"?}` (per-user; non-PII `mailbox_label` keeps `sources.url = imap://{host}:{port}/{label}` unique). Then store that mailbox's credentials with **`PUT /api/v1/me/connector-credentials/imap?instance={source_id}`** `{"host","port","username","password","use_ssl","auth_type":"app_password"}`. The credential store is multi-instance (`instance = sources.id`). **`sources.url` is canonical** for host and port: when `instance` is non-empty, a credential PUT whose `host` or `port` does not exactly match the owning source row is refused with **`422 imap_host_mismatch`** (LUM-773, [ADR-200](decisions/200-lum-773-mailbox-host-invariant.md)) — no silent overwrite. Legacy `instance=""` env-fallback IMAP rows skip this check (no source row to anchor). Because `sources.url` is canonical **and** has no edit path, registration itself refuses an empty or whitespace-only `host` with **`422 bad_host`** (LUM-781): such a row builds `imap://:993/{label}` and then fails *every* credential PUT with `422 imap_source_url_invalid`, leaving a mailbox that can never complete the two-step contract. The host is stored **trimmed**, so a stray surrounding space cannot yield a url whose host differs from the one the credential layer parses back out of it.
- **Auth:** **app-password** (Gmail, Fastmail, iCloud, self-hosted Dovecot) **or OAuth sign-in** for Outlook.com. TLS is required for any non-loopback host; plaintext is permitted only to a loopback host. **OAuth (XOAUTH2)** is a supported mode — tokens ride the same Fernet-encrypted credential store as app passwords (`auth_type:"xoauth2"`); see **OAuth email connect (LUM-686/687, [ADR 190](decisions/190-oauth2-provider-connect.md))** below.
- **OAuth email connect — Outlook.com (LUM-686 / 674a + LUM-687 / 674b, [ADR 190](decisions/190-oauth2-provider-connect.md)):** Microsoft retired app passwords for personal Outlook.com / Hotmail / Live IMAP, so those mailboxes connect via the **OAuth 2.0 Device Authorization Grant (RFC 8628)** instead of a stored password. **Bring-your-own OAuth app:** the operator registers a free Microsoft app (personal-accounts / `/consumers/` tenant) and sets **`LUMOGIS_OAUTH_MICROSOFT_CLIENT_ID`** (a public client id — no secret); see **`docs/operators/oauth-email-setup.md`**. The connect flow: the household member picks **Outlook.com**, types their address + a label, and Lumogis shows a short **user code** + a Microsoft sign-in link; the browser polls **`POST /api/v1/me/email-sources/oauth/outlook/device/{start,poll}`** (owner-scoped, CSRF-guarded, rate-limited) while Core (the RFC 8628 client) polls Microsoft. The provider `device_code` and the minted `refresh_token` **never reach the browser** — the browser sees only the opaque owner-scoped `flow_id`, the `user_code`, and the verification URL. On authorization Core **live-verifies IMAP** with the fresh token, then persists **credential-first** (the xoauth2 IMAP credential + a reusing SMTP credential, then the `sources` row); on an egress-proxied deployment where the live check can't run it **soft-saves** (`verified:false` — verification defers to the first sync). **`GET /api/v1/me/email-providers`** advertises Outlook as an OAuth provider and computes its **`enabled` dynamically**: a configured install shows it enabled; an unconfigured one keeps an honest disabled-with-reason card (no dead-end). **Gmail is not an OAuth provider in v1** — Google's device flow can't grant the `mail.google.com` IMAP scope (documented incompatibility), so Gmail stays app-password; Gmail OAuth is a deferred auth-code + loopback follow-up. Live-proof against a real Outlook mailbox is CI-gated (**LUM-688**).
- **Fetch:** APScheduler poll (per-source `poll_interval`) plus a user-triggered **`POST /api/v1/sources/{id}/sync`** ("Sync now", 202 enqueue-only). Cursor is UIDVALIDITY-aware (`{uidvalidity}:{last_uid}`); the dedup URL `imap://{source_id}/{uidvalidity}/{uid}` is PII-free.
- **Guided setup (LUM-644, [ADR 182](decisions/182-email-setup-v2.md)):** the web mailbox-setup flow is a guided on-ramp rather than a bare host/password form. A **static provider registry** — **`GET /api/v1/me/email-providers`** (Gmail / iCloud / Fastmail with app-password steps + deep links; **Outlook.com** as an **OAuth sign-in** provider — enabled when the operator's `LUMOGIS_OAUTH_MICROSOFT_CLIENT_ID` is set, else an honest disabled-with-reason card (see the OAuth email connect entry above); "Other" = manual host) — prefills server settings with **zero external lookup** (no ISPDB/SRV; nothing leaves the box at setup). A **live connection test before save** — **`POST /me/email-sources/test`** — takes credentials **transiently** (never persisted, never logged), runs the same SSRF/TLS/egress guards as a saved mailbox plus a read-only `probe()` (RFC 6154 folder detection + INBOX count), and returns the message count + detected folders; it is **CSRF-guarded and per-user rate-limited**, and **gates Save** (editing credentials re-gates it). On a Layer-2-proxied deployment the pre-save test is a soft **verify-on-first-poll** (`proxy_unverified`). **Import scopes** (columns on `sources`, migration `059`): **Just new / Last 7 days / Last 30 days (default) / Custom `[start, end]`**. Live tracking always starts at *now* (`poll_cursor` seeded to `UIDNEXT−1`); history comes via a **separate, additive, re-runnable backfill** (its own cursor, 200/tick, bounded by the seed-time max UID, **terminating on an empty search**) that never disturbs live polling — **duplicates in an overlapping/re-run window are skipped** (URL-based dedup) and the UI says so. **Opt-in folder-derived labels (5A):** the probe's folders pre-fill the editable taxonomy (via the existing **`PUT /email-taxonomy`**) — these are **Lumogis labels** (Lumogis's own view; editing never touches the mailbox), not a mailbox mirror. *v1 backfill reads INBOX only; multi-folder / folder-as-ground-truth is deferred to the cleanup chunk.*
- **Modes:** metadata-only by default (headers → classified signal); **`EMAIL_FULL_INGEST_ENABLED=true`** additionally ingests the message body into the `documents` store (`external_kind="email"`, dedup by `external_document_id`). Switch a mailbox's mode in place with **`PATCH /api/v1/sources/{id}`** `{"full_ingest": true|false}` (LUM-628) — owner-only; updates `extraction_method` and reschedules the poll job (no delete+re-register). Full-ingest still requires the operator flag, so the response and **`GET /api/v1/sources`** carry `extraction_method` + `full_ingest_active` (mode == full-ingest **and** flag on); toggling to full-ingest while the flag is off stores the intent but returns `full_ingest_active: false` (not a silent no-op). Forward-only — the mode applies from the next scheduled poll. In the web app the toggle is exposed per mailbox in the Email signals view (LUM-639), rendering the current mode and a "pending operator enable" hint when full-ingest is selected but the flag is off.

- **Editing a source (LUM-837):** **`PATCH /api/v1/sources/{id}`** is the general source-edit route, not only the IMAP mode toggle. `name`, `category` and `poll_interval` (floor `60`) apply to **every** `source_type`; `full_ingest` remains IMAP-only and returns `422 mode_toggle_not_supported` elsewhere. Owner-only (`404` for a foreign or unknown id — no existence oracle). A body supplying **no** field is a `422`, not a no-op: `status: "unchanged"` means *the values you supplied already match*. `full_ingest_active` is **`null`** when the request did not mention mode (`false` means "requested and inert because the operator flag is off"). Changing `poll_interval` reschedules the poll job — the scheduled job holds a `SourceConfig` snapshot — but never resurrects a paused source. **`url` is deliberately not editable:** the poll cursor, the detected `source_type` and the extraction method all derive from the original, and for paperless the poller reads the *credential's* `base_url` rather than `sources.url`. Delete and re-add instead.

- **Source health (LUM-837):** `GET /api/v1/sources` carries `last_poll_error_code` / `last_poll_error_at` for **every** source type. Until LUM-837 only the IMAP pollers recorded them, so a paperless source with no credential — or an RSS feed whose host had gone away — advanced `last_polled_at` on each tick and recorded nothing, reading as freshly polled forever. `last_polled_at` is **not** health on its own: every poll path advances it, including the ones that failed. Codes: `credential` (paperless credential missing or unloadable), `auth` (paperless token rejected), `poll_failed` (RSS/page adapter raised); a successful poll clears them.

- **Outbound policy for RSS and web-page sources (LUM-838, ADR-216):** this class had **no** outbound URL validation at all — at detection or at poll — while connectors and IMAP each had one. Both adapters now route every outbound call through `services/outbound_signal_fetch.py`, which reuses `validate_outbound_connector_base_url`: non-`http(s)` schemes, credentials embedded in the authority, and link-local / metadata addresses (when `LUMOGIS_ALLOW_PRIVATE_OUTBOUND_URLS=false`) are refused. **Redirects are followed manually and every hop is validated** — validating only the entry URL while following redirects blindly would leave `https://ok.example/r` → `http://169.254.169.254/` open. Ordinary redirects (`http`→`https`, moved domains) still work. **Private and LAN addresses remain allowed by default**, unchanged: watching an internal feed is ordinary in a self-hosted product, and the flag is there for operators who want otherwise — it simply did not apply to this class before. A refused URL returns `422 source_url_not_allowed` from `POST /api/v1/sources` with the reason, rather than failing downstream as "no feed found".

- **Source detection reports reachability (LUM-841):** `POST /api/v1/sources` with `confirm=false` returns **`reachable`** alongside `source_type` / `url` / `preview_items` — **on the detect path only**. The `source_type: "paperless"` preview branch omits the key, because it never contacts the host and so has nothing to report; a client must treat a missing `reachable` as "not known", never as `false`. **`false` means the fetch itself failed** — DNS, connection refused, timeout, or a non-2xx status. It is *not* "no feed found": a page that answered with nothing extractable is `reachable: true` with zero items, and is a perfectly good page source. Before this the two were indistinguishable — both produced `{"source_type": "page", "preview_items": []}` — so a mistyped hostname was reported as "we'll watch this page" and then polled nothing forever. A feed that parsed is reachable by construction. **Advisory, not a refusal:** `confirm=true` still creates the source, because a host can be briefly down and the poller now records `poll_failed` health so a genuinely dead source shows in the sources list.

- **Managing sources from the web (LUM-837, LUM-839, [ADR 217](decisions/217-lum-839-per-user-source-creation.md)):** **`/me/sources`** lists paperless, RSS and page sources with "Sync now", **Pause/Resume** and delete-with-confirm. Mailboxes are excluded — they are managed in the Email signals view, and deleting an IMAP source additionally tears down cleanup jobs and removes its IMAP/SMTP credentials. **Everyone connects their own sources.** All four verbs (`POST`, `GET`, `PATCH`, `DELETE`) are per-user and owner-scoped; create was the last one still admin-only and no longer is, so a household member adds their own feeds and their own paperless without an admin doing it for them. A source you create is yours: its signals are personal to you and are not visible to the rest of the household. `POST` and `PATCH` carry `require_same_origin` alongside `DELETE`. Two guards come with that: creating is capped at **100 sources per person** (`LUMOGIS_MAX_SOURCES_PER_USER`; counts only the types this screen manages, so your mailboxes do not count against it), and checking an address is rate-limited to **10 attempts a minute** — a preview is never blocked by the cap, only by the rate limit. Both refusals say which one you hit. **Pause and resume (LUM-844):** pausing stops polling (the poll job is removed, and stays removed across restarts) and keeps the row, its poll cursor and its last error. A check already running when you pause finishes first. Resume checks the source straight away: paperless continues from its stored cursor; an RSS feed stores the items still in the feed that Lumogis has not seen (items that dropped out of the feed while paused are not recovered); a page is compared with the last version Lumogis saw. A paused source still counts against the 100-source cap, and a paused paperless source still makes Lumogis ask before moving mail out of the inbox, and still raises the paperless warning on mail sorting and bulk clean-up, because paperless keeps reading the mailbox on its own. Remove the source if you no longer use paperless. **First run offers this (LUM-282, [ADR 221](decisions/221-lum-282-paperless-onboarding-offer.md)):** with no document archive, feed or watched page yet, `/me/sources` opens with an offer that names Paperless-ngx as the usual starting point and spells out its two steps — save the address and API token first, then add the source. The wording names the missing categories rather than the state of your account, because mailboxes are filtered out of this list and someone with three of them reaches the same screen. The offer disappears once you have one source of these types; there is no flag to remember a skip, and skipping leaves nothing half-configured. The **Connect sources** step of the first-run tour hands off here — it finishes the tour as it goes, and says so on the button. That step is only shown when authentication is on, so on a single-user install the chat page links here when the library has no documents yet (LUM-853), and this offer is the whole of it.
- **Email surface (web, LUM-642; LUM-655 — core opt-in integration, not a plugin; foundation **[ADR 174](decisions/174-email-imap-signal-source.md)**):** a discoverable top-level **Email** destination (`/email`) — promoted out of the Settings **Email signals** panel. It renders classified email signals richly (sender, one-line summary, category chip, time, importance) in **three lanes** — *Needs you* / *Good to know* / *Done* — with a category filter, a client-side text filter, and a "Search all email →" link to Unified Search. Email is a **core opt-in integration**, so the nav item appears **only once a mailbox is configured** (per-user, fail-closed while loading). Scoping to email uses a single household-union query — **`GET /api/v1/signals?source_type=imap`** (filters on the `imap://` url scheme) — so a member's **shared** email signals still appear, not only their own mailboxes. The sender is now **persisted** on the signal (`from_addr` + `from_display`, migration `056`; parsed from the `From` header at ingest, `''` for non-email/historical rows) and carried onto shared/projected rows. Signals ingested **before** migration 056 render "Unknown sender" until backfilled — the operator command **`python -m services.email_sender_backfill [--limit N] [--user-id U]`** (LUM-657) re-fetches the `From` header over read-only IMAP for such rows and fills it in (bounded, resumable, and safe: a changed `UIDVALIDITY`, a deleted message, or an unreachable mailbox is skipped, never failed). The Email nav item is seeded from a last-known-activation cache so it renders on first paint of a cold load rather than popping in (LUM-658). **Every card says which mailbox it arrived in, once you have more than one (LUM-821).** The lanes have always been cross-mailbox — that is the decided shape, *unified read, per-mailbox act* — but until now nothing on a card distinguished personal mail from work mail sitting next to it, which is how you end up replying from the wrong address. The name shown is the one you gave the mailbox on its settings row, so there is one name per mailbox rather than a second vocabulary. It is **absent with a single mailbox**, where it would be a word repeated on every card that tells you nothing, and absent on a household member's **shared** mail, where you cannot reply anyway (LUM-719) and naming their mailbox would disclose their setup to answer a question the card does not pose. Same rule the Attachments review list already follows. **You can start a message, not only answer one (LUM-830).** A **New message** button on `/email` opens an empty composer — until now the composer could only be reached by replying or forwarding, so writing to someone required finding an old email from them. Because a new message has no original to inherit from, it is the first place Lumogis has to ask **which mailbox it comes from**: the composer shows a **From** row every time, as a picker when more than one of your mailboxes can send and as a plain statement when only one can, and the confirmation step names that mailbox rather than saying "your address". Only mailboxes with sending switched on are offered — one that cannot send would fail at the last step — and if none of yours can, the page says so and links to the setting rather than leaving you with no button and no explanation. Changing the mailbox mid-message **swaps** its signature rather than adding a second one, and leaves the signature alone once you have edited it.
- **Durable triage state (LUM-643):** each signal carries a **Lumogis-owned, per-user** triage status — *needs you* / *good to know* / *snoozed(until T)* / *done* — decoupled from the mailbox's read-state (*the mailbox forgets; Lumogis remembers*). Reading never changes state; the user defers/completes explicitly (**Done**, **Snooze▾** with presets — Later today / This evening / Tomorrow / This weekend / Next week — **Not important**, **Reopen**/**Un-snooze**). Triage is **per-user**: each household member triages a shared signal independently. **Snooze** hides an item until `T`, then it **re-surfaces to Needs you** at query time (no scheduler); snoozed-not-due items live in a collapsible **Snoozed (N)** disclosure. An untriaged signal falls back to the provisional derivation (*Needs you* = `notified` **or** importance ≥ 0.6). State is stored in **`signal_triage(user_id, signal_id, status, snoozed_until)`** (migration `057`, FK `ON DELETE CASCADE`); mutated via **`PATCH /signals/{signal_id}/triage`** (set) and **`DELETE /signals/{signal_id}/triage`** (clear) — owner/visibility-guarded (a signal outside the caller's household union → 404, no existence leak), not the Actions/proposal framework (low-stakes personal state). **`GET /signals`** returns per-caller `triage_status`/`snoozed_until` via a LATERAL join, and a **`?triaged=set`** filter returns the caller's full triaged set independent of the recency window (so Done/Snoozed items are never window-lost); the `/email` view merges the windowed and triaged fetches.
- **Reading a message (LUM-810; **[ADR 207](decisions/207-lum-810-email-body-read-view.md)**):** a **Message** disclosure on each email card shows the body as **extracted text**. Lumogis **does not render sender HTML** — no sender-controlled bytes ever enter a rendered HTML context, so remote tracking pixels and sanitiser-bypass XSS are avoided rather than defended against. The cost is real and the UI states it rather than leaving it to be discovered: newsletters read as flattened text, and a footer says so on every body. **`POST /api/v1/email/body`** sits beside `/quote` with the same `require_user` + ownership posture (**404, never 403** — a 403 would confirm the signal exists) and **its own** rate bucket, because a bounded IMAP fetch must not consume the LLM budgets. Extraction prefers `text/plain` and falls back to a **stdlib `html.parser` block-aware walker** — newline at block boundaries, **tab** between table cells so a receipt's columns stay apart, `script`/`style`/`head` dropped, and **no new dependency**. That same extractor now backs ingestion: HTML-only mail previously reached the classifier and the summariser as an **empty string** (or, single-part, as raw markup), so their summaries were built on nothing — one extractor now serves the read view and ingestion alike, and newly-ingested HTML-only mail carries real text. Existing signals are **not** rewritten; a re-summarisation backfill is its own opt-in job. **Bidi control characters are marked, never stripped** (`␎U+202E␏`), because a Trojan-Source override reorders what you read without changing the bytes — while **zero-width characters are deliberately left alone**, since ZWJ is structural in emoji and ZWNJ is orthographically required in Persian, and marking them would render a family emoji or a Farsi sentence as sentinel soup. Every expected failure is a **200 with a reason** rather than an error code — mailbox unreachable (retryable, and the only one offering *Try again*), message gone, message too large, or a `Message-ID` several messages claim — so a read view never 5xxs on mail a stranger authored. The fetch is bounded at **1 MiB** before parsing, checked again after download for servers that withhold `RFC822.SIZE`, and the message is located by `Message-ID` across folders (so organized mail is still readable) under a whole-sweep deadline. Mail in a **mailbox you do not own** shows an explanatory line instead of the disclosure — the affordance is decided client-side from ownership, never by probing the route and reading a 404.
- **Searching your mail (LUM-819; [ADR 211](decisions/211-lum-819-email-search.md)):** a search box above the triage lanes finds any ingested message by **sender, subject or message text**, locally, with no provider round trip. Message text is searchable because Lumogis now **stores the extracted plain text** of full-ingest mail (`email_body_text`, migration `074`) — the same text `extract_text` already produced at ingest and previously discarded. Retention is unbounded, so a message triaged months ago is still findable. Two engines, deliberately, because there are two corpora: subject and sender are **substring**-matched over `pg_trgm` indexes, message text is **word**-matched over a `tsvector` and ranked with `ts_rank_cd`. They behave differently and you cannot see which one answered, so **every result carries per-field match counts** (`All 24 · Subject 8 · Sender 3 · Message 19`), and clicking one narrows the search. That is the point rather than decoration: search fails *silently* — an empty list looks identical to a message Lumogis does not hold — and `Message 0` beside `Subject 3` explains the behaviour without a help page. Counts are bounded at 200 (rendered `200+`), because an exact count cannot run under the result limit. The text index uses the **`'english'`** configuration with the **`:*` prefix operator** on every query token, which is what makes an English configuration safe for a multilingual household: measured, `Rechnung` matches "Rechnungen" and `plumb` matches "plumbing", both of which plain `'english'` or plain `'simple'` miss. The configuration is baked into a stored generated column, so changing it means re-indexing. **Message-text matches are owner-only.** Subject and sender use the household union the lanes already show; the body half filters to the caller, because LUM-810 decided shared signals get no read affordance and a body match would leak through search exactly what the read view refuses — so a household member's shared mail shows `Message 0` permanently. **`GET /api/v1/email/search`** takes `q` (≥3 characters *and* at least three letters or digits — a punctuation-only query is a **400**, not a silent empty list), optional `fields` and `source_id`, and `limit`; it has its own rate bucket, and answers **404, never 403**, for a mailbox you do not own. Two limits are stated rather than discovered: a **metadata-mode** mailbox stores no body and so is not text-searchable (said on the mailbox's own settings row, not only when a search comes back empty), and mail from a **suppressed sender** (LUM-824) or predating the **import window** (LUM-825) was never ingested and cannot be found. Existing mail is made searchable by an **operator-invoked** backfill — `python -m services.email_body_backfill [--limit N] [--user-id U] [--source-id S]` — which never runs automatically, paces itself between fetches (`EMAIL_BODY_BACKFILL_PACE_SECONDS`), skips metadata-mode mailboxes entirely, and records permanently-unfetchable messages so a re-run terminates instead of rescanning its own failures. Stored text is capped at `EMAIL_BODY_TEXT_MAX_BYTES` (64 KB) and a truncated message says so on the hit, so a miss inside a very long message is attributable. **Numbers are searchable as a person writes them (LUM-827):** typing `2400` finds a message saying `€2,400.00`, and `1234567` finds `1,234,567`. The word index still cannot do this — it tokenises the amount as `2` and `400.00` — so migration `078` adds a second, digits-only generated column beside it, and the two are OR-ed. It normalises **per number**, never across the message: a separator *between* digits joins them, anything else breaks the token, so digits from a phone number and an invoice can never run together into a match that appears in neither. Three limits worth stating: matching is by **prefix**, so `2400` finds `2,400.00` but not `124005`; a query containing **letters** is not a numeric search, so `INV-2400` is answered by the ordinary text index rather than matching every message that mentions 2400; and a number **grouped with ordinary spaces** (`12 34 56 78 90`) is indexed as separate tokens, because treating a space as part of a number would glue every adjacent pair of numbers in a message together. No backfill is needed — the column is generated, so mail you already have becomes searchable by number as soon as the migration runs. **A thread is indexed once, not once per reply (LUM-826):** `extract_text` returns the quoted history along with the new content, and migration `074` stored that verbatim, so a phrase written once in the first message was indexed again in every reply quoting it. Migration `075` adds `text_stripped` beside the original and points the search vector at it; on a four-message thread a phrase written once went from **four hits to one**. The full text is deliberately **kept**, so a better stripper can be re-run rather than having destroyed the original, and a message that is entirely a quoted block stays findable because "the stripper declined" falls back to indexing the whole message. Mail stored before `075` is unchanged until `python -m services.email_body_backfill --restrip`, which is local-only and never touches IMAP. **Operators pointing `POSTGRES_HOST` at an external instance (LUM-828):** migration `074` installs `pg_trgm`, the repo's only extension. It is a **trusted** extension on Postgres 13+, so superuser is not required — a role that owns the database, or holds `CREATE` on it, installs it fine, which covers the usual managed-Postgres setup. A role with neither gets a **refusal to boot**, not a degraded search, because a partial schema is worse than a refusal; the migration says so by name and prints the remedy — run `CREATE EXTENSION pg_trgm;` once as an administrator, then restart. Verified for all three roles in `orchestrator/tests/test_migration_074_extension_privilege.py`.
- **Which address a message leaves from (LUM-831):** the compose **From** row and the confirm card on **every** send name the mailbox as `Name — address` — e.g. `Work — alice@acme.com`. The address is **resolved on demand** from the mailbox's credential through `mailbox_account_address` and is never stored a second time, so what you are shown **cannot drift** from what the send uses: both read one field of one row. `GET /api/v1/email/sending-addresses` is owner-only, `no-store`, and rate-limited at 20/min; a mailbox whose credential will not decrypt shows **name-only and stays in the picker** rather than disappearing (removing it would take away a mailbox you can genuinely send from). With two or more sendable mailboxes and no addresses loaded, the From row says so; with one there is no choice to get wrong, so it stays quiet. A failed lookup **never blocks a send** — `From` is resolved server-side from the credential regardless.
- **Reply all (LUM-705):** a **Reply all** action beside Reply pre-fills the composer's `Cc` from the original message's `To` and `Cc`, minus the user's own mailbox address (matched case- and display-name-insensitively) and minus the sender, who is already in `To`. Duplicates collapse, keeping the first display name, so the field reads like the thread. Parsing uses the stdlib address parser, so a display name containing a comma stays **one** recipient. The Cc field is **expanded on open** — a pre-filled field behind a collapsed disclosure is how this feature would mail four people by surprise — and stays fully editable; it is a proposal, not a fact. Above 25 recipients the composer warns prominently, and beyond 90 it truncates and says how many were left out, **before** the send. Reply all is offered wherever Reply is, rather than only when the original had other recipients: deciding that needs the header fetch, which would then fire on every card in the inbox. **`POST /api/v1/email/reply-all`** re-fetches the original's named headers over read-only IMAP (the `To`/`Cc` fields were added to the same selective `HEADER.FIELDS` set LUM-651 established, so no bulk header copy is introduced and an injected header in a crafted original is never read). A **UIDVALIDITY** mismatch, a moved/deleted message, or an unreachable mailbox all **degrade to a plain Reply** with a 200 and an explanation — never an error code, since the signal is the caller's own and it is the mailbox that did not answer. That UIDVALIDITY check is shared with the send path rather than duplicated: a reset means the stored uid now identifies a *different message*, and using its headers would put a stranger's thread participants into the user's Cc. First-contact force-Ask applies across the expanded recipient set unchanged, and the confirm card still lists every resulting recipient.
- **Bulk triage + keyboard shortcuts (LUM-696):** `/email` gains **multi-select** — a per-row checkbox, **shift-click** for an inclusive range over the rendered order, and a **select-all** checkbox per lane — feeding a bulk action bar with exactly **two** data actions, **Mark done** and **Snooze▾** (the same five presets, with one wake time computed once for the whole batch). Selection is **pruned whenever the visible set changes**, so a filter keystroke can never leave you acting on rows you can no longer see. An **Undo** banner restores **each row's own prior state** rather than one state — a snapshot grouped by `(status, snoozed_until)` and replayed as one call per group, so undoing a bulk snooze does not silently clear rows that were already Done. **Single-key shortcuts**, scoped to the triage view and discoverable via a **`?`** overlay (never hidden): `j`/`k` (or `↓`/`↑`) move, `x` selects, `X` extends the range, `e` marks done, `s` opens snooze (then `1`–`5`), `u` undoes, `r`/`f` open reply/forward, `/` jumps to the filter box, `Esc` clears. They deliberately **refuse** to fire while you are typing in an input, textarea or contenteditable, while a composer or the help overlay owns the page, or when **⌘/Ctrl/Alt** is held — so `Cmd-R` still reloads — while **Shift** is honoured, since `?` and `X` need it. The keyboard cursor **is** DOM focus (it focuses the row's checkbox), so the browser's native focus ring is the visible state, screen readers announce the row, and the cursor cannot drift from real focus; it is never created on mount, only by intent. Server-side, **`POST /signals/triage/bulk`** `{signal_ids[≤200], status|null, snoozed_until?}` does the whole batch in **one statement** — `status: null` clears — returning `{updated, skipped, count}` where **`skipped` means "not visible to you"**, never "had no triage row": clearing a signal you can see but never triaged is a success, exactly as the single-signal `DELETE` has always been. Visibility is enforced **inside** the write via a CTE over `signals` under the household `visible_filter`, which closes the check-then-write race the single-signal path still has and means one purged signal cannot fail a batch of 200. No new triage states, no migration. The web chunks selections against the 200 cap; if a chunk fails, the batches that already landed **stay applied**, the banner names how many, and only the failures remain selected.
- **Proactive email surfacing (LUM-648):** the "Needs you" email subset now **comes to** the user through the unified dispatcher, off the request path via two in-process APScheduler jobs (no new service). A **snooze re-surface scan** (`signals/triage_reminders.py`, every `TRIAGE_REMINDER_INTERVAL`s, default 900) runs one atomic guarded `UPDATE signal_triage … WHERE status='snoozed' AND snoozed_until <= now() RETURNING …`, flipping due snoozes back to **needs you** and emitting one **`SIGNAL_NEEDS_YOU`** notification per affected user (rich sender+subject copy; grouped "N snoozed emails are back" when several are due). A **morning brief** (hourly cron at minute 5, gated to each user's local `TRIAGE_BRIEF_HOUR`, default 7) emits a **`SIGNAL_MORNING_BRIEF`** summarising the needs-you count and **stays silent when the count is zero**; the count mirrors the frontend `effectiveLane` (household-union, email-scoped, owner/projection-deduped by `COALESCE(published_from, signal_id)`). At **ingest**, an email that needs you (`importance ≥ 0.6`) is the single needs-you push; every other email is downgraded to **in-app-only** (tier `BACKGROUND`) and no longer marks `signals.notified` — `notified` now means "a needs-you push fired". Delivery honours per-user prefs + quiet-hours (a snooze expiring inside quiet hours flips but its push is **dropped**, surfacing via the brief / next `/email` visit). **Native web push** carries these two types via a dynamic-body path (`{title, body, url:"/email"}` through the `build_safe_push_json_from_dict` allowlist), gated on the per-subscription **`notify_on_signals`** opt-in (reset to FALSE once on this chunk's deploy so the PII-bearing push requires fresh consent); `/email` is in the service-worker click allow-list. `/email` also live-refreshes on the `needs_you` / `morning_brief` SSE events while open. Both new notification types appear in **`/me/notifications`** immediately. Jobs are individually switchable via `TRIAGE_REMINDER_ENABLED` / `TRIAGE_BRIEF_ENABLED`.
- **Feedback → relevance learning (LUM-649; [ADR 181](decisions/181-feedback-relevance.md)):** 👍/👎 feedback on email signals now measurably and legibly tunes what gets flagged. Each signal card carries a **👍** ("flag more like this") and the existing **Not important** button now also records 👎 (it both reclassifies the lane *and* teaches the profile). Explicit feedback nudges small, bounded per-user learned weights (±0.15 per click, clamped to [-1, 1]) on the signal's **topics**, **entities** (with the sender folded in as a "who" term), and **category** — stored as additive JSONB overlays on `relevance_profiles` (migration `058`), never mutating the shared `relevance_score`/`importance_score` columns. The effect is legible **two** ways: an in-the-moment toast naming the term that moved ("I'll flag fewer like this: *newsletter*"), **and** a durable, browsable **Relevance tuning** settings view (`/me/relevance`) listing every demoted/promoted term. Learning applies in two distinct places: **ingest-time, owner-scoped** — `match_relevance` gains an additive ±0.3 `learned_component` so the owner's own history shapes whether *they* get notified for similar future signals; and **read-time, per-viewer** — `GET /signals` returns a per-caller `learned_relevance_delta` (±0.6, added to `importance_score` before the *Needs you* lane threshold) so feedback tips a borderline signal across the line for *whoever is looking*, without changing what another household member sees. `POST /feedback` returns the moved term(s) synchronously; `GET /profile/learned` returns the caller's own current learned weights (visibility-scoped; feedback on a signal you can't see discloses nothing). v1 is explicit-feedback-only (opens/dismissals are recorded but not learned from) with no weight decay; the delta magnitude is a fixed constant, not env-tunable.
- **Outbound / SSRF:** the IMAP host is validated by a dedicated guard (`169.254.0.0/16` / link-local always blocked; loopback/private gated by **`LUMOGIS_ALLOW_PRIVATE_OUTBOUND_URLS`** + **`LUMOGIS_OUTBOUND_PRIVATE_HOST_ALLOWLIST`**).
- **Egress containment (LUM-625, [ADR 178](decisions/178-lum-625-email-imap-egress-containment.md); optional):** two honest layers constrain IMAP egress to the declared mailbox host, covering all four connection paths (poll, full-ingest body fetch, write-back apply/reverse — all via the single `EmailImapSource._connect`). **Layer 1** (`LUMOGIS_FF_IMAP_EGRESS_GUARD=true`, default **off**; every deployment): an in-process `tethered` socket allowlist scoped to the one host each connection dials, plus a connect-time SSRF re-check. Honest posture — **in-process, bypassable by a fully-compromised Core** (defense-in-depth, not an external wall). **Layer 2** (Docker only; **`LUMOGIS_IMAP_EGRESS_PROXY=host:port`**): Core routes IMAP(S) through the LUM-618 Squid proxy via HTTP `CONNECT`, which allowlists the mail host by TLS SNI (peek+splice, no MITM — the mail-host cert is still verified) and refuses undeclared hosts at the network layer; because Core dials the *proxy* and never resolves the mail host, the DNS-rebinding window is closed. The proxy rule is **source-scoped to Core** (`core_egress_src`) so it does not widen the LUM-618 community-capability containment. A set-but-invalid proxy value **fails closed**; a host the SNI allow file can't express (IDN / IPv6 / nonstandard port) falls back to the direct path (Layer 1 only). Not a hard wall against a fully-compromised, dual-homed Core — same bypassability class as Layer 1. **Allow-file / ceiling host enumeration (LUM-634, [ADR 199](decisions/199-lum-634-plaintext-mailbox-host-enumeration.md)):** the household union that feeds Layer 2's SNI allow file and the LUM-571 process-wide ceiling reads each mailbox's `(host, port)` from the plaintext `sources.url` row (`instance == sources.id`) via a DNS-free string parse — **not** by decrypting the IMAP credential payload on the happy path. A payload decrypt remains only on url-miss (missing source row or unparseable url), so a decrypt failure no longer silently drops a valid host from the allow file (the phantom-`egress_blocked` class LUM-633 surfaced). `GET /api/v1/sources`'s derived `smtp_host_required` uses the same shared parser.
- **Mailbox health — why a mailbox stopped syncing (LUM-690 / LUM-633, [ADR 195](decisions/195-lum-633-poll-health-connect-phase.md)):** a mailbox that can no longer poll says so in the Email signals view instead of failing silently in the operator log. `sources.last_poll_error_code` + `last_poll_error_at` (migration `063`) are stamped by `feed_monitor` and returned by **`GET /api/v1/sources`**; they clear automatically the next time the mailbox connects, so the banner is self-healing and needs no dismissal.
  **Health means *connected*, not *configured*.** `EmailImapSource.__init__` opens no IMAP socket — it loads the credential row — so an earlier version stamped healthy at construction and a mailbox blocked by the LUM-625 egress layer was reported as **fine** while it could not reach its server at all. Health is now recorded at every connecting call: the metadata seed and poll, the full-ingest poll and body fetch, and the backfill slice and its UIDVALIDITY reseed.
  **The code says which failure it was, because the right user action differs.** `credential` (reconnect — the only one the user can fix), `egress_blocked` (an operator allow-list decision; the credentials are fine), `network` (usually clears on its own), `config` (an invalid port, a plaintext connection to a remote host, or an empty or space-padded password — never clears until corrected). A single message previously told everyone they could not sign in, which sent a blocked user to re-enter a password that was already correct. Unknown codes fall back to a generic message, so the server can add one before the web client knows it.
  **OAuth token refresh reports the same four codes (LUM-757).** A mailbox on OAuth resolves its credential by refreshing an access token, and every way that can fail used to arrive as one exception the classifier read as `credential` — so a token endpoint that timed out, or an operator who had not set `LUMOGIS_OAUTH_MICROSOFT_CLIENT_ID`, both told the household member to reconnect a mailbox whose grant was fine. The refresh now labels its own failures at the point the provider's response is in scope: a revoked or expired grant (`invalid_grant`) is `credential`; an unregistered app (`invalid_client`) or a missing client id is `config`; a timeout, a 429 or a 5xx is `network`; and a block by the egress layer is `egress_blocked`, not `network`, because it never clears without an operator changing the allow-list. The mapping keys on **RFC 6749** error values rather than provider-specific codes, so it holds for a second provider. Send failures follow the same split: a transient refusal reports `smtp_send_unavailable` rather than `smtp_auth_failed`, though every kind still fails the send permanently — the composer builds a fresh proposal on retry, so a lingering row would become a duplicate send.
  **A failing token endpoint is not called again straight away (LUM-761).** After a `network` failure of the refresh — a 429, a 5xx, an unreachable endpoint, or a success reply that is not a JSON object — Lumogis remembers it per mailbox and answers later callers with the same `network` error without a request, until the time the provider's `Retry-After` asks for has passed (kept between 5 s and 10 minutes), or 10 s when there is no such header. It never sleeps through a `Retry-After`. A connection that fails before anything was sent is retried once; a failure that may have been received is not, because a provider that rotates refresh tokens could already have used it. The health code and the send error code are unchanged: the cache raises the same error with the same `kind` ([ADR 228](decisions/228-lum-761-oauth-refresh-transient-retry.md)).

  **Scope is the connect, deliberately.** A failure *after* connecting — one malformed message mid-fetch — clears the banner rather than raising it: reaching the fetch proves the mailbox connected, and flapping a health indicator on transient fetch noise is how people learn to ignore it.

  **Turning on sending answers with the same distinctions (LUM-759).** `PUT /api/v1/me/email-sources/{id}/smtp` resolves the mailbox's IMAP credential first, and used to report *every* way that could fail — a decrypt failure, a host refused by the SSRF policy, a token endpoint that timed out, or an internal bug — as `422 imap_not_configured`, with no log line. Operators debugging a failed send opt-in had one status code and nothing else. It now answers by cause: **`503`** for conditions the user cannot fix by changing anything (`mailbox_unreachable` for a timeout or DNS failure, `egress_blocked` for an allow-list refusal, `oauth_unavailable` when the operator has not configured a client id, `credential_unavailable` for a decrypt failure), and **`422`** for conditions they can (`imap_not_configured` when no mailbox sign-in is stored, `imap_reauth_required` when it has expired, `imap_settings_invalid` for a bad stored port). Anything unrecognised is a **500** with a traceback rather than a 4xx blaming the user's settings. Every branch logs `email.smtp.optin.imap_load_failed` with the exception type — never the message, which can name a host or a payload field.

  **An OAuth mailbox can actually be switched on (LUM-771).** The pre-save connect-test verifies with the mailbox's own credential: an app-password mailbox with its app password, an **OAuth** mailbox with its access token (`xoauth2`). It used to forward neither on this route, so an Outlook mailbox — whose stored connection deliberately carries *no* password — was connect-tested with an **empty** one and failed every time; because the OAuth connect flow enables sending automatically, turning sending off was a one-way door. When the provider refuses an OAuth mailbox's submission, the opt-in answers **`smtp_oauth_denied`** rather than `smtp_auth`: there is no password to correct, and the fix is a permission at the provider — a Microsoft 365 tenant with SMTP AUTH switched off, a grant missing the send scope, or a grant that was revoked. `smtp_auth` still means what it always did (the sending password is wrong) and is reserved for mailboxes that have one. For the same reason an OAuth mailbox **refuses** a separate sending password rather than accepting one it would never use: asking for `reuse_imap_password: false` on one answers **`422 smtp_password_not_applicable`** (LUM-772), because the send path always authenticates such a mailbox with its token — a password stored there would be an encrypted secret nothing reads and no revocation clears. `GET /api/v1/sources` also carries a per-row **`smtp_host_required`** — true only for an IMAP source whose host has no provider-registry entry, so a client can tell in advance which mailboxes need a submission host/port typed in instead of discovering it as a failed opt-in. It is **derived on read** from the source's own url by the same registry lookup the opt-in route matches with; it is never stored, and it is `false` for every non-mailbox source. `GET /api/v1/sources` also carries **`auth_method`** (`oauth`, `app_password` or `null` for unknown), derived on read from the credential's stored field names without decrypting it; the mailbox health and send controls use it to name the right fix, and fall back to naming both owners when it is unknown.

  **Sending can be turned on and off after setup (LUM-769).** Until now the opt-in had exactly one home — the create form — so "let Lumogis send as me" was a decision made once while connecting a mailbox and never revisitable, even though the backend has always treated it as independently revocable. Each mailbox card now shows **Sending** and **Attachments** as always-visible lines, readable without opening a disclosure, and a named button rather than a switch, because the interaction is asymmetric: turning sending off is instant, turning it on is one click for a known provider or an OAuth mailbox and a short form for the rest. **A sending password is asked for only when the server proves the mailbox password was refused** — never up front, never when the sending server was merely unreachable, and never for an OAuth mailbox, which has no password to give. A mailbox whose provider Lumogis does not recognise shows the submission host and port before the first attempt rather than after a failed one. An opt-in that saved but could not be checked reads **"on — not yet verified"** rather than a plain "on", and if Lumogis cannot read your credential list at all the line says **unknown** rather than claiming sending is off.

  **A failed send opt-in no longer disappears.** The setup form previously discarded the result entirely: a user who ticked *"let Lumogis send as me"* got a connected mailbox with sending silently off, and found out at the first send. The mailbox still connects regardless — that part was always right — but the form now says which of the above happened and who can fix it. `docs/decisions/195-…` owns the wording; the send-opt-in copy deliberately mirrors it so the same condition reads the same way in both places.
- **Cross-user label on shared signals (LUM-632):** `GET /api/v1/signals` returns the household union, so a member sees another member's **shared** email signals carrying category **slugs** from the *owner's* taxonomy. Alongside the stored `category` (slug), each row now carries a resolved **`category_label`** — the human label from the **signal owner's** (`signals.user_id`) taxonomy, so a household member sees the owner's label (e.g. "Landlord") rather than a raw slug they can't resolve. Resolution is batched per distinct owner (cached, no N+1); it falls back to the **raw slug** when the slug isn't in the owner's taxonomy (deleted custom / DB blip) and is **`""`** only when `category` is empty. It exposes **no** new visibility — only rows already returned by `visible_filter` are touched, and personal (non-shared) signals never resolve cross-user. `category_label` is **presentation-only** (never persist or filter on it); the prerequisite that shared projections carry the slug is handled by `projection.project_signal` (forward-only — pre-existing shared rows render the raw slug until re-shared).
- **Mailbox write-back — the act tier (LUM-623, ADR-164):** Lumogis can apply a classification-driven **mark-read / flag / move / label** back to the mailbox on a specific message, under **per-message Ask/Do approval** — never auto-write. The flow: **`POST /api/v1/approvals/proposals`** `{action_name, payload:{signal_id, target?}}` creates a `pending` proposal (`imap_mark_read` / `imap_flag` / `imap_move` / `imap_label`); **`POST …/proposals/{id}/approve`** marks it `approved`; **`POST …/proposals/{id}/execute`** runs it. The four ops are **reversible** (`POST /api/v1/audit/{token}/reverse` undoes them — move-back relocates the message by **`Message-ID`**), and **audited**. The client passes only a **`signal_id`** (never a raw UID); the handler recovers `(source_id, uidvalidity, uid)` from the signal's `imap://…` url and requires the **source to be OWNED by the caller** (ownership, not visibility — a member cannot write to another member's mailbox via a shared signal). Server-capability-resolved: moves use **UID MOVE** (RFC 6851) with a **COPY + targeted UID EXPUNGE** fallback under UIDPLUS (never a bare EXPUNGE), and "label" is Gmail **`X-GM-LABELS`**, else a custom IMAP keyword, else it asks you to pick a folder. Uses the same IMAP credential as ingest (no separate scope). Permanent failures (stale UID, unsupported capability) dead-letter without retry. **Outbound SMTP send** (reply / compose) landed separately in LUM-650 (see the outbound-send bullet below); standing category→action rules and bulk remain out of scope. `EMAIL_WRITEBACK_ENABLED` is not required — writes are gated by the connector's ASK/DO mode + per-message approval.
- **Systematic mailbox organization — opt-in label / folder-sort (LUM-645, ADR-183):** on top of the per-message act tier, Lumogis can **systematically** apply its classification to a mailbox under two independent, default-off, reversible **per-mailbox opt-ins**: **Label** — tag every classified email with its category (Gmail nested label `Lumogis/<category>`; non-Gmail via an IMAP keyword **atom** `Lumogis_<slug>`), mail stays in the inbox; **Sort into folders** — **move** the selected categories into per-category `Lumogis/<category>` folders (created on demand using the server's own hierarchy delimiter), never moving the protected `other`. Set via **`PATCH /api/v1/me/email-sources/{id}/organize`** `{organize_label, organize_folder, organize_folder_categories[], apply_to_existing}` (owner-only, CSRF + rate-limited, returns **202** — the IMAP work runs on the poll-tick sweep, never synchronously). Application is a **standing per-tick reconcile sweep** driven by the `email_organize_log` ledger: go-forward on live-poll mail (backfill history is owned by the sweep, not the ingest hook) and, when `apply_to_existing` is set, back over existing mail from an `organize_since` watermark; a transient IMAP failure writes no ledger row and is retried next tick. **Bulk undo** via **`POST …/organize/undo`** `{scope: label|folder|all}` (202) disables the covered opt-in and tick-reverses every applied row (move before label, by `Message-ID`); the **activity log** is **`GET …/organize/log`**. Every op reuses a single IMAP session per sweep (no per-message login churn). **Honest cross-provider posture:** Gmail shows native labels; on iCloud/Fastmail the keyword is often not displayed by the mail client, so the provider registry carries a `label_visible` flag and the web steers those users to folder-sort (the visible path). Reuses the LUM-623 mechanical write/reverse layer; triage state stays Lumogis-only (never written to the mailbox).
- **Chunked inbox cleanup — date-range passes + safe spam clearing (LUM-646, ADR-183 / explore LUM-647):** an on-demand tool to work through a messy inbox one **date range** at a time, distinct from (and independent of) the standing organize opt-ins above. **`POST /api/v1/me/email-sources/{id}/cleanup`** `{window_start?, window_end?}` starts a re-runnable **cleanup job** (`email_cleanup_job`, migration `061`) that backfills+classifies that window (reusing the LUM-644 `backfill_slice`), **auto-labels** it (label-visible providers only, and only when the standing label opt-in is off), and records per-message membership (`email_cleanup_item`). Once the window is `ready`, **`GET …/cleanup/{job}`** returns per-category proposals; **`POST …/cleanup/{job}/approve`** `{actions:[{category, move}]}` files the chosen categories into `Lumogis/<category>` folders. The **only destructive action** is a separate **"empty spam folder to Trash"** — **`GET/POST …/cleanup-spam`** moves the provider's own `\Junk` special-use folder to `\Trash` (provider-confirmed spam; the window pass never trashes inbox mail — bulk ≠ spam). Everything is executed off the request path on the poll tick and is **reversible** via **`POST …/cleanup/{job}/undo`**: cleanup-written rows carry a `cleanup_job_id` on the shared `email_organize_log` ledger, so a job-scoped undo reverses **only** that job's rows, never a row the standing organize owns. Window and spam jobs are **mutually exclusive** per mailbox. Move-to-Trash is reversible until the provider clears Trash (~30 days on Gmail); never a silent delete / EXPUNGE.
- **Outbound send — reply + compose-new, sent as you (LUM-650):** the first **outbound** email capability. Lumogis sends **as you, through your own provider's SMTP submission** (Gmail/iCloud/Fastmail) — never a Lumogis relay or a home-IP MTA — so your provider applies your own SPF/DKIM/DMARC. Opt in per mailbox with **`PUT /api/v1/me/email-sources/{id}/smtp`** `{enabled, reuse_imap_password?, app_password?, smtp_host?, smtp_port?}` (owner-only, CSRF, rate-limited; a **live pre-save connect-test** fails a bad sending password loudly without persisting; `enabled:false` removes the send credential so receiving is untouched — independent revocation). The default reuses your mailbox's IMAP app-password; host/port come from the provider registry (an **"Other"** mailbox supplies its own). Two actions ride the **existing** proposal → Approvals → executor pipeline (no bespoke send route): **`email_reply`** (recovers the mailbox + original sender from the signal; re-fetches the original `Subject` + `Message-ID` + `References` so "Re: …" and the **full RFC 5322 threading chain** (`In-Reply-To` + `References`) are correct and the reply nests in the recipient's client (LUM-651), degrading gracefully when a cleanup/organize move already relocated the original) and **`email_compose`** (fresh message from an owned mailbox). **From is always the mailbox's authenticated account** — the action inputs have no `from` field (anti-spoofing, and required by provider submission). Sends are `is_write`, **not reversible** (you can't unsend — the reversible sibling, Save-to-Drafts, is a later chunk). Header-injection safe (`EmailMessage` + CR/LF rejection); egress-contained (the submission host folds into the LUM-571 ceiling). **First-contact protection:** `email_send` is deliberately **not** hard-limited, so a user could set it to Do (auto-approve) — but a send to a **new address** (never received-from nor sent-to before) is **always forced to an explicit Ask**, even in Do mode. This is a create-time risk annotation stamped on the proposal (`action_proposals.annotation`, migration `062`) that **fails closed** (uncertainty → Ask) and is read by the Ask/Do resolver. **Not in v1:** the compose/reply UX (LUM-652), autonomous/bulk send (the hard-limited `first_contact` action_type stays reserved for it). *(OAuth/Outlook connect shipped in LUM-686/687 — see the OAuth email connect entry above.)*
- **Send UX — composer, confirm, Save-to-Drafts (LUM-652, [ADR-187](decisions/187-send-ux.md)):** the surface that turns the LUM-650 send backend into "you can send from Lumogis." A **Reply** affordance on a flagged email (shown only when the signal has a sender) opens an accessible **composer** (native `<dialog>`, focus-trap/Escape, an "In reply to:" context header) that can pre-fill an **on-box LLM-suggested** reply draft — generated locally (the same `require_local_model` privacy boundary as email classification; **never** a cloud model), fetched asynchronously so the composer opens instantly and a late draft never overwrites text you've already typed, and bounded by a per-request deadline **and** a global concurrency cap so draft-generation can't contend the shared on-box model. Submitting shows a **confirm card** — "Send this to X, from your address?" — with the **first-contact** notice, and two outcomes: **[Send]** (SMTP, LUM-650) and **[Save to Drafts]**, a new **`email_save_draft`** action that IMAP-`APPEND`s the *same* MIME the send would emit (byte-identical modulo its Message-ID, threading included) to the mailbox's SPECIAL-USE **`\Drafts`** folder so it shows up in your real client. Save-to-Drafts needs **no** SMTP opt-in (From is the mailbox's own IMAP account) and is **not** a send (it never touches the sent-log or first-contact history); it degrades to Send-only when the mailbox advertises no Drafts folder. It is **reversible** (LUM-681): the Approvals audit trail can un-save a draft — the reverse locates it in the Drafts folder by its Message-ID and removes it (targeted UID EXPUNGE under UIDPLUS; a draft already gone is an idempotent no-op). Both outcomes ride the **existing** proposal → Approvals → executor pipeline; a failed attempt dead-letters, so **Retry** builds a fresh proposal from your preserved text, and the confirmation reads **"Saved to Drafts ✓"** vs **"Sent ✓"** so a draft is never mistaken for a delivery. The confirm card creates the send proposal when you reach it, so diverting to Save-to-Drafts, going back to edit, or closing the card **cancels** that unsent proposal (`pending → rejected`, owner-scoped) rather than leaving it to linger (LUM-682). The pending-proposal API additionally exposes a display-only **`first_contact`** boolean (the executor's force-Ask gate remains the security truth) and an additive machine **`code`** on the execute response so the card branches on the failure kind, not an English string. **`POST /api/v1/email/reply-draft`** `{signal_id}` returns the suggested body (owner-scoped 404; separate rate-limit bucket; `""` when no local model / no body / a miss). **Not in v1:** proactive/background pre-drafting + learning-from-corrections (app-scope), HTML/rich-text compose.
- **A failed send is recoverable — from your mailbox, not the app (LUM-793):** a send that fails is finished (LUM-762 / [ADR 201](decisions/201-lum-762-action-proposals-claim-not-queue.md)), and the message it carried is kept. **Messages that didn't send** on the Approvals page lists failed sends for **30 days** (`RECOVERABLE_SENDS_WINDOW_DAYS`) with their full text, and offers one action: **Save to Drafts**, which runs the same `email_save_draft` the composer offers and writes the message to your mailbox's real Drafts folder. That is deliberately a **mailbox** recovery rather than an in-app one — where the failure was SMTP itself (down, misconfigured, rate-limited, an app password revoked), restoring into Lumogis would fail again on the same path, while a draft in the real folder can be sent from any client. The exception is a mailbox where IMAP and SMTP share one OAuth credential: saving a draft is an IMAP `APPEND`, so a revoked grant breaks both. **Each row says whether the message actually went out**, and says it rather than hedging — Lumogis holds the send log, so it looks. `email_sent_log` is written at **submission time**, inside the handler, before anything can strand the proposal, so a row reads **Sent** (with the time), **Partly sent** (naming who did and did not receive it — a partial recipient refusal logs the accepted recipients and *then* fails, so recovery stays open for the ones who never got it), **Not sent**, or **Couldn't confirm**. A fully-**Sent** row offers no Save-to-Drafts, and the server re-checks that on the click (**409**), not just by hiding the button. **Dismiss** moves the row out of the listing (`dead → archived`) and deletes nothing. Attachments have their own clock: making failure terminal let the sweep reclaim a failed send's staged files promptly, so terminal proposals now get a **7-day grace** (`EMAIL_ATTACHMENT_DEAD_GRACE_HOURS`, default **168**) and the row states availability from what is **actually still on disk**, never from the stored payload. If a file has expired, Save-to-Drafts writes the draft anyway and tells you what to re-attach — a draft you can fix beats no draft. Migration **`072`** adds **`email_sent_log.proposal_id`** so the match is exact; sends recorded before it resolve through a bounded fallback. **Known gap:** a mailbox with no Drafts folder still has no recovery path — the text is visible and copyable, which is more than before, but LUM-793 stays open on it.
- **Cc/Bcc, Forward, and the quoted original (LUM-698):** the composer now covers what people actually reach for after their first reply. **Cc and Bcc** are accepted by `email_reply`, `email_compose`, `email_forward`, and `email_save_draft`, behind a collapsed disclosure so the simple case stays simple. Bcc is set as a header and delivered by `smtplib`'s `send_message`, which builds the envelope from To+Cc+Bcc and then **strips the `Bcc:` header before serialising** — so a Bcc recipient is delivered to but never disclosed on the wire (there is a test that runs the real stdlib `send_message` against a fake transport and asserts both halves; the adapter carries a "do not 'fix' this" note because the code *looks* like a leak until you read the stdlib). A saved **draft** deliberately keeps its Bcc — it lands in your own mailbox, and real clients preserve it so you can resume the send. **Bcc is never a first-contact input**: the `_is_first_contact` sent-side lookup unions `to_addrs || cc_addrs` only, and there is no index on `bcc_addrs` — a Bcc address is recorded for audit/export but must never become an oracle for who you have quietly mailed. Recipient lists are capped at **100 per field**. A new **`email_forward`** action forwards an owned signal to recipients you choose: it re-fetches the original `Subject` for an idempotent `Fwd:` prefix, and deliberately carries **no threading headers** (a forward starts a new conversation, it does not nest in the original). **Attachments are not forwarded** — the body text is (LUM-695 covers attachments). The **quoted original** is built by `services/email_quote.py` and served by **`POST /api/v1/email/quote`** `{signal_id, style: reply|forward}` — owner-scoped through the same `_signal_url` → `_parse_imap_url` → `_load_owned_source` chain as the reply-draft path (a foreign signal returns `""` and **no body is ever read**: the ownership gate runs before the fetch), best-effort and never-raises so the composer degrades to "no quote" rather than blocking a send, and bounded at 20k chars. It is served to the **composer**, not stapled on server-side at send time, and rendered **visible and editable** — you can see and trim exactly what you are about to forward before an irreversible action, and the composed body (your note + the quote) is what the confirm card previews and what gets sent. The confirm card lists **every** recipient including Cc and Bcc, and its first-contact notice is **recipient-agnostic** ("one or more recipients…") — the flag can be raised by any recipient including a Bcc, and `_annotate_send` returns a boolean only, by design, because it runs before the execute-time ownership gate and must not become a recipient oracle. **Not in v1:** Reply-all, forwarding attachments, HTML quoting.
- **Unsubscribe + sender suppression (LUM-697, [ADR 191](decisions/191-email-unsubscribe.md)):** cleanup sorted a recurring newsletter but never stopped it arriving. `List-Unsubscribe` was **already** fetched at ingest (it is in the IMAP adapter's lean `_HEADER_FIELDS` and already read as a bulk-mail boolean by the classifier) — only the value was discarded. It is now parsed and stored **per sender** (`email_unsubscribe_target`, migration `065`, one row per `(user_id, source_id, from_addr)` with a message count), alongside `List-Unsubscribe-Post` for RFC 8058 detection. **The parser is the security boundary:** a `mailto:`/`https:` **scheme allowlist** (a `javascript:` URI in this header is a real stored-XSS vector — CVE-2025-68673), URIs carrying **userinfo** rejected (`https://evil@real-bank.example/…` is a display spoof on a link we render), and **only the first address** of a multi-address `mailto:` taken so a crafted header cannot fan out into a send to recipients the user never reviewed. **Lumogis never fetches an unsubscribe URI server-side.** The `https:` form is handed to the **user's browser**, which is what mainstream mail clients do; the `mailto:` form is sent through the existing SMTP stack. That is a decision, not an omission: the destination is written by whoever sent the message, the LUM-571 egress ceiling bakes its allowlist at boot and cannot express a runtime-discovered host, and RFC 8058's DKIM requirement — the mechanism that would distinguish a genuine one-click header from a forgery — is unmeetable because there is no inbound DKIM verification (LUM-707). Nextcloud Mail shipped server-side fetching here and took a blind-SSRF advisory; a structural test asserts these modules contain no HTTP client at all, and `one_click` is stored but **gates nothing**. Acting on `mailto:` is a new **`email_unsubscribe`** action: **one proposal per batch** (max **10** senders, reviewed once), **one SMTP message per target** (a multi-recipient send would put every other unsubscribe address in `To:` and leak the whole subscription list to each recipient), recipients resolved **server-side** by `POST /api/v1/email/unsubscribe/propose` so no address crosses the boundary inbound and the approved payload is byte-for-byte what sends. It is **always force-Asked** — it declares an `annotate` hook returning `first_contact: True`, which is both the key `executor._resolve_force_ask` actually reads and literally true; without it, a user who set the `smtp` connector to DO would have got silent unreviewed bulk unsubscribes, because permission mode is resolved **per connector, not per action type**. It is deliberately **not** hard-limited (that would refuse it even on the approved path); the batch cap makes "mass" structurally impossible instead. Each target is stamped as its **own** send succeeds and already-stamped targets are skipped, so retrying a batch that died midway sends only the remainder. **Sender suppression** (`email_sender_rule`) is a standing per-sender **`hide`** rule checked in `process_signal` **before the on-box classification call**, so a silenced high-volume sender costs a cached dict lookup rather than an LLM run; it performs **no IMAP operation**, so there is nothing to fail, retry or reverse. Clearing a rule is **go-forward only** — a hidden message has no `signals` row and the poll cursor has advanced past it. `mark_read`/`trash` suppression is **deferred (LUM-709)**, not omitted: `apply_organize` accepts only label/move/trash, `_pending_for_op` cannot retry work with no `signals` row, and `undo_tick` reverses only `{label, move}` — all three would need building, not inheriting. **Not in v1:** server-side one-click (LUM-708), `mark_read`/`trash` rules (LUM-709), historical backfill (LUM-711).
- **Attachments — read on demand, send from the composer (LUM-695):** the most obvious real use case for a household admin assistant, and previously impossible in both directions. **Reading:** attachment *metadata* (filename, MIME type, decoded size, part index) is extracted during full-ingest, in the **same MIME parse that already produces the body text** — no extra IMAP round trip and no second traversal — and persisted per signal (`email_attachment`, migration `066`). **Bytes are never stored.** They are fetched on demand when the user opens one, which is a product-visible trade rather than only an implementation choice: opening an attachment needs the mailbox reachable, and a message deleted upstream takes its attachment with it. The UI says so, and the API keeps **503 (mailbox unreachable, retry)** distinct from **410 (message gone, never will work)** so the cost never reads as a bug. The fetch does **not** assume INBOX — LUM-645's organize routinely moves classified mail into `Lumogis/<label>`, so the message is located by `Message-ID` (organize's recorded folder first) and only declared gone once that search is empty. Two independent size caps apply, because the fetch and the attachment are different objects: the attachment's decoded size, **and** the whole message's via an `RFC822.SIZE` precheck before any `BODY.PEEK[]` — a hostile 400 MB message carrying a 10 KB attachment would otherwise pass the attachment check and still exhaust memory, since `client.fetch` buffers. Downloads are **always** `Content-Disposition: attachment` plus `nosniff` (serving a sender's `text/html` inline would be stored XSS on our own origin), filenames are sanitised before storage, and executable extensions are refused — **not** virus scanning, and labelled as the partial measure it is. A **metadata-mode mailbox reports `available: false`, never an empty list**, because "none" would be an outright lie about a message with three. **Sending:** the composer stages files through `POST /api/v1/email/attachments/stage` and the action payload carries **references only** — `action_proposals.payload` is JSONB rendered verbatim on the approval card, so base64 there would bloat the row, cross the wire twice, and show the approver noise instead of "3 files, 1.2 MB", which is what the card now shows. The on-disk name is **server-controlled** (`{staged_id}/blob`), never the client's filename, which eliminates the Unicode-normalisation / case-collision / reserved-name class outright rather than trusting a sanitiser. `build_message` grows one `multipart/mixed` path, so reply / compose / forward / save-draft all carry attachments through the single shared builder. Staged files are swept by **proposal state, not wall clock**: `action_proposals` rows never expire, so a flat TTL would have deleted the attachments of a proposal staged on Friday and approved on Monday — every weekend, deterministically. A live proposal's files are never swept however old; only an **unreferenced** file (an abandoned composer) ages out on `EMAIL_ATTACHMENT_STAGING_TTL_HOURS`, and a terminal proposal's are reclaimed after `EMAIL_ATTACHMENT_DEAD_GRACE_HOURS` (default **168** — 7 days) measured from its `finished_at`. That grace was **0** between LUM-762 and LUM-793: making a failed send terminal meant its files went on the next hourly tick, roughly an hour after the failure, while LUM-793 lists the message for recovery for 30 days. The grace is bounded and applies to **terminal rows only** — it is not a return to pinning a live proposal's files forever. A per-user quota on unconsumed staged bytes refuses **before** writing, since the TTL bounds a file's lifetime and not the rate they arrive. **Forwarding an original's attachments (LUM-712)** closes the gap LUM-698 named: a forward lists the original's own attachments and carries the ones the user ticks. They are **opt-in per file, none pre-selected** — forwarding a 20 MB document someone did not notice is exactly the surprise the approval card exists to prevent. The payload carries **part indexes**, not bytes, on the same reasoning as staged uploads: the signal already identifies the message, so the handler re-fetches at execute time — all of them in **one IMAP session and one parse**, not one per file. A part that cannot be re-fetched dead-letters the send rather than quietly delivering a message missing the document it existed to pass on, and the approval card counts re-attached originals so its summary stays true. Saved forward drafts carry them too, because a saved forward and a sent forward must be the same message.

**Attachment size caps are per-provider (LUM-715)** where the provider is known — Gmail 25 MB, iCloud and Outlook 20 MB, Fastmail 70 MB — falling back to `EMAIL_ATTACHMENT_MAX_MB` for an "Other" host, because inventing a limit for a server whose policy we do not know would refuse legitimate sends. A single global number was wrong in both directions: too strict for a provider that allows more, and too loose for one that allows less, where the user only discovered it as an SMTP refusal *after* approving.

**Organize asks before it can starve paperless (LUM-729).** Folder-sort moves classified mail out of `INBOX`. A paperless mail rule watches **one** folder, and its default is `INBOX`. Both systems poll on their own clock, so whichever arrives first takes the message — and modelling the two defaults (Lumogis 900s, paperless 600s) with arbitrary phase, roughly **one message in three** was taken before paperless ever saw it. Nothing reported it: paperless found nothing to consume, Lumogis recorded a successful organize, and the archive of record developed holes at a rate slow enough never to be noticed. It was also selective in the worst direction, since only *classified* mail moves and that is disproportionately the mail carrying documents worth keeping.

So turning folder-sort **on** — or ticking **apply to existing mail**, or approving a cleanup window that moves anything — while a paperless source is configured now requires an explicit acknowledgement (`acknowledge_external_consumer`, **422** `external_consumer_may_starve`). **It is a consent gate, not a refusal:** both systems are the user's, and a product that decides they may not use its own organize feature because they also run paperless is overreaching. The failure was that the consequence was *invisible*, not that the choice was wrong. **Three arming events, because each looks complete on its own:** the OFF→ON transition, and `apply_to_existing` — which sets the organize watermark to epoch and moves every classified message the mailbox has ever received, and which an already-sorting user reaches without ever crossing the transition. The third is **connecting paperless while a mailbox already folder-sorts** — the same starvation, armed from the other side, and at least as likely an ordering for someone who set Lumogis up first. Editing your category list is **never** gated (the request body is a full replace, so reading the value rather than the change would toll you on every save), turning it **off** is never gated, labels alone are never gated, and the paperless *preview* step is never gated because it writes nothing. Enabling folder-sort with no categories chosen yet **is** gated, even though nothing moves at that moment: picking categories afterwards is an already-on edit, so that first save is the only point at which you are asked. **The check is deliberately coarse** — it asks only whether paperless is configured, not whether it watches *this* mailbox — because a false positive costs one click and a false negative costs documents. It **fails open** if the query breaks, and logs a warning when it does: a broken guard must not stop you configuring your own mailbox.

**The alternative is offered to every provider, not just Gmail.** Labels and moves are separate IMAP operations read from two independent opt-ins, so labels-only leaves mail in the inbox everywhere — on a provider that does not *display* Lumogis labels you lose the visible category, but paperless keeps receiving everything, and that is a trade for you to make rather than one to be made for you. The organize undo also gained its scope control (`folder` puts mail back without discarding your labels), because a warning that implies recoverability alongside a recovery path you cannot reach is a promise the product does not keep. The warning says plainly that undo returns messages to your inbox and does **not** hand paperless the documents it missed while they were gone.

**Two follow-ups closed with LUM-729.** **The organize undo now gives up rather than wedging.** `email_cleanup` has bounded its undo since LUM-646; the organize undo did not, and its failure was worse. `undo_tick` cleared the pending scope only when *no* un-reversed row remained, so one message that could never be moved back — deleted upstream, moved in your mail app, a folder that no longer exists — left the scope set forever. And because the poll tick skips the standing reconcile sweep whenever an undo reports work, that single message **permanently stopped Lumogis organizing that mailbox**, silently, while opening a fresh IMAP session every tick to retry it. The sweep now stops after 20 ticks (the same bound `email_cleanup` uses), releases the mailbox so organizing resumes, and **says so in the activity view** — how many messages it abandoned and that they stay where Lumogis put them. A bound that gave up invisibly would have traded one silent failure for another, which is the thing this whole area exists to stop. Migration `071`.

**And a Do-mode `imap_move` is now always Asked when you run paperless.** LUM-729 gated the standing policies that take mail out of the inbox; LUM-623's per-message write-back was the path left over, and it runs under whatever permission mode the `imap` connector is set to — so with that set to Do, an agent could move a message out of the inbox before paperless consumed it, with nobody looking. It is a different shape from a standing policy, so it gets the mechanism the product already uses for "this particular call has to be seen": a create-time annotation that forces an explicit approval even in Do mode. **Only `move`** — marking read, flagging and labelling leave the message in the inbox, and annotating them would train people to click through the one that matters. The check **raises rather than failing open**, deliberately opposite to the settings-page guard: there a broken check must not stop you configuring your own mailbox, here an unanswerable question must put the action in front of a person.

**Inline `cid:` images are not attachments (LUM-713).** A part the HTML body can reference by `cid:` — a signature image, a newsletter logo — is classified inline and kept out of the attachment list, where it was previously noise that made the body read as if something were missing. An explicit `Content-Disposition: attachment` still wins over a Content-ID, so a real attachment is never hidden.

**And they are now shown, below the text.** That left them visible nowhere — out of the attachment list by design, with no rendered body to appear in — so the photo, the scanned letter and the chart were all invisible. They now appear as a **strip beneath the extracted text** on the message card. The containment argument this needed is not an exception to the rule that sender bytes stay out of a rendered context; it is narrower than the rule and does not depend on it: **nothing sender-authored is ever parsed as markup or executed.** Every image is identified from **its own first bytes** against an allowlist of four signatures — PNG, JPEG, GIF, WebP — and the `Content-Type` the sender declared decides nothing. That is what excludes **SVG**, which is the one image format that is also a script container, and which has no magic number, so only an allowlist can exclude it; a blocklist would admit it the moment a sender declared something else. Identification reads twelve bytes rather than decoding the image, because decoding an attacker's picture is a far larger attack surface than reading its header. Images ride the **same `/body` response** as the text, so the ownership gate that protects the message protects them, and one action costs one request. They are bounded — six images, 512 KB each, 2 MB total — and when a cap bites the strip **says how many are missing** rather than showing gaps. A part that fails identification is simply **absent**, not a broken-image icon, and is never counted as missing: a refused part was never something you could have seen. The footer stops claiming images are not displayed once they are. **Remote images are still never loaded** — only the bytes the sender put in the message itself, which is what makes this free of tracking pixels.

- **Attachments into the document library (LUM-702, revised by LUM-727):** opt-in **per mailbox**, off by default. Enabling it now means *"show me this mailbox's attachments so I can decide"* — see LUM-727 below; the machinery described here is what runs once you have decided. Filing takes the attachments LUM-695 already recorded, fetches their bytes on demand, runs them through the **same `@extractor` registry** that reads uploaded files, and files the text as ordinary documents — searchable, and indistinguishable downstream from something you dragged in yourself. Registering a new extractor widens this feature without touching it. **Nothing is filed without consent**: creating documents from someone's mail uninvited is the behaviour this product exists to be the opposite of, so every existing mailbox keeps behaving exactly as before until someone turns it on, and enabling is **go-forward only** unless you explicitly ask to apply it to existing mail. Since LUM-727 the consent is **per attachment**, not per mailbox. A **metadata-mode mailbox cannot be enabled at all** — it never downloaded message bodies, so there is nothing to file; the toggle is disabled with an explanation rather than accepting a click that would do nothing. **Dedupe is by the sha256 of the attachment bytes**, so the same PDF forwarded twice is one document while two scans of the same invoice are two — and it is enforced by a **partial unique index**, not by an application check that races itself. The key is per mailbox: the same invoice arriving in two connected mailboxes files twice, which is the honest cost of keeping disconnection clean (removing a mailbox removes its filings without orphaning a document another one still needs). Every filing is listed with the email it came from, and **reversible** — one row or a whole mailbox's worth. Undo deletes the chunks **before** marking the row reversed, because the other order tells you a document is gone while it keeps turning up in search, and a failed delete leaves the row un-reversed so the next attempt retries rather than lying. **Undo sticks**: an attachment you remove is never re-filed by a later sweep. That is deliberate — the alternative is a document reappearing tomorrow with no explanation — and it means re-filing something you undid needs an explicit action, which is a follow-up. The list also shows what was **skipped and why** ("no text could be read from this file type", "already filed", "too large"), because an attachment that silently never appears reads as a broken feature. Executable extensions and oversize files are refused **from the recorded metadata, before any bytes are fetched**; extraction runs through a temporary file that takes only a sanitised extension from the sender's filename, never a path component, and is deleted on every path including a parser that throws. **Not in v1:** re-filing after an undo, cross-mailbox dedupe, routing into a category folder, filing through to paperless, and OCR of attachment images beyond what the existing extractors already claim.

**Your library is one list over several stores (LUM-724).** Until recently `/documents` showed only files you had uploaded or dropped into a watched folder. A paperless document, or an invoice you had deliberately filed from an email, was **searchable but not browsable** — search found it, the library did not list it. Someone who browses rather than searches concluded the feature had done nothing.

It was not only a listing problem, and the rest of it mattered more. Deleting a document works from its library row, so a paperless document had **no way to be deleted from Lumogis at all** — and because the paperless poll only ever asks for documents added *since last time*, a document you deleted in paperless stayed searchable in Lumogis indefinitely. That is a privacy problem rather than an untidiness one, and it is the reason this was worth doing before anything else in the paperless work.

So `/documents` is now **the complete picture of what Lumogis holds**. Every row carries a badge saying where it came from — *From paperless*, *From email*, or nothing at all for something you uploaded, because that is the ordinary case and badging everything would make the badge meaningless. **The actions differ by origin**, and that is what keeps a single list honest rather than pretending three different things are the same: paperless owns its documents, so a paperless row sends you to paperless rather than opening a Lumogis viewer.

Two actions are **refused, with the reason given up front** rather than failing when you press them. You cannot share an external document with your household yet: the system it came from can delete the original at any time, and a shared copy would outlive it. And you cannot re-ingest one, because re-ingest reads the file from disk and these documents do not live on your disk — the message names paperless or the email instead of saying "source unavailable", which would read as a bug.

Everything ingested **before** this change needs a one-off backfill to appear; it is an operator script rather than a button, because it necessarily touches every account. It skips attachments you declined and documents you have deleted, so running it does not undo decisions you have already made.

**Deleting an externally-filed document keeps its record.** The row that says "this attachment has been dealt with" survives the deletion, marked. Without that, the next sweep would see an undecided attachment again and — if you had written an *always file* rule for that sender — re-file it within the quarter hour, with no error and no explanation. What you deleted stays deleted; what the rule governs is what arrives next.

**Filing is a per-attachment decision (LUM-727).** LUM-702 shipped the opposite: enable a mailbox and every readable attachment was filed, with undo as the safety net. That trade assumes filing everything is acceptable *because* undo exists — which only holds when most attachments are worth keeping. In real mail they are not. The share not worth filing is large enough that a global rule does not work at all, and a library full of signature blocks, delivery notices and calendar invites is worse than an empty one: it makes search worse for the documents you actually wanted.

So the mailbox toggle now means **"show me this mailbox's attachments"**, and nothing reaches the library without you picking it or a rule you wrote saying so. The **review list** groups what is waiting **by sender, biggest group first** — the list is only affordable if it shrinks, and deciding once for whoever sends you the most is the largest single reduction available. Each attachment shows its **subject** alongside its filename, because `scan_0043.pdf` is not a decidable thing on its own. You can file or skip one at a time, or select a whole sender and do it in one action. There is also a **File to library** button on the message itself, for the moment you are already looking at the invoice and do not want a trip to a list.

**Where you actually find all this (LUM-742, ADR-193).** Everything above shipped complete and, for a while, unreachable: the review list, the rules list, the filing opt-in, the "Filed from email" list and LUM-697's unsubscribe view were each built, tested, and imported by nothing. The opt-in toggle was one of them, and it is the switch the whole sweep is gated on — so the feature was not merely hard to find, it could not be turned on at all. It now lives where its shape says it should.

**Email gains a second view.** `/email` keeps the three triage lanes and gains a tab strip; **Attachments** is the other tab, carrying a count when something is waiting and nothing when it is not. The review list there spans **all** your mailboxes at once, and each sender group carries the mailbox it arrived in when you have more than one — a filing rule belongs to a single mailbox, so a group that could not name one had nothing *Always file from this sender* could mean. A mailbox never gets starved out of that list by a busier one: the page is shared out per mailbox rather than filled newest-first, and if a mailbox has more waiting than the page could show, it says which.

**The empty version of that page is where you switch filing on.** Filing defaults off and never enables itself, so a page that simply said "nothing here" would leave the feature undiscoverable for anyone who had not already found the setting. Instead the empty state explains what filing does and offers the per-mailbox switches inline — and tells you what turning it on will actually surface, which is not the same answer every time: a mailbox you are enabling for the first time starts from now, whereas one you had enabled before resumes from your original opt-in and brings back everything that has arrived since. A mailbox in metadata mode, or one whose full ingest is selected but not switched on for this Lumogis, is explained rather than offered as a switch that would do nothing.

**Per-mailbox settings stay per-mailbox.** The filing switch and the standing rules live on the mailbox card in Settings → Email signals, alongside organize and cleanup; the unsubscribe view joins the cleanup section there. Configuration is a different kind of thing from a queue of decisions, and the two had been drifting into the same place.

**Rules are the exit from the list.** Next to every sender group is *Always file from this sender*, which is deliberately where it is: that is the moment you know the answer, not a settings page you visit later. Creating the rule also files what is already waiting from that sender — a rule governs future arrivals, and being told "always" then still seeing four pending invoices reads as the rule not working. Rules can also key on a **taxonomy category**; they key on its slug rather than its label, so renaming "Bills & finance" does not silently detach every rule that used it. A rule whose category you later delete is shown as **stale** rather than quietly removed — it cannot fire, and deleting a category is not the same as retracting a filing instruction.

**If paperless already watches that mailbox, Lumogis asks first (LUM-728, [ADR 192](decisions/192-lum-728-paperless-mailbox-overlap.md)).** Paperless can
monitor a mailbox itself, and if it does, a Lumogis rule on the same mailbox
files every document twice — once by each system, with nothing linking the two
copies. So the first *Always file from this sender* click on such a mailbox
returns the consequence instead of the rule, with **File anyway** beside it. The
click is the answer; Lumogis never decides this for you, and it never turns
filing off on your behalf. Answering once covers the whole list — the overlap is
a fact about the mailbox, not about the sender.

**And it warns in the other direction too (LUM-835/836).** That first check only
fires when you *create* a rule, so it never reached anyone who set Lumogis up
first and connected paperless afterwards — their existing rules simply began
filing twice with nothing said. Two surfaces now close that. Connecting paperless
refuses once, naming the mailboxes and how many rules each has, with its own
acknowledgement separate from the folder-sorting one: accepting "paperless may
miss some mail" is not the same answer as accepting "documents may be filed
twice", and being asked one question must never be taken as answering the other.
And the standing rules list on each mailbox card carries a line whenever paperless
also watches that mailbox — recomputed whenever you look, so it is current rather
than a stored flag that could go stale.

**When Lumogis cannot tell, it says nothing.** If paperless is unreachable, or its
API refuses, the check reports "could not tell" and both surfaces stay silent
rather than implying all-clear. None of this prevents the duplication — it only
makes sure you are told; documents already filed twice stay filed twice, and are
removable from the Lumogis library without touching what paperless holds.

Lumogis only asks when it is reasonably sure: it compares the mail server **and**
the username. If it can match the server but not the username — two mailboxes at
the same provider, which is ordinary in a household — you get a single line
saying paperless *may* also be watching, and nothing is blocked. A check that
cannot reach paperless, or is not permitted to read its mail rules, says nothing
at all rather than guessing; with no paperless configured this does nothing
whatsoever. Two settings control it, both optional:
`PAPERLESS_OVERLAP_CHECK_ENABLED` and `PAPERLESS_OVERLAP_TIMEOUT_S`.

One honest limit: if the paperless API token belongs to a user who does not own
the mail rules, paperless returns an empty list rather than an error, and Lumogis
cannot tell that apart from "no overlap". Point Lumogis at the token of the
account that configured the mail rules.

**Two things behave differently on purpose, and both are visible.** Saying *no* is free and immediate: nothing is fetched, so the row disappears as soon as you click. Saying *yes* is not — each file is a real fetch, extract and embed that can fail on its own, so accepted rows stay put until the server says which ones actually landed, and anything it could not file keeps its place with the reason attached. A **decline is terminal** in the database (the part is judged once, ever, which is what stops tomorrow's sweep re-offering it) but **reversible by you** from *Filed from email*, where declined rows are listed like any other skip.

**Stopping a rule is not a retraction.** Deleting a rule stops future filing and changes nothing already filed — those documents keep their place in your library and keep their undo. The UI says so, because "Stop" reads like it would take things back. Deliberately, the rules that file attachments live in their **own** table rather than joining LUM-697's sender rules: *hide this sender* and *file this sender's attachments* are incompatible instructions, and one table would make the contradiction live. Split, hiding simply wins — a suppressed message never becomes a signal, so it never produces an attachment for a file rule to match.

**The background sweep got cheaper, not busier.** It no longer files what it finds; it applies rules only. Its IMAP and embedding cost is now proportional to what you have actually asked for, and with no rules configured it is one cheap query and an exit.

**Changing your mind, and the cost of a tick (LUM-721, LUM-722).** An undone filing now has a **File again** action. It exists because undo is deliberately sticky — the sweep will never re-file on its own, since a filing that reappeared tomorrow with no explanation is worse than one that stays gone — so putting something back has to be something you ask for. It re-runs the fetch and extraction (the bytes were never stored), and it refuses if the same file has since arrived from another message, rather than filing a second copy. Separately, a sweep now uses **one mailbox connection per run** instead of one per message: connecting and logging in for every message is what gets an account rate-limited or locked out by a provider. The connection is opened only if something actually needs downloading, and is replaced rather than reused if it drops, so one hiccup costs one attachment rather than the rest of the run.

**Not in v1 (attachments):** rendering inline `cid:` images, previews, virus scanning, an *"ignore this sender's attachments"* rule (declining is per attachment; the rule table's `action` CHECK admits only `file` and must be widened deliberately), rules that span mailboxes, and **sharing an externally-filed document with your household** (refused for now — see LUM-724 above).

- **Legacy single-mailbox env fallback** (only under `AUTH_ENABLED=false`, `user_id="default"`): `EMAIL_IMAP_HOST` / `EMAIL_IMAP_PORT` / `EMAIL_IMAP_USERNAME` / `EMAIL_IMAP_PASSWORD`.

**Routines** — Scheduled automation elevating trusted **Ask** actions toward **Do** after enough clean approvals (`ROUTINE_ELEVATION_THRESHOLD`).

**Notifications** — Core signals, digest, and routine-elevation paths route through a unified in-process **dispatcher** ([ADR 077](decisions/077-lum-189-notification-architecture.md), **LUM-93** chunk 1 shipped) with **ntfy**, **Web Push**, and **in-app SSE** channel adapters. Per-user **routing preferences** (notification type × channel) live in Postgres (`notification_preferences`, `notification_user_settings`) and are editable in Lumogis Web **`/me/notifications`** ([ADR 098](decisions/098-lum-93-notification-settings-ui.md)). The read-only **`GET /api/v1/me/notifications`** channel-status façade remains separate from prefs. **Quiet-hours** columns exist but full policy UI is **LUM-144**; dispatcher applies server-side quiet-hours gate when start/end are set (UTC fallback when timezone unset).

**Web Push prefs bootstrap (operator recovery):** On startup, core runs a one-time idempotent seeder keyed by `webpush_prefs_seeded_v1` in `app_settings`. If it fails, boot continues (fail-open per ADR 077/098); orchestrator logs `webpush_prefs_seeder: failed` at error level and tier defaults apply until a successful run. Fix the underlying DB/connectivity issue and **restart core** — the seeder retries automatically because the success flag was not written.

**Implemented vs planned:** Dispatcher + prefs API + editable Web matrix are **shipped**. Browser **Web Push** subscription plumbing and minimal templates are **shipped**—see **§13**; **`ACTION_EXECUTED`** Web Push templates and inbox persistence remain **LUM-28** / **LUM-174**. Pushing notifications for **every** connector/action outcome category remains **incomplete**. The **ntfy server** remains optional; the **ntfy mobile app is not required** — Web Push and in-app SSE cover Lumogis Web surfaces.

#### Background model tasks (LUM-877)

Each background LLM job is a named **task** with its own ordered model list. Without any configuration every task uses its code default (what it used before), so nothing changes until you opt in. To choose models, uncomment the **`tasks:`** block in `config/models.yaml` and list model **aliases** (for example `qwen2.5`, not the Ollama tag `qwen2.5:7b`):

```yaml
tasks:
  session_summary: [qwen, llama]
```

| Task | What it does | Default | On-box only | First entry only |
| --- | --- | --- | --- | --- |
| `signal_enrichment` | Summarises and scores feed and page signals | `llama` | no | no |
| `email_classify` | Classifies incoming mail | `llama` | yes (also refuses an off-box default) | no |
| `email_reply_draft` | Drafts a reply | `llama` | yes (also refuses an off-box default) | no |
| `email_compose_refine` | Refines a message you are writing | `llama` | yes (also refuses an off-box default) | no |
| `entity_extraction` | Finds people, places and organisations | `llama` | yes (listed entries) | no |
| `relation_extraction` | Finds relations between entities in memory you add | `llama` | no | no |
| `session_summary` | Summarises a chat session | `llama` | yes (listed entries) | no |
| `routine_weekly_review` | Writes the weekly review prose | `llama` | yes (listed entries) | no |
| `temporal_extract` | Extracts when a fact became true | `llama` | yes (listed entries) | no |
| `temporal_judge` | Judges whether a new fact contradicts an older one | `llama` (the eval-reference judge; auto-apply runs only on it) | yes (listed entries) | yes |

- **Rule:** the first listed entry that is usable for the user wins; the code default is the last resort. *Usable* means the model exists, passes the task's on-box rule, has a key for that user, is switched on, and is allowed by privacy mode.
- **On-box only:** tasks that can see email text accept only models on loopback, a LAN address, or a host in `EMAIL_LLM_ALLOWLIST`; any other listed entry is skipped. This cannot be loosened by configuration.
- **First entry only:** `temporal_judge` never falls back down its list, because its verdicts can invalidate facts.
- **Not runtime failover:** the list is read when a job starts. A listed model that is down fails the job; it does not move to the next entry.
- **Prompt size:** a model pulled into Ollama has no `context_budget`, so prompts are sized to 2048 tokens. Define the model under `models:` with a `context_budget` for larger prompts.
- **Retired variables:** `SIGNAL_LLM_MODEL`, `EMAIL_CLASSIFY_MODEL`, `LUMOGIS_TEMPORAL_EXTRACT_MODEL` and `LUMOGIS_TEMPORAL_JUDGE_MODEL` are no longer read; Core logs one warning at start-up for each that is set.
- **Start-up warnings (log codes):** `retired_model_env`, `task_config_invalid`, `task_model_unsatisfiable`, `task_model_no_context_budget`, `task_model_needs_user`, `task_models_ollama_unavailable_at_boot`, `task_models_boot_check_failed`; and, when the temporal pipeline is on, `temporal_judge_not_reference`. Under `AUTH_ENABLED=true` Core refuses to start if a task that runs without a user has no model that works without a per-user key.
- **Diagnostics:** the **Background model tasks** table on the admin Diagnostics page (`GET /api/v1/admin/diagnostics`, field `tasks`) shows each task, its configured list with a reason for every skipped entry, and the model it uses now for you.

## 11. Knowledge graph

**Lay view:** An optional “knowledge graph” can track relationships between entities beyond flat search. You do **not** need it for basic chat and RAG.

**Technical view:**

- **In-process vs service:** Graph routing is described in **[ADR 002](decisions/002-graph-store-falkordb.md)**; operators enable `GRAPH_MODE=service` with the FalkorDB and `lumogis-graph` overlays. That is the only mode that works on the standard Core image; `inprocess` needs a Core build that includes `services/lumogis-graph/`. **Default `GRAPH_MODE` is `disabled`.** The graph is AGPL-3.0-only (**[ADR 229](decisions/229-lum-855-kg-agpl-relicence.md)**).
- **FalkorDB** — backing store for KG in service mode; see `docker-compose.premium.yml` / FalkorDB overlays. Optional **`docker-compose.falkordb.yml`** publishes **`127.0.0.1:${FALKORDB_HOST_PORT:-6380}:6379`** so host-side tools (including **`make m1-compat-with-retry`**) can use **`FALKORDB_URL=redis://127.0.0.1:6380`** without container IP discovery; in-network services keep **`redis://falkordb:6379`** (**[ADR 053](decisions/053-lum-237-falkordb-host-port-loopback-publish.md)**).
- **`query_graph` tool** — When bridged over HTTP (capability invoke contract v1 — **[ADR 169](decisions/169-lum-41-capability-invoke-contract-v1.md)**), Core POSTs the wrapped request envelope to the tool's declared **`invoke.path`** (KG: `/tools/query_graph`, tool name `graph.query`) and parses the **`{ok, output|error}`** response envelope—[`tool-vocabulary.md`](architecture/tool-vocabulary.md) and **[ADR 002](decisions/002-graph-store-falkordb.md)**.
- **Temporal validity (LUM-104, flag-gated, default off):** with **`LUMOGIS_FF_TEMPORAL_KG`** on (requires `GRAPH_MODE=inprocess` in v1), KG edges carry a two-axis temporal model (`created_at`/`valid_at`/`invalid_at`/`expired_at` + `edge_uid`), graph reads filter out invalidated/expired edges (null-tolerant — legacy edges pass), and a background Core-side pipeline extracts real-world `valid_at` and detects contradictions with local models. Contradictions **archive** facts as no-longer-current (soft `invalid_at` + a `SUPERSEDES` history edge) — Lumogis never destroys memories; forgetting stays a deliberate user act (LUM-544). Auto-apply is **off** (shadow-mode proposals only) until the hand-graded eval meets the precision bar on the reference judge model; admin backfill via **`POST /graph/backfill/temporal`**. See **[ADR 151](decisions/151-lum-104-temporal-validity.md)** (and ADR 150 for the build-vs-wrap decision).
- **Daily reconcile — orphan cleanup and co-occurrence counts (LUM-952):**
  - **Orphan cleanup scope.** The orphan GC removes entity nodes whose `(user_id, lumogis_id)` no longer has an `entities` row (merge losers whose `ENTITY_MERGED` webhook was lost, deleted entities, shared projections after unshare or purge). It covers `:Entity` (shared/system) and the personal type labels `:Person`, `:Organisation`, `:Project` and `:Concept`, never evidence (`Document`, `Session`, `Note`, `AudioMemo`), code-structure or Memory nodes.
  - **Ordering.** It scans the graph before reading Postgres, so an entity created during the pass is never mistaken for an orphan.
  - **Mass-delete guard.** It refuses to delete **personal** nodes when more than `GRAPH_GC_MAX_ORPHANS` (500) would go, or when at least `GRAPH_GC_MIN_ORPHANS_FOR_RATIO` (25) of them are more than `GRAPH_GC_MAX_ORPHAN_RATIO` (20%) of the personal nodes scanned. Shared `:Entity` orphans are always cleaned up. A refused pass is logged as a WARNING and reported as `orphan_gc_refused` in the reconcile summary.
  - **`co_occurrence_count`** on `RELATES_TO` is the number of distinct evidence items both entities appear in, recomputed from Postgres and only ever raised by projection. Replays and two-sided projection no longer inflate it. `GRAPH_COOCCURRENCE_THRESHOLD` (3) applies to that count.
  - **Operator procedure (graph service).** Both routes are dry runs unless `"dry_run": false`, and a real run needs `GRAPH_ADMIN_TOKEN` set on the service. They are not exposed through Caddy; call them inside the stack:
    - `docker compose exec lumogis-graph curl -s -X POST localhost:8001/kg/orphan-gc -H "X-Graph-Admin-Token: $GRAPH_ADMIN_TOKEN" -H 'Content-Type: application/json' -d '{"dry_run": true}'` counts orphans per label.
    - `POST /kg/recount-cooccurrence` lowers counts inflated before this change; edges without a count (typed relations) and pairs with no shared evidence are left alone.
    - If a daily pass is refused, check a dry run, then run once with `"force": true` or raise `GRAPH_GC_MAX_ORPHANS`. The env knobs are the only override in in-process mode.
  - **Operator procedure (in-process mode).** There is no HTTP route; call the same functions in the orchestrator container. Both default to a real run here, so pass `dry_run=True`:
    - `docker compose exec orchestrator python -c "from plugins.graph.reconcile import garbage_collect_orphan_nodes as gc; print(gc(dry_run=True))"` counts orphans per label.
    - `docker compose exec orchestrator python -c "from plugins.graph.reconcile import recount_cooccurrence as rc; print(rc(dry_run=True))"` reports how many counts would change.
  - **Stop phrases are Core's.** Core discards stop phrases before an entity is stored, in every graph mode (`{workspace}/config/stop_entities.txt`, edited on Core's `/graph/mgm`, backed up). The graph service keeps no list; its `/kg/stop-entities` returns 410 with a pointer to Core.
- **KG-specific vs generic:** KG proxy and manifest are the **reference capability**; generic discovery, health, `/tools/{name}`, and bearer env patterns apply to **any** capability.

## 12. Optional capability services

**Plain English:** A capability is an **extra program** Lumogis can discover—like a plug-in module, but running in its **own container**, with its **own data** if needed.

**Technical contract (invoke v1 — [ADR 169](decisions/169-lum-41-capability-invoke-contract-v1.md)):**

- `GET {base}/capabilities` — `CapabilityManifest` (`orchestrator/models/capability.py`, vendored to `services/lumogis-graph/models/capability.py`); includes `contract_version`, per-tool `invoke {method, path}`, `is_write`/`idempotent`/`timeout_ms`, and manifest `auth`.
- `GET {base}/health` — liveness for registry (`health_endpoint` on the manifest).
- **Invoke** — Core POSTs to each tool's declared **`invoke.path`** (default `/tools/{name}`) the v1 request envelope `{contract_version, tool, arguments, meta}`; the capability returns `{ok:true, output}` or `{ok:false, error:{code, message, retryable}}`. Core validates `output` against a non-trivial declared `output_schema` and maps transport failures into the same error vocabulary. Bearer tokens use `LUMOGIS_CAPABILITY_BEARER_<SANITIZED_ID>` (fail-closed when `auth.mode="bearer"` and unset); **`X-Lumogis-User`** / **`meta.user`** are **attribution only**, not authentication or data scoping — per-user scoping uses **`arguments.user_id`**.
- **No shared Core DB credentials** on capability containers—policy in remediation Phase 5.

**Mock capability:** `services/lumogis-mock-capability/` + `make mock-capability-test`; compose overlay `docker-compose.mock-capability.yml` — **not** in default `docker-compose.yml`.

**Status:** Phase 5 **scaffolding** is **sufficient for self-hosted** experiments; **Phase 6** marketplace / signed manifests / mTLS-by-default is **deferred**—see **§17**.

**Styling convention (LUM-852, [ADR 222](decisions/222-lum-852-dead-css-classes.md)):** every global CSS class in Lumogis Web is `lumogis-`-prefixed. `clients/lumogis-web/tests/design/classNames.test.ts` runs under `make web-test` and fails on a `className` token that is neither `lumogis-`-prefixed nor defined in `src/design/tokens.css`, and on any unprefixed class that stylesheet defines. Visually hidden text uses `.lumogis-visually-hidden` (the two admin fieldset legends included); the guard does not see classes built in variables, CSS-module members, or whether a `lumogis-*` class has a rule.

**Password management** — shipped per [ADR 029](decisions/029-self-hosted-account-password-management.md).  
**Admin import/export** — inventory + dry-run/real import via `/api/v1/admin/user-imports`; per-user export via `/api/v1/me/export` with `target_user_id`—see [`clients/lumogis-web/README.md`](../clients/lumogis-web/README.md). Refusal → HTTP semantics (including **413** policy cap vs reserved **507** for host storage exhaustion) are documented in [`docs/guides/per-user-export-format.md`](guides/per-user-export-format.md).

**Sign-out and shared devices (LUM-886, [ADR 242](decisions/242-lum-886-web-signout-client-state.md)):** one module, `clients/lumogis-web/src/auth/clientStateBoundary.ts`, decides which browser state belongs to the signed-in household member. At sign-out (explicit logout **and** session expiry) it removes the chat-tab threads (`sessionStorage`), every `lumogis:draft:*` IndexedDB key, the TanStack query cache and its persisted slot, and the email-activation and invite-onboarding hints. It never calls `sessionStorage.clear()`, `localStorage.clear()` or idb-keyval `clear()`; a source-scanning test (`tests/auth/storageInventory.test.ts`) fails when a new file touches browser storage without being classified. Explicit logout also deletes this browser's Web Push row on the server, closes shown notifications and unsubscribes the browser (each step bounded; the logout POST is aborted after 3 s), and signs out the other open Lumogis tabs of that browser through `storage` events. At sign-in, a device marker (`lumogis:last-signed-in-user`), a per-tab owner tag (`lumogis:tab-owner`) and the provider's previous user are compared with the new member; on any mismatch, or an absent marker, the same wipe runs (keeping `/me`) and leftover push is unsubscribed before any page renders. The **capture outbox is never wiped**: rows carry `owner_user_id` and Quick Capture lists, counts, syncs and discards only the signed-in member's rows; rows saved before this change appear under *Saved on this device before an update* with **Sync to my account** / **Discard**. `ApiClient` tracks whose session it holds: a refresh that returns another member is refused (no replay, the tab signs out), and an outbox sync stops as soon as the live session is no longer the rows' owner. After updating, each device drops chat drafts and chat-tab threads once and Web Push must be switched back on once.

**Legacy admin:** FastAPI **root-mounted** pages (`/dashboard`, `/settings`, `/graph/*`, `/backup`, …) still exist and are linked from older UX; **full replacement** of that SPA by Lumogis Web is **deferred**. **`GET/PUT /settings`** (admin JWT) exposes **`ingest_paths`** (effective host paths), **`pending_ingest_paths`**, **`restart_required`**, and **`paperless_configured`** (boolean only — no Paperless URL). **`filesystem_root`** / **`pending_filesystem_root`** are **removed** (LUM-397). With **two or more** paths, the API returns **`ingest_compose_snippet`** (copyable override YAML) and, when **`/project/.env`** is writable, may auto-write **`docker-compose.override.yml`**, append **`:docker-compose.override.yml`** to **`COMPOSE_FILE`** (colon-separated for **stack-control**), and set container paths **`/data-1`**, **`/data-2`**, … in **`INGEST_PATHS`**. Indexed paths **must not contain spaces** (Compose limitation). Shrinking to a single path removes the managed bind block and unchains the override file when empty. Runtime **search**, **tools**, chat **`read_file`**, and **ingest-path watchers** use **`INGEST_PATHS`** (container JSON). Chat **`read_file`** and the filename fallback of search reach only files that are indexed and visible to the caller under the same rule as search (no admin exception; LUM-884), and **`GET /browse`** (the legacy folder picker) is admin-only. **`POST /api/v1/ingest/upload`** (user JWT) queues per-user document push ingest to persistent storage under **`ai-workspace/uploads/`**.

OpenAPI: orchestrator `/openapi.json`; committed snapshot `clients/lumogis-web/openapi.snapshot.json`; codegen `npm run codegen` / `make web-codegen`. **Regenerate snapshot** (from repo root): `cd orchestrator && python -m scripts.dump_openapi --pretty --sort-keys --out ../clients/lumogis-web/openapi.snapshot.json` (same as `test_api_v1_openapi_snapshot.py`). **CI** additionally runs **`make openapi-breaking-check`** (oasdiff semantic diff vs merge-base / `HEAD~1` after the LUM-94 snapshot gate) — see **CONTRIBUTING.md** (LUM-302).
- **Legacy routes** — `/ask`, `/ingest` (an admin-only **Rescan** of the configured library folders: no folder argument, any body field is a 422; files are filed under `INGEST_PATHS_OWNER_USER_ID`, otherwise the calling admin; it needs `INGEST_PATHS` or `FILESYSTEM_ROOT`), `/search`, OpenAI-compatible **`/v1/*`** paths (used by optional LibreChat and similar clients), root admin pages—still present for compatibility.
- **`/mcp/`** — MCP streamable HTTP (trailing slash matters for some clients). **Cursor (local):** the **`lumogis-mcp`** stdio bridge (`clients/lumogis-mcp/`, `make lumogis-cursor-install`) forwards tool calls to this endpoint without re-declaring tools; **`make test-cursor-integration`** runs the LUM-299 smoke harness (in-process `/mcp/` breadth over `tests/fixtures/coding_bank.json` plus a real stdio subprocess slice) without Docker — see [ADR 137](decisions/137-lum-299-cursor-integration-smoke-test.md); **opt-in tier-2:** **`make prove-cursor-integration-full`** seeds the same fixture into **lumogis-test** Postgres+Qdrant and asserts **`recall` p95 &lt; 200ms** ([LUM-540](https://linear.app/lumogis/issue/LUM-540); `tests/integration/README.md`); direct HTTP transport remains supported for advanced setups (Step 10 in `docs/private/ops/connect-and-verify.md`). Read tools (`memory.*`, `entity.*`, `context.build`) plus **write** tools **`add_memory`**, **`add_entity`**, **`add_relation`** (LUM-291) that persist into the knowledge graph; write tools require a token carrying the **`mcp:write`** scope (`mint()` supports scopes; `NULL` = unrestricted). New memory text lives in `memories`, typed relations in `entity_edges` (Postgres system-of-record, projected to FalkorDB when enabled); both bank-scoped. See [ADR 128](decisions/128-lum-291-mcp-memory-write-surface.md). The write set is completed (LUM-526) by **`forget`** (reversible **soft archive** — sets `valid_until`, never a hard delete), **`update_observation`** (supersede: add new with `metadata.supersedes`, then archive old, history retained), and **`checkpoint`** (a `metadata.kind=checkpoint` session-boundary memory); all three also require **`mcp:write`**. Per-memory hard erasure is an admin concern, kept off the MCP surface (deferred, LUM-529). See [ADR 129](decisions/129-lum-526-mcp-supersede-archive-tools.md). Tokens are minted with a chosen scope (LUM-527): **`POST /api/v1/me/mcp-tokens`** accepts a validated **`scopes`** list (allowlist `mcp:read`/`mcp:write`; unknown values and `[]` → 422; **omitted/`null` ⇒ read-only `["mcp:read"]`** — LUM-531; write requires explicitly sending `mcp:write`), and **Lumogis Web → Me → MCP tokens** offers a **Read-only / Read + write** selector (default least-privilege) plus per-token access display — closing the fail-open default so **no** token minted via the API can write unless write is explicitly granted (the route never mints an unrestricted `NULL` token; `NULL` = unrestricted remains a legacy/internal-only state). See [ADR 130](decisions/130-lum-527-mcp-token-scope-selection.md). **Origin guard (LUM-296):** requests with a non-loopback `Origin` header are rejected with `403 origin not allowed` before bearer evaluation; absent `Origin` (Cursor, curl, stdio) and loopback origins pass — see [ADR 132](decisions/132-lum-296-mcp-origin-dns-rebinding-guard-shipped.md). The **read** surface gains **`recall`** (LUM-295) — fused retrieval over the LUM-291 memory store combining **semantic** (Qdrant), **BM25** (Postgres `tsvector`, migration `041-memories-fts.sql`), **graph** (1-hop `entity_edges`, Postgres-default), and a **temporal** validity filter (`as_of`), merged with Reciprocal Rank Fusion and an optional cross-encoder rerank (`cross-encoder/ms-marco-MiniLM-L-6-v2` via the existing `sentence-transformers` path; env **`RECALL_RERANKER_BACKEND`**/**`RECALL_RERANKER_MODEL`**). Results carry `source_strategies` and `entity_ids`; the temporal filter is enforced Postgres-side at hydration, so `forget`/`update_observation` (LUM-526) are observable (archived memories drop out). Like the other reads, `recall` is **ungated** (no `mcp:write`). See [ADR 133](decisions/133-lum-295-tempr-recall-fusion.md). **Coding-context type registry (LUM-294):** `add_entity` accepts these `entity_type`s — base `PERSON`/`ORG`/`PROJECT`/`CONCEPT` plus coding `CODING_DECISION`/`CODING_CONVENTION`/`COMPONENT`/`FAILURE`/`SESSION`/`TASK`/`LIBRARY`; `add_relation` accepts `DEPENDS_ON`/`PART_OF`/`DECIDED`/`RELATES_TO`/`SUPERSEDES`/`DECIDED_BY`/`IMPLEMENTS`/`REPLACES`/`CAUSED_BY`/`DISCUSSED_IN_SESSION`/`BLOCKED_BY`/`REFERENCES_ISSUE`. Tokens are **`UPPER_SNAKE`** (send `CODING_DECISION`, not `CodingDecision` — the validator upper-cases but does not insert underscores; `decided_by`/`DECIDED_BY` both work, `DecidedBy` does not). The registry is an in-code allowlist (no migration to add a type), and `add_memory`'s LLM relation extraction proposes the coding relations too. `checkpoint` auto-creates a `SESSION` entity per checkpoint. `DECIDED_BY` (subject→decision) coexists with the legacy `DECIDED` (decision→subject). **Bank isolation (LUM-293):** memories and edges are bank-scoped (`coding`, `personal`, `default`); Qdrant uses payload tenancy on `bank` (tenant index); FalkorDB routes each bank to a separate graph via `get_graph_store(bank)`; `recall` accepts `bank="*"` for cross-bank read opt-in; entities remain user-scoped (names visible across banks). See [ADR 138](decisions/138-lum-293-bank-isolation.md).
- **`/events`** — SSE stream.
- **Caddy** — Terminates TLS optional; routes API and events to Core; SPA fallback for `/`.
- **CSRF / Origin** — Cookie-authenticated writes use same-origin assumptions; set `LUMOGIS_PUBLIC_ORIGIN`—`ARCHITECTURE.md`, `.env.example`. In v1, **Bearer**-authenticated writes skip `require_same_origin` by design; narrowing that bypass ships with the `cross_device_lumogis_web` cookie-session programme—see the module docstring in `orchestrator/csrf.py` and [ADR 046](decisions/046-lum-35-fp017-per-user-backup-followups.md).

## 15. Deployment and local development

**Stack:** `docker-compose.yml` — orchestrator, Postgres, Qdrant, Ollama, stack-control, **Caddy**, **lumogis-web**, **`backup`** DR sidecar (LUM-185); optional **LibreChat** profile (legacy-compatible chat); optional FalkorDB / premium / GPU / dev overlays.

**Disaster recovery backup (LUM-185):** A **`backup`** Compose service runs **supercronic** on a schedule (default **`0 3 * * *`** in the container **`TZ`**) and writes verified snapshots under **`BACKUP_HOST_DIR`** (host bind, default **`./ai-workspace/backups`**) → in-container **`/backups/snapshots/YYYYMMDD-HHMMSS/`** with **`manifest.json`**. Stores: Postgres **`pg_dump -Fc`**, per-collection Qdrant REST snapshots, optional FalkorDB **`BGSAVE`** + read-only **`falkordb_data`** mount when the graph overlay is active. Since **LUM-892** the snapshot also holds a **`files`** store (manifest **`schema_version: 2`**; schema 1 still verifies and restores): **`scripts/backup/lib/files.sh`** copies the workspace (**`WORKSPACE_HOST_DIR`**, default **`./ai-workspace`**, mounted at **`/workspace`** in the orchestrator and the backup sidecar — uploads, inbox, quarantine, captures) minus **`backups/`** and **`mcp/`** into **`files/workspace/`**, hard-linked against the newest snapshot that passed verify, root-owned and read-only, with a **`sha256sum`**-format **`files.list`**. A failed file copy is retried without ownership changes and otherwise leaves a database-only snapshot (**`stores.files.status: "failed"`**, backup exits 1). Restore copies files back after the databases, never deletes, moves changed files to **`restore-displaced/<snapshot-id>/`**, and writes them as **`LUMOGIS_RUN_UID`** or the workspace owner; **`make backup-verify ARGS="<snapshot> --deep"`** re-reads every file. Capture photos and voice notes default to **`{WORKSPACE_PATH}/captures`** (explicit **`CAPTURE_MEDIA_ROOT`** / **`LUMOGIS_DATA_DIR`** still win); before LUM-892 they lived in the container's writable layer and were lost on recreate. The status endpoint reports a **`files`** store, a ten-item **`coverage`** list (covered / not covered: library folder, **`.env`**, models; the stop-entities list is covered since LUM-922, when it moved to **`{WORKSPACE_PATH}/config/stop_entities.txt`**) and **`files_missing`** / **`files_missing_by_area`** (indexed uploads and captures not on disk; inbox informational) — [ADR 248](decisions/248-lum-892-backup-uploads-capture-media.md). Operators use **`make backup`**, **`make backup-verify`**, and interactive **`make restore SNAPSHOT=snapshots/<id> --yes`** (stop orchestrator + lumogis-web before restore). Admin read-only status: **`GET /api/v1/admin/diagnostics/backup-status`** and the Lumogis Web **System status** backup card. Legacy **`POST /backup`** remains a **logical JSON export**, not DR — see **`docs/guides/backup-restore.md`** and [ADR 098](decisions/098-lum-185-backup-restore.md).

**Update mechanism (LUM-187):** migrations are forward-only numbered SQL files in **`postgres/migrations/`** applied idempotently by **`orchestrator/db_migrations.py`** on every container boot (a failed migration halts start and logs **`[migrations] ERROR …`** — never silent). Operators preview pending work with **`make migrate-dry-run`** (read-only), then update with **`make update`** (**`scripts/update/update.sh`** — records per-service image digests from running containers into **`.lumogis-state/previous-images.txt`**, generates **`rollback-compose.override.yml`** for rollback pinning, **`docker compose pull`**, **`docker compose build --pull backup`** (the backup image bakes in **`scripts/backup/`**; a failed build only warns — LUM-892), **`scripts/update/rescue-captures.sh`** (copies capture media out of the old orchestrator container before it is recreated; the update stops if it fails — LUM-892), **`up -d`** to restart and apply migrations, then **`/healthz`** plus a migration dry-run and boot-log check via **`scripts/update/common.sh`**). If an update goes bad, **`make rollback`** (**`scripts/update/rollback.sh`**) appends the saved override to **`COMPOSE_FILE`**, re-pins the previously-running image refs, and restarts with the same health + migration gate — it **requires a backup within `LUMOGIS_BACKUP_MAX_AGE_HOURS`** (default 24h, LUM-185) because schema migrations are not reverted; cross-migration data changes need **`make restore`**. Override generation uses **`scripts/update/write_rollback_override.py`** (unit-tested); it pins **`CAPTURE_MEDIA_ROOT=/workspace/captures`** for the orchestrator when **`.env`** sets no capture root, so a rollback to a pre-LUM-892 image keeps captures in the workspace. **`make build`** and **`make dev`** run the same capture rescue right before the recreate; **`make rescue-captures`** runs it alone. Both ops scripts prompt unless **`LUMOGIS_ASSUME_YES=1`**. Admin read-only version/update state: **`GET /api/v1/admin/diagnostics/update-status`** (compares running **`__version__`** to the latest GitHub release; fail-soft, no auto-update; tune via **`LUMOGIS_UPDATE_CHECK_ENABLED`** / **`LUMOGIS_UPDATE_REPO`**). **Deployment hardening (LUM-887):** Compose publishes the orchestrator on **`127.0.0.1:${ORCHESTRATOR_HOST_PORT:-8000}`** only; other machines reach Core through Caddy. **Client IP:** Caddy decides it. It trusts no upstream proxy by default (**`LUMOGIS_CADDY_TRUSTED_PROXIES`**, default `127.0.0.1/32`, space-separated CIDRs, with `trusted_proxies_strict`) and hands Core exactly one **`X-Forwarded-For`** value (`header_up X-Forwarded-For {client_ip}`; a client-sent `X-Real-IP` is stripped). Every orchestrator route in `docker/caddy/Caddyfile` goes through the `(to_orchestrator)` snippet. Core's **`LUMOGIS_TRUSTED_PROXIES`** takes IPs, CIDRs or hostnames and defaults to **`caddy`** in compose: hostnames are re-resolved every 30 s, single-flight, an unresolvable name trusts nothing, and a private range wider than /24 (IPv4) or /64 (IPv6) logs a WARNING. Unset outside compose still means trust nothing. **Process user:** the orchestrator entrypoint runs its one-shot init (LibreChat seed, secret rewrite, migrations) as root. It then repairs ownership of the paths the app writes: named volumes and image-internal dirs fully, host-visible binds (`ai-workspace`, `.env`, `config/librechat.yaml`, `docker-compose.override.yml`) only for root-owned entries, never `backups/snapshots/` or the rest of the checkout. It adds a passwd entry for the target UID and `setpriv`s to the **owner of the `/project` checkout**, or UID 10001 when that is root; **`LUMOGIS_RUN_UID`** / **`LUMOGIS_RUN_GID`** override it and `0` keeps root. Under rootless Docker, Podman or userns-remap it neither drops nor repairs, because container root is not host root there. `docker compose exec orchestrator` still enters as root. The HF cache lives at `/var/lib/lumogis/hf-cache` (`HF_HOME`, `hf_cache` volume). **`lumogis-web`** runs `nginxinc/nginx-unprivileged` as uid 101 on port 80, and both containers set `no-new-privileges`. Make targets that `pip install` through the entrypoint (`compose-test`, `compose-test-stack-control`, `compose-test-integration`, `web-caddy-headers*`, `caddy-client-ip-prove`) pass `LUMOGIS_RUN_UID=0`. Checks: **`make caddy-config-check`** (Docker only) and **`make caddy-client-ip-prove`** (live stack). — [ADR 246](decisions/246-lum-887-deployment-hardening.md).

## 16. Security model

- **Cloud LLM and connectors:** If you configure a **cloud LLM**, assume **prompt-sized payloads** (including retrieved snippets) may go to that provider. **Connectors** use **your** stored credentials to reach **their** services—network egress is expected when those features run. Neither path implies a bulk export of the whole corpus; still, treat outbound content as sensitive.
- **Trust boundary:** You run Lumogis on a **trusted LAN**; **admin** is powerful (user reset, imports, credential management).
- **Local recovery:** CLI password reset for operators with shell access—[ADR 029](decisions/029-self-hosted-account-password-management.md).
- **Secrets:** In encrypted credential store + env for server secrets; not echoed in diagnostics façades.
- **Refresh invalidation:** Password change/reset clears refresh **JTI**—stolen cookies short-lived after rotation.
- **Capability bearer:** Proves Core is allowed to call **your** capability instance; **`X-Lumogis-User`** labels who the action is **for**—capabilities must not treat it as proof of identity.
- **Network exposure and process privilege (LUM-887):** Core's port 8000 is published on loopback only. The per-IP login, reset, invite and ALTCHA limits key on the client IP that Caddy resolves, which a LAN host cannot choose. Neither the orchestrator app process nor the web server runs as root (see §15). Behind Tailscale Serve or a tunnel every device shares one per-IP bucket until `LUMOGIS_CADDY_TRUSTED_PROXIES` is set (`docs/deployment/remote-access.md`). `stack-control` compares its restart token in constant time. — [ADR 246](decisions/246-lum-887-deployment-hardening.md).
- **Internet exposure:** Not the default threat model for v1; reverse-proxy hardening, TLS, rate limits, and operator-proven **forgot-password** email (**LUM-65**, **[ADR 209](decisions/209-lum-65-forgot-password-reset.md)**) require **`LUMOGIS_PUBLIC_ORIGIN`** and ALTCHA—treat wide exposure as **extra** hardening work.
- **Responsible disclosure (public tree):** The policy for reporting **undisclosed** vulnerabilities—private channels, coordinated publication, safe-harbour framing, and credit defaults—is in **`SECURITY.md`** at the repo root and duplicated at **`.github/SECURITY.md`** for GitHub’s Security tab. See [ADR 044](decisions/044-coordinated-vulnerability-disclosure-policy.md).
- **Pre-launch audit (LUM-190):** Human-authored findings live under **`docs/security/pre-launch-audit-2026.md`**. CI exposes a path-gated **`security-audit`** job (`.github/workflows/ci.yml`) that runs **`make audit-local`** (blocking) plus advisory **Bandit**; local parity via **`make bandit-check`**. Methodology record: [ADR 060](decisions/060-lum-190-pre-launch-security-audit-methodology.md). `make audit-local` runs `npm audit` on Lumogis Web and `pip-audit` over every `requirements*.txt`; the only npm suppressions are the entries in the fail-closed table in **`scripts/npm_audit_allowlist.py`**, each version-gated, dev-only, checked against `src/` imports and carrying a `review_by` date after which the gate fails until the entry is re-checked. Advisories with a published fix are fixed through scoped npm `overrides` whose removal conditions are listed in the header of `scripts/audit_local.sh` ([ADR 223](decisions/223-lum-859-web-deps-security-audit.md)).

## 18. How to extend Lumogis safely (contributors)

**Do:**

- Put business logic in **`services/`**; keep **`routes/`** thin.
- Use **`ports/`** and **`config.get_*()`** from services—never **`from adapters`** in services or routes.
- Respect the **plugin import** allow-list—[`plugin-imports.md`](architecture/plugin-imports.md).
- Register connectors in **`connectors/registry.py`**; use **ToolCatalog** for visibility; use **ToolExecutor** / capability proxy for OOP tools.
- Add tests; update **OpenAPI snapshot** when changing `/api/v1/*`.
- Record architecture shifts in **ADRs** via project skills (`/explore`, `/verify-plan`).

**Do not:**

- Expose secrets in logs, diagnostics, or Web JSON.
- Bypass Core **permission** or **Ask/Do** policy from a client or capability.
- Give capability containers **Postgres/Qdrant** credentials.
- Slip **Phase 6 marketplace** assumptions into household code paths.
- Introduce new **`user_id="default"`** literals in hot paths—grep gates exist.

See [`CONTRIBUTING.md`](../CONTRIBUTING.md). **§19** below groups real extension work into **five practical families** and only then maps the lower-level building blocks—so you can choose a path without memorising every construct on day one.

## 19. Extending Lumogis without getting lost

Lumogis is **modular** and has **real moving parts**—services, routes, adapters, connectors, actions, signals, plugins, capabilities, MCP. That is intentional. It also means the docs can look like a long checklist of equal options, which oversells how often you need each one.

In practice, **most** changes fall into **five families** below. The underlying constructs stay important, but they are **building blocks**, not **eleven separate front doors** for every newcomer. Start from the family that matches your goal; reach for adapters, plugins, or MCP when the family (and **§19.4**) says so.

### 19.1 The simple decision tree

```text
Do you want a new UI or app?
  → Add a client.

Do you want Lumogis to talk to an outside service?
  → Add an integration.

Do you want new logic inside Core?
  → Add Core behaviour.

Is the feature heavy, optional, separately packaged, or premium?
  → Add an optional capability.

Do you only want an external agent to call an existing Core function?
  → Expose it through MCP.
```

**Rule:** Do not introduce a new architectural category unless one of these five families cannot express the need.

### 19.2 The five extension families

| Family | Use when | Usually touches | Avoid |
| --- | --- | --- | --- |
| **Add a client** | Building a new UI, mobile shell, desktop wrapper, script, or HTTP consumer. | `/api/v1/*`, OpenAPI snapshot/codegen, auth, maybe Caddy. | Direct DB access, duplicating Core policy, sending secrets to a third-party server. |
| **Add an integration** | Lumogis must talk to another service (calendar, notification, LLM provider, storage, …). | Connector registry, credential services, permission labels, maybe tools/actions. | Storing credentials in random tables, bypassing Ask/Do, exposing secrets. |
| **Add Core behaviour** | Adding business logic inside Lumogis Core. | `services/`, `routes/`, adapters, actions, signals, tests; sometimes Compose + Caddy for a new daemon the stack needs. | Routes importing adapters, business logic stuffed in route handlers, missing `user_id` scoping. |
| **Add an optional capability** | The feature is heavy, separately packaged, optional, premium, or should not live inside Core. | Capability manifest, health endpoint, `/tools/{name}`, bearer config, ToolCatalog. | Shared Core Postgres/Qdrant credentials, trusting `X-Lumogis-User` as auth, marketplace assumptions. |
| **Expose through MCP** | External MCP agents need a **curated** Core function. | `mcp_server.py` and MCP tests. | Treating MCP as the primary tool registry or plugin system. |

### 19.3 How the lower-level constructs fit

| Construct | Role |
| --- | --- |
| **Service** | Business logic inside Core |
| **Route** | HTTP entrypoint |
| **Adapter** | Talks to infrastructure behind a port |
| **Connector** | External integration identity + credentials |
| **Action** | Audited side effect with Ask/Do |
| **Tool** | LLM-callable structured interface |
| **Signal** | External or scheduled event input |
| **Routine** | Repeated or automated behaviour |
| **Plugin** | In-process extension point |
| **Capability** | Out-of-process optional service |
| **MCP** | Curated external-agent transport |

These are **building blocks**. Most features use **several** of them. New contributors should start from the **five families** in **§19.2**, not from this raw list.

### 19.4 Recommended defaults

- **New UI:** Use `/api/v1/*`; do **not** talk to Postgres or Qdrant directly.
- **New internal logic:** Service first, thin route second.
- **New external credentials:** Connector + encrypted credential tier ([ADR 018](decisions/018-per-user-connector-credentials.md), [027](decisions/027-credential_scopes_shared_system.md)).
- **New side effects:** Action + Ask/Do + audit ([ADR 006](decisions/006-ask-do-safety-model.md)).
- **New LLM-callable behaviour:** `ToolSpec` backed by service or action.
- **Heavy or optional features:** Prefer a **capability**, not a plugin ([ADR 010](decisions/010-ecosystem-plumbing.md); graph boundary **[ADR 002](decisions/002-graph-store-falkordb.md)**).
- **Agent interoperability:** MCP only if the tool is **intentionally** part of the MCP surface ([ADR 017](decisions/017-mcp-token-user-map.md)).
- **New stack daemon:** Compose overlay (or base file), wire Core through an adapter and `config.py`—not ad hoc connection strings in random modules.

### 19.5 Plugin vs capability

#### Plugin

- Runs **inside** Core.
- Use **sparingly**—good for first-party or internal hooks.
- Shares Core’s process and failure surface ([ADR 005](decisions/005-plugin-boundary.md)).

#### Capability

- Runs **outside** Core.
- Preferred for optional, heavy, or premium features.
- Talks to Core over HTTP; **no** direct Core DB/Qdrant access.

**Rule:** For new optional features, **prefer a capability** over an in-process plugin unless there is a **strong** reason to run inside Core.

### 19.6 MCP is not another architecture pillar

MCP is **transport**. It exposes a **curated subset** of Core functions to external agents. It is **not** the primary plugin system, **not** the main tool registry, and **not** a way to bypass Core permissions, credentials, or audit. Heavy or stateful tools should usually be implemented as Core **services/actions** or **capabilities** first, then **optionally** exposed to MCP ([`tool-vocabulary.md`](architecture/tool-vocabulary.md)).

### 19.7 Practical examples

#### Example 1 — Add Google Drive connector

- **Family:** Add an integration.
- **Touches:** Connector registry, credential form, permission mode; possibly a tool or action that calls the API.

#### Example 2 — Add mobile app

- **Family:** Add a client.
- **Touches:** `/api/v1/*`, auth, OpenAPI snapshot/codegen; client talks only to your Core.

#### Example 3 — Add OCR service

- **Family:** Add optional capability if it is heavy or a separate container.
- **Touches:** Manifest, `/health`, `POST /tools/…`, bearer trust; optional ToolCatalog exposure.

#### Example 4 — Add weekly digest routine

- **Family:** Add Core behaviour.
- **Touches:** Signal or schedule, routine/action wiring, audit, notification path.

## 20. Glossary

| Term | Meaning |
| --- | --- |
| **Core** | Orchestrator + its stores and policies |
| **Orchestrator** | FastAPI app in `orchestrator/` |
| **Client** | HTTP UX surface (**Lumogis Web** first; optional LibreChat; MCP; scripts) |
| **Connector** | Named integration id for credentials + permissions |
| **Credential tier** | Per-user / household / system scope ([ADR 027](decisions/027-credential_scopes_shared_system.md)) |

| **Action** | Audited registry operation with Ask/Do |
| **Signal** | Polled or received event input |
| **Routine** | Scheduled elevation of trusted actions |
| **Plugin** | In-process extension |
| **Capability** | Out-of-process HTTP service with manifest |
| **MCP** | Agent transport at `/mcp/` |
| **KG** | Knowledge graph (optional FalkorDB-backed) |
| **Qdrant** | Vector store |
| **Postgres** | Relational metadata + audit |
| **Ask/Do** | Safety execution modes |
| **Audit log** | Durable record of actions/tools |
| **Household LAN** | Primary deployment trust model |
| **OOP capability** | Out-of-process tool provider over HTTP |
